## [Unreleased]

### Changed

- `spoa-hub.yaml` (2033 lines) split into the `libraries/spoa-hub/` directory of fragments per ADR-0008, mirroring the `gateway/` library layout: `_index.yaml` (load rules + `maps:`), `10-features.yaml` (utility snippets + features-spoa-hub + backends-100-spoa-hub), `20-config-content.yaml` (TOML + SPOE config rendering), `30-frontend-filters.yaml` (frontend filter directives), `tests/general.yaml` (default-rendering + multi-plugin tests), `tests/coraza.yaml` (Coraza WAF dispatch + modsec-snippet tests). `_libraries.tpl` merge entry switched to the directory form `"libraries/spoa-hub/"`. Rendered HAProxyTemplateConfig is byte-identical to pre-split; 253/253 chart validation tests pass; `make lint-chart` green.
- `annotation-compat.yaml` renamed to `ingress-annotations-compat.yaml`; values key `controller.templateLibraries.annotationCompat.enabled` renamed to `controller.templateLibraries.ingressAnnotationsCompat.enabled`. The scaffold was always Ingress-scoped — `BuildAnnotationSSLPassthrough` walks `resources.ingresses.List()` directly, the other macros take typed `*resources.ingresses.T` parameters — and the original generic naming made the typed Ingress access feel like a violation. A vendor library operating on a non-Ingress CRD writes its own equivalents at the same hierarchy level (2.5). No behaviour change — the macros themselves are unchanged; snapshot consumers who explicitly set `annotationCompat.enabled` need to rename the key. Library default stays `true`. See ADR-0003's Update section for the rationale.
- Tightened the Level-1 / Level-2+ shared-state boundary in `ssl.yaml`: the two Gateway-owned mTLS keys (`gf["mtlsBlockedListeners"]`, `gf["gatewayListenerMTLSConfig"]`) used to be pre-seeded by `features-050-ssl-initialization` "for convenience", even though they are produced and consumed entirely within the gateway library and ssl.yaml itself never reads them. The seed moved into `features-110-gateway-frontend-mtls` (its actual producer) — ssl.yaml no longer references Level-2+ keys. Behaviour unchanged.
- Renamed the cross-library mirror-fanout shared-state key `gf["mirrorRouteMirrorCount"]` → `gf["mirrorMaxFanout"]` (producer: `gateway/20-route-analysis.yaml`; consumer: `spoa-hub.yaml`). The previous name leaked the Gateway-API "Route" concept into spoa-hub's reads — undoing the resource-agnostic guarantee the spoa-hub refactor was meant to establish. The new name describes what the value is (max number of mirror filters on any single rule) without binding it to a specific routing-resource family. Local variables (`routeMirrorCount`) renamed to `mirrorFanout` to match.
- `spoa-hub.yaml` is now resource-agnostic per RULE #1: the per-Ingress `nginx.ingress.kubernetes.io/modsecurity-snippet` + `/enable-modsecurity` scan, the `nginx.ingress.kubernetes.io/*`-rooted validation, and the contributing `map-coraza-app-*` / `map-coraza-disabled-*` snippets moved out to `nginx-ingress.yaml` (new `util-nginx-ingress-coraza-scan` plus two map-population snippets). The `haproxy-ingress.github.io/waf` plugin-enabled check moved into `haproxy-ingress.yaml`'s existing waf-map walk. `spoa-hub.yaml`'s `spoa-hub-config-content` now reads the per-app modsec-snippet list from `gf["sphCorazaApps"]` instead of walking Ingresses directly, so an operator using a CRD-based annotation surface no longer has to fork `spoa-hub.yaml`. Behaviour unchanged — the same 253 chart-level validation tests pass with identical fail() messages.
- **`SPOA_PLUGIN_MIRROR_VERSION` bumped to `v0.5.0`** with per-dispatch HTTP-roundtrip timeout and connection-error retry budget plumbed from the chart-wide `timeout server` and a default of `retries 3`. The gateway library's `frontend-filters-550-gateway-mirror` snippet now emits two additional `set-var(...)` directives per mirror filter — `gw_mirror_timeout_ms_<i>` (derived from `extraContext.timeout_server`, default 50000ms) and `gw_mirror_retries_<i>` (derived from `extraContext.retries`, default 3) — and the `spoe-message-mirror-body` template wires them through as `arg_timeout_ms` / `arg_retries` SPOE args. Closes the gateway-conformance `HTTPRouteRequestMultipleMirrors` / `HTTPRouteRequestPercentageMirror` flakes that surfaced as 100%-failure dispatch metrics hitting exactly the prior 200ms uniform plugin default against backend Services that were freshly created seconds before the test fired (kube-proxy iptables / CoreDNS propagation cold-start race). The plugin treats `arg_timeout_ms=0` as absent (falls back to plugin default — guards against a misconfigured chart emitting a literal zero), and `arg_retries=0` as explicit "no retries". Mirror dispatch is fire-and-forget at the SPOE layer so a longer failure tail never affects user-visible latency.
- Removed the explicit `timeout_ms = 200` from `controller.config.spoaHub.plugins.mirror.params` in `values.yaml`. The fallback now lives in the plugin's own default (`60_000ms` since v0.5.0); the per-route value derived above wins for chart-emitted dispatches anyway. Operators who want a tight uniform mirror timeout should set `controller.config.haproxy.timeouts.server` (which the per-dispatch derivation reads from), not the plugin params knob.

### Fixed

- `haproxy.dataplane.validateConfig: false` now actually skips the dataplane API's internal `haproxy -c` validation. The chart's `dataplaneapi.yaml` heredoc placed `validate_cmd:` directly under `haproxy:`, but the dataplane API only reads `validate_cmd` from `haproxy.reload.*` (`client-native/v6/configuration/configuration_storage.go:131` — top-level `Haproxy.ValidateCmd` exists but is never consulted). The misplaced field parsed into the unused struct, then dropped on YAML re-serialize because of `omitempty` — masking the bug as "no `validate_cmd` line in the live config". Effect since chart `alpha.10` (when the flag was introduced): the flag had no observable behavior, every endpoint push ran the default `haproxy -c` regardless. Moving the field under `haproxy.reload.*` drops POST /configuration/raw server-side time from ~130ms to ~18ms (measured on the rolling-restart probe; cuts the 5s curl-visible 503 race that the timing window opened).
- Post-install `NOTES.txt` warning about Gateway API CRDs no longer claims "Gateway API library is enabled" when it isn't. The trigger condition `controller.templateLibraries.gateway.enabled=true AND no Gateway API CRDs on cluster` fires on every cluster without Gateway API by default (the values flag defaults to true), and the prior text implied the library IS loaded — while in fact `libraries/gateway/_index.yaml`'s `_helm_load.enable` predicate already short-circuited the library out of the merge because the capability is absent. Reworded the notice to state that the library was NOT loaded, point at the `_helm_load.enable` predicate as the source of truth, and give both directions of fix (set `gateway.enabled: false` to silence the notice if you don't want Gateway API; install the CRDs and re-upgrade if you do). Severity downgraded from `⚠️ WARNING` to `ℹ️` since for the no-CRDs default path nothing is actually broken.
- `networkPolicy.ingress.webhook.from` default switched from `[podSelector: {}, namespaceSelector: {}]` to `[ipBlock: 0.0.0.0/0, ipBlock: ::/0]`. The pod/namespace-selector default never matched the kube-apiserver — the apiserver runs as a host-network process (k3s embedded, kubeadm static-pod, any standard distro) and the dial it opens against the webhook pod has no pod identity from the CNI's NetworkPolicy enforcement layer. Result on every cluster with NetworkPolicy enforcement enabled: `failed calling webhook ... 502 Bad Gateway` / `proxy error ... while dialing <pod-ip>:9443`, surfacing as silent admission-blocks for every Ingress (and any other watched-resource validation the chart registers). Symptom hid behind k3s default flannel (which silently no-ops NetworkPolicy) until enforcement turned on. The two `ipBlock` entries cover IPv4 and IPv6 separately — K8s NetworkPolicy `ipBlock.cidr` is single-family, so `0.0.0.0/0` alone would still drop IPv6 apiserver dials on dual-stack / IPv6-only clusters. Operators who need a narrower rule for production override `from` with a CIDR list (typically the node network) — the webhook still enforces TLS + AdmissionReview shape, so source-address exposure is not the security boundary.
- `networkPolicy.egress.kubernetesApi` default grew an `::/0` entry alongside the existing `0.0.0.0/0`. The outbound apiserver dial is the mirror image of the inbound webhook dial — same host-network apiserver, same single-family `ipBlock` constraint, same dual-stack gap. The fix keeps both directions consistent.

- `base.yaml` no longer references gateway-library state, restoring Level-0 architecture. Two violations had crept in:
  - **`pod-listener-port.map`**: base.yaml's `util-routing-prefix` unconditionally referenced this map in the frontend routing logic, but the registrar (`features-170-pod-listener-port-map`) lives in the gateway library (only loaded when `gateway.networking.k8s.io/v1/GatewayClass` is present on the cluster). On a cluster without Gateway API CRDs, render failed at the auxiliary-set check ("rendered config references map files missing from the desired auxiliary set: pod-listener-port.map"). base.yaml now sets `txn.listener_port = txn.dst_port` by default and exposes a `frontend-routing-listener-port-*` extension point; gateway's new `frontend-routing-listener-port-100-gateway` snippet plugs in the pod-port → user-facing-port translation when the library is loaded. No map files are referenced when gateway is off.
  - **`bindHTTPSDefault` from `sslPassthroughBackends`**: `gateway/10-features.yaml` carried the cross-library propagation (any registered passthrough backend → bind on httpsPort), even though `sslPassthroughBackends` is shared state owned by ssl.yaml and populated by ingress libraries too (haproxy-ingress, nginx-ingress). Without gateway loaded, an annotation-driven `haproxy-ingress.github.io/ssl-passthrough: "true"` Ingress would register the passthrough backend but `bindHTTPSDefault` never lit, so `frontend ssl-tcp` silently didn't bind. The bind decision moved to ssl.yaml's new `features-140-ssl-passthrough-binds` (Level 1, next to the `sslPassthroughBackends` state and the `frontend ssl-tcp` consumer). Behaviour with gateway loaded is unchanged.
- Moved `test-k8s-haproxy-service-gateway-listener-ports` from `base.yaml` to `gateway/tests/17-per-gateway-services.yaml`. The test references `gateways` / `gatewayclasses` fixtures which only exist when the gateway library is loaded; living in base meant it ran (and failed at "resource type not found in watched resources") against any non-gateway render.

### Added

- `haproxy.dataplane.aclFormat` to override the dataplane API's Apache Common Log Format for the access log. Empty default leaves the dataplane API's built-in format in place; setting it (e.g. `'%h %l %u %t "%m %U%q %H" %>s %b "%{Referer}i" "%{User-agent}i" %{us}T'`) appends per-request μs duration, which the default omits. Test profiles (`dev`/`e2e`/`conformance`) ship this opted-in so CI failure dumps carry publish-step timing without a re-run; production keeps the unchanged default.
- ClusterRole now grants `apiextensions.k8s.io/customresourcedefinitions get/list/watch` so the controller's typebootstrap (which materialises typed top-level globals from each watched resource's OpenAPI schema) can resolve schemas via the CRD path. The OpenAPI v3 endpoint fallback works without this permission, but the CRD path gives higher-fidelity schemas (preserves x-kubernetes-preserve-unknown-fields subtrees); both are tried at controller boot. RBAC narrowed to read-only verbs only.
- Plugin metrics across the SPOA bundle. Every plugin bundled in the haptic/spoa-hub image (mirror, coraza, external-auth, fingerprinting, maxmind, otel, sso-auth) now emits Prometheus counters / gauges / histograms through the hub's `/metrics` endpoint. No chart-side opt-in — metrics surface when each plugin is enabled. Names appear with a `plugin_<plugin>_` prefix.

- HAProxy-Ingress and nginx-ingress `auth-headers-succeed` / `auth-headers-fail` annotations now emit their `http-request set-header` / `http-after-response set-header` directives into BOTH the HTTP/1.1 and HTTP/2 cleartext frontends, not just whichever frontend rendered first. The chart previously deduped the unique header set via `first_seen`, which is render-scoped and shared across the two `render_glob "frontend-filters-*"` calls (one per frontend) within a single haproxy.cfg render — so the second frontend's render saw `first_seen` return false for every header and emitted nothing. Effect: HTTP/1.1 clients hitting an auth-protected Ingress saw the 200 from the backend instead of the chart's 401-with-`WWW-Authenticate` / `X-Error-Reason` response. Caught by the e2e `TestIngressAuthHeadersFail` and tracked as #49. Switched to a local map-based dedup (within the ingress-walk loop) that resets per snippet render, so both frontends now emit the same set of directives.

- SPOA hub mirror plugin no longer flakes the upstream `HTTPRouteRequestMirror` / `HTTPRouteRequestPercentageMirror` / `HTTPRouteRequestMultipleMirrors` conformance tests. The chart now floors the rendered `mirror-<i>` SPOE message slot count at a static minimum (`spoaHub.mirrorStaticMinSlots`, default 4) — applied to both the SPOA-hub-side TOML `messages = [...]` and the haproxy-side `spoe.conf` group declarations. Issue #47.

  The chart originally carried a `mirror-1..mirror-4` static default. That default was removed in the same MR that introduced `skip_reload=true` on auxiliary file UPDATEs (controller `77c760c2`), with the rationale "the earlier-floor-of-4 workaround for a controller-side ordering race is no longer needed". That rationale was correct for **race A** (aux-file PUT ordering against haproxy reload) but missed a separate **race B** that the floor was independently masking: the SPOA hub sidecar reloads plugin handler state on every TOML file change, so any transient render that emits `messages = []` (chart's `routeMirrorCount` is recomputed per render — if the resource watcher snapshot hasn't observed an HTTPRoute with a `RequestMirror` filter yet, or a conformance subtest just tore one down, the count drops to 0 and the TOML follows) deregisters the mirror plugin's `mirror-1` handler at the hub. Every in-flight `send-spoe-group mirror-1-group` from haproxy then hits the hub's "no plugins registered for message" path and gets silently dropped. The static floor closes race B by keeping the messages list at a known-good minimum regardless of the per-render route observation.

  **Do not remove the floor without confirming race B is independently resolved.** `skip_reload=true` only addresses race A; the never-shrink-messages upstream work that would address race B is tracked under #47 (SPOA hub plugin loader change, not chart-side). Until that lands, workloads with > 4 mirrors per HTTPRoute rule retain a smaller version of race B for slots 5+ — the floor only raises the minimum, never caps the dynamic ceiling, so a 12-mirror route still allocates 12 slots, but slots 5..12 are still exposed to the transient-empty-messages race.

### Changed

- Bundled SPOA image bumped to spoa-hub v0.6.0 with the v2-consumer release of every plugin (plugin-API `PLUGIN_API_VERSION` 1 → 2 transition, append-only vtable evolution — v1 plugins still load on the v0.6.0 hub, v2 plugins still load on v0.5.x hubs).
- HTTPRoute `RequestMirror` filter now detects HTTPS targets and dispatches over TLS. Previously the chart hardcoded `set-var(txn.gw_mirror_scheme_<i>) str(http)` for every mirror filter — operators setting up a mirror to an HTTPS Service would have seen mirrors silently sent over plain HTTP (the plugin supported `arg_scheme=https` since v0.1.0 but never received it). The chart now resolves the mirror's `backendRef` → Service → port spec and emits `str(https)` when the port carries `appProtocol: https`, `appProtocol: kubernetes.io/https`, or `name: https` (the three Gateway-API / Kubernetes Service conventions for declaring an HTTPS port). Mirror dispatch still doesn't validate TLS certs by default (`verify_tls = false` plugin param) — operators wanting strict validation flip it once `BackendTLSPolicy`-style trust material is plumbed through.
- The chart-rendered list of `mirror-<i>` SPOE messages is now sized fully dynamically per render. Previously the chart hardcoded `messages: ["mirror-1", "mirror-2", "mirror-3", "mirror-4"]` in `spoaHub.plugins.mirror.messages`, capping at 4 mirror filters per HTTPRoute rule with no clear error if exceeded. The gateway library's `20-route-analysis` pass now computes the actual max-mirrors-per-route in the cluster and writes it into `globalFeatures["mirrorRouteMirrorCount"]`; the spoa-hub library expands `messages: ["mirror"]` (a placeholder) into `mirror-1`..`mirror-<count>` in both the hub TOML and `spoe.conf`. No cap and no static floor — a route with 12 mirror filters allocates 12 message slots; with 0 mirror filters anywhere the list expands to empty and the plugin is loaded but never invoked. The earlier-floor-of-4 workaround for a controller-side ordering race is no longer needed: that race is now resolved upstream by `skip_reload=true` on auxiliary file UPDATEs (see controller CHANGELOG).

- Bundled `haproxy-spoa-hub-plugin-mirror` bumped from `v0.1.0` to `v0.2.0`. Two new optional knobs under `spoaHub.plugins.mirror.params`:
  - `worker_threads` (omitted by default, auto-derived from `std::thread::available_parallelism()` floored at 2). Lifts the pre-v0.2.0 hardcoded 2-thread tokio runtime; high-fan-out workloads on multi-core hosts now scale with their CPU allotment. The floor of 2 is load-bearing — a single-worker runtime self-deadlocks under load because reqwest's connection driver and per-request dispatch tasks would share one worker. `available_parallelism()` is cgroup-aware on Linux 5.16+ / glibc 2.36+, so a sidecar with `cpu: 100m` sees its CPU limit rather than the host's CPU count. Operators who want predictable resource accounting can pin `worker_threads = N` in the `params:` blob.
  - `pool_max_idle_per_host` (default 32). Bounds the per-target idle-connection pool. reqwest's default is unbounded, which is fine for a single hot target but accumulates unbounded idle keep-alive sockets in a long-running plugin mirroring to many distinct backends. `0` disables idle reuse entirely (useful when reuse would mask staleness in a churning target set).

### Added

- Gateway API `HTTPRouteFilter` of type `RequestMirror` is now supported via the bundled `spoaHub.plugins.mirror` plugin. The gateway library walks each HTTPRoute rule's mirror filters; for the i-th mirror filter on a rule it emits a `(set-var(txn.gw_mirror_target_<i>), set-var(txn.gw_mirror_scheme_<i>), send-spoe-group spoa-hub mirror-<i>-group)` triple, gated by the route's match condition and (optionally) a `var(txn.gw_mirror_sample_<i>) -m int lt <percent>` ACL when the filter specifies `percent` or `fraction` sampling. Sampling draws `rand(100)` once per filter into the indexed sample variable so the three directives in a triple see the same draw (a per-directive re-draw would cause partial firings + (N/100)^3 effective rate at percent N). Per-index group names are load-bearing — HAProxy SPOE only processes each group once per stream, so two filters sharing one `mirror-group` would silently drop the second NOTIFY; the chart therefore enumerates `mirror-1` through `mirror-4` under `spoaHub.plugins.mirror.messages` (bump if a real workload exceeds 4 mirrors per rule). Frontends carrying any mirror filter force `option http-buffer-request` so PUT/POST bodies reach the plugin. The mirror plugin auto-enables whenever `controller.templateLibraries.gateway.enabled=true`; operators get the new filter wired without flipping a second toggle. Closes the chart-side gap for the upstream conformance features `SupportHTTPRouteRequestMirror`, `SupportHTTPRouteRequestMultipleMirrors`, and `SupportHTTPRouteRequestPercentageMirror`.
- The bundled `haptic/spoa-hub` image now layers in a seventh plugin: `haproxy-spoa-hub-plugin-mirror` (HTTP request mirroring, pinned at `v0.1.0`). Lays the groundwork for the chart's gateway library to back the Gateway API `HTTPRouteFilter` of type `RequestMirror` against per-route dynamic mirror `backendRef`s with optional percentage/fraction sampling. Adding the binary does not enable mirroring on its own — hub configs still need an explicit `[[plugins]]` entry referencing `libmirror_plugin.so` before any traffic is mirrored.

### Changed

- The chart-static `haptic-haproxy` LoadBalancer Service is now declared via the controller's new `spec.k8sResources` mechanism (template `haproxy-service` in `libraries/base.yaml`) instead of being emitted by `templates/haproxy-service.yaml` at Helm install time. The controller renders the Service from listener state and applies it via Server-Side Apply with an `OwnerReference` to the `HAProxyTemplateConfig` CR, so `helm uninstall` cascade-GCs it. Operationally identical for typical operators (same name, same `spec.type`, same port set, same `loadBalancerIP` / `loadBalancerClass` / `externalTrafficPolicy` / `internalTrafficPolicy` / `healthCheckNodePort` / `publishNotReadyAddresses` from `haproxy.service.*`); the only visible change is a brief delay between `helm install` completing and the Service appearing (a few seconds, until the controller's first reconcile loop). The internal `haptic-haproxy-dataplane` Service stays chart-static — it's controller-to-haproxy plumbing with no listener-derived state. The previously partial-ownership `features-090-gateway-listener-ports-service` snippet is removed because there is no chart-static Service to patch any more — its job (folding non-default Gateway listener ports into the Service) is now done declaratively by the same `k8sResources.haproxy-service` template that also emits the static port set.

### Fixed

- ClusterRole now grants cluster-wide `services` write verbs (`get/list/watch/create/update/patch/delete`) whenever `controller.templateLibraries.gateway.enabled=true`. Required for `SupportGatewayInfrastructurePropagation`: the chart's gateway library now emits the per-Gateway marker Service in the Gateway's own namespace rather than the controller's, so the upstream conformance test's namespace search finds it via the `gateway.networking.k8s.io/gateway-name` label. The narrower namespace-scoped Role grant in `templates/role.yaml` stays in place for same-namespace emissions (per-Gateway LoadBalancer Services for `SupportGatewayStaticAddresses` still land in the controller's namespace, alongside MetalLB).
- Gateway TLS-cert registration now treats an unspecified `tls.mode` as the spec-implied default `Terminate` instead of silently skipping the listener. Previously a Gateway listener with `tls.certificateRefs` but no `tls.mode` (which is the common case — Gateway API spec defaults `mode: Terminate`) had its cert never registered, never written to disk, and never appearing in the crt-list, breaking SNI-based cert selection. The chart now skips only when `mode` is explicitly set to a non-Terminate value (e.g. `Passthrough`, handled by the SSL passthrough path). Conformance impact: lifts the Frontend mTLS test family's status-side assertions and unblocks listener-cert loading for any Gateway that doesn't set `mode` explicitly.
- Two embedded validation-test fixtures (`test-listenerset-hostname-conflict`, `test-gateway-https-misdirected-listener-claim-maps`) had malformed self-signed certs/keys with mangled base64 bodies. With the TLS-mode-default fix above, the chart now actually loads those certs and HAProxy's stricter cert validation surfaces the corruption. Replaced with fresh self-signed certs.

### Added

- SSL passthrough SNI matcher now supports wildcard listener hostnames (`*.example.com`). The `frontends-500-ssl-tcp` snippet emits `req_ssl_sni -m end .example.com` instead of `-m str *.example.com` when the listener hostname starts with `*.`, matching any single-label subdomain per Gateway API hostname semantics. Closes 3 sub-tests in the `TLSRouteHostnameIntersection` conformance test that exercise wildcard intersection.
- New `https-bind-extra-*` extension point in the SSL library's HTTPS frontend (sibling to the existing `http-bind-extra-*` in the HTTP frontend). Resource libraries that need to expose Gateway HTTPS listeners on non-default ports (e.g. `port: 9443`) emit one TLS bind per listener via this hook; the gateway library now ships `https-bind-extra-050-gateway-multi-port-bind` which walks `Gateway.spec.listeners` and admitted `XListenerSet.spec.listeners`, filters to `protocol: HTTPS`, skips chart-static `httpsPort` and `httpPort` to avoid duplicate-bind errors, and emits `bind *:<port>{{ render "util-ssl-bind-options" }}` for each remaining unique port — so non-default HTTPS Gateway listeners get the same crt-list / ALPN handshake as the chart-static bind. Custom libraries follow the same pattern; reuse `util-ssl-bind-options` instead of literal SSL options to stay in lockstep with chart-static. Also extends the existing `http-bind-extra-*` snippet to skip `httpsPort` for symmetry — a Gateway HTTP listener on the chart-static https port no longer crashes HAProxy startup with a duplicate-bind error (the conflicting listener should surface as `Accepted=False/ProtocolConflict` per Gateway API spec).

### Changed

- `haproxy.ports.http` and `haproxy.ports.https` defaults shift from `8080` / `8443` to `80` / `443`. The chart already grants `CAP_NET_BIND_SERVICE` so privileged binds work as non-root. With chart-static binding on the literal Gateway-API well-known port numbers, `dst_port` inside HAProxy equals the Gateway listener port the connection actually entered through — eliminating the structural collision where a Gateway listener on port 8080 was indistinguishable from Gateway port 80 traffic NAT'd into HAProxy's `bind *:8080`. The chosen ports are now threaded through `extraContext.httpPort` / `extraContext.httpsPort` so libraries (base, ssl, gateway) emit binds and well-known-port omit checks against the operator's actual values rather than hardcoded constants. Operators who explicitly set `haproxy.ports.http` / `https` in their values keep their override; only the defaults change.

### Added

- HTTPRoute `RequestRedirect` filter with `spec.scheme` and `spec.port` both unset now preserves the inbound Gateway listener port in the `Location` header, per Gateway API spec ("when both unspecified, the redirect port MUST be the Gateway listener port"). Implemented as a runtime-resolved `txn.gw_redir_port_part` variable: empty when `(scheme, dst_port)` matches the well-known pair `(http, chart-static-http)` / `(https, chart-static-https)`, otherwise `:<dst_port>`. Closes the `/scheme-nil-and-port-nil` failure in the `HTTPRouteRedirectPortAndScheme` conformance test.
- Frontend routing logic now falls back to `:<dst_port>` when no hostname-based `host_match` lookup matched. Gateway/ListenerSet listeners on non-default ports without a hostname write a `:<port> :<port>` entry into `host.map`; the new fallback finds it via the inbound listener port. Resolves per-listener-port routing isolation when each Gateway listener port has a unique HAProxy bind (e.g. ports 8090, 9443, …). The chart's `controller.config.routing.regexMatchOrder=last` variant carries the same fallback. Edge case: Gateway listener port 8080 still collides with the chart's internal HAProxy http port (both arrive on the same `bind *:8080`); a follow-up will shift the chart's internal http/https ports to a non-conflict-prone range.
- Gateway library `features-090-gateway-listener-ports-service` snippet now writes Gateway-listener ports onto the existing `haptic-haproxy` Service via a partial-ownership Server-Side Apply patch (`haproxy-haptic.org/ownership: partial`). Listeners on non-default ports (anything other than the chart's static 80/443/8404) become `gw-<port>-<proto>` Service ports that coexist with the helm-owned static entries via SSA's per-list-map-entry ownership (`Service.spec.ports` is keyed by `(port, protocol)`). Replaces the previous separate `haptic-gw-listener-ports` Service — single LB IP for all addressless Gateways, matches HUG / Envoy Gateway industry pattern. Gateways that set `spec.addresses[]` continue to get their own dedicated `LoadBalancer` Service via the existing static-addresses path, so per-Gateway IP requests are still honored per Gateway API spec (`GatewaySpec.Addresses` Extended support).
- HAProxy NetworkPolicy now opens to all TCP ports when `haproxy.networkPolicy.allowExternal: true` (default). The previous static port allowlist would drop dynamic Gateway-listener traffic; restricting ports added no security in permissive mode (external traffic was already allowed) and prevented Gateway API `SupportHTTPRouteListenerPortMatching` from working. Restrictive mode (`allowExternal: false`) keeps the explicit port + source allowlist unchanged.
- Gateway API GEP-91 frontend client-cert verify mode honors `validation.mode`: bind directives use `verify required` when the listener's frontend validation is `AllowValidOnly` (default) and `verify optional` when `AllowInsecureFallback`. Optional mode lets the TLS handshake complete without a cert OR with an invalid cert (state recorded in `ssl_c_verify` for downstream gating); required rejects both at handshake time.
- `SupportGatewayStaticAddresses` multi-IP allocation: per-Gateway LoadBalancer Services now also emit a `metallb.universe.tf/loadBalancerIPs` annotation listing every `spec.addresses[]` IP comma-separated. MetalLB walks the list in order and picks the first allocatable IP, so a Gateway listing `{unusable, usable}` succeeds by skipping the unusable entry. `spec.loadBalancerIP` keeps the first IP for non-MetalLB cloud LBs that honor the legacy field.
- Gateway API `SupportListenerSet` (GEP-1713) routing path: HTTPRoute and GRPCRoute parented to a ListenerSet (parentRef.kind=ListenerSet) now actually route to the ListenerSet's listeners. Previously F1/F2 work admitted ListenerSets in status only — routes attaching via kind=ListenerSet produced no host-map entries or routing rules. Closes the conformance gap on `ListenerSetAllowedRoutesNamespaces` and `ListenerSetHTTPRouting`.
- Gateway API GEP-91 listener-level frontend client-cert validation reasons. The chart now distinguishes between `InvalidCACertificateKind` (unsupported group/kind), `RefNotPermitted` (cross-namespace ref without ReferenceGrant), and `InvalidCACertificateRef` (nonexistent / malformed) when emitting the listener's `ResolvedRefs=False` reason. Previously every failure mode collapsed into `InvalidCACertificateRef`, breaking the `GatewayInvalidFrontendClientCertificateValidation` conformance test.
- Gateway API GEP-91 `InsecureFrontendValidationMode` Gateway condition: Gateways that opt into `AllowInsecureFallback` for client-cert validation (gateway-level default OR any per-port override) now get `InsecureFrontendValidationMode=True/ConfigurationChanged` appended to status.conditions. Removed automatically once the mode is reverted to `AllowValidOnly`.

### Fixed

- Gateway API `SupportBackendTLSPolicy`: when a BackendTLSPolicy targets a Service but every entry in `.spec.validation.caCertificateRefs` fails to resolve (and no `.spec.validation.wellKnownCACertificates: System` fallback), the targeted backend now emits `http-request return status 503` instead of silently downgrading to plaintext. Per Gateway API spec a misconfigured policy must surface as 5xx so operators notice.
- Gateway API TLSRoute status patches now target `gateway.networking.k8s.io/v1` instead of the retired `v1alpha2` API version. Gateway API v1.5+ only serves TLSRoute on v1; the chart's hardcoded v1alpha2 caused every TLSRoute status apply to hit "the server could not find the requested resource" and the TLSRoute conformance suite to time out polling for status conditions.

### Added

- Gateway API `SupportTLSRoute` feature (Standard channel, v1.5+): TLSRoutes parented to a Gateway listener with `protocol: TLS` and `tls.mode: Passthrough` now produce TCP-mode backends named `gtw_tls_<namespace>_<name>_<ruleIdx>` and corresponding SNI dispatch lines (`use_backend ... if { req_ssl_sni -m str <host> }`) on the existing `ssl-tcp` frontend. Status patches and listener `attachedRoutes` counts were already in place; this commit closes the data-plane gap.

### Fixed

- Named Service-port references in Ingress, HTTPRoute, GRPCRoute, and annotation-driven SSL-passthrough backends (`nginx.ingress.kubernetes.io/ssl-passthrough`, `haproxy-ingress.github.io/ssl-passthrough`, `haproxy.org/ssl-passthrough`) now resolve to the correct numeric pod port instead of silently producing broken backends. Every backend-rendering library (`ingress`, `gateway` ×2, `nginx-ingress`, `haproxy-ingress`, `haproxytech`, `base/util-default-backend`, `annotation-compat/BuildAnnotationSSLPassthrough`) now goes through a single `ResolveServicePort` helper in `base.yaml` that handles both `port.number` and `port.name` shapes (and Gateway API's bare-int `port`), calling `fail()` on unresolvable input so misconfigurations surface in controller logs and `deployFailed` status rather than masquerading as runtime 503s. Previously, an Ingress referencing its backend by `port.name` (instead of `port.number`) produced HAProxy `server` lines pointing at port 80 regardless of the actual pod port, returning 503 with `<NOSRV>/SC--` for every request; the SSL-passthrough variant of the same bug silently produced zero backends (the annotation scan converted the name string to 0 via `toint("https-gui")` and filtered the entry out).
- `haproxy-ingress.github.io/path-type` annotation (values `regex`, `exact`, `prefix`, `begin`) now actually routes to the named backend. Three structural bugs in `charts/haptic/libraries/haproxy-ingress.yaml`'s four path-map renderers had silently broken every value of this annotation since it was written: (1) the map value was emitted as just `<backend_name>` instead of `BACKEND:<backend_name>`, so `base.yaml`'s `field(1,:)` qualifier dispatch never matched and routing silently fell through to `default_backend` (404); (2) the regex renderer used `render "util-backend-name-ingress"` which only defines the `BackendNameIngress` macro without calling it, so regex rows had no backend name AT ALL; (3) none of the four renderers applied `MapKeyForHost`, so wildcard hosts (`*.example.com`) leaked the literal `*` into regex patterns and HAProxy rejected the resulting path-regex.map at parse time. All three are fixed by aligning the four renderers with `ingress.yaml`'s standard form: import + macro call for the backend name, prepend `BACKEND:` qualifier on the value, normalise the host via `MapKeyForHost`. Existing validation tests for these renderers were extended to assert the `BACKEND:<backend_name>` value (previously they only checked the key was present, which is why none of them caught the breakage); two new tests added for the regex variant + a wildcard-host regex variant. The skipped `TestIngressAuthURLRegexPath` e2e test from MR !911 is un-skipped now that the underlying routing works.

### Changed

Headers in the hardcoded six are skipped (no duplicate SPOE arg); cross-ingress duplicates collapse to one capture; RFC 7230 token validation via the existing `util-auth-validate-header-name` macro applies.
- Both ingress libraries wire the client-mTLS annotation family for incoming client-cert verification: `nginx.ingress.kubernetes.io/auth-tls-secret` + `auth-tls-verify-client` + `auth-tls-error-page` + `auth-tls-pass-certificate-to-upstream`, and the haproxy-ingress equivalents `haproxy-ingress.github.io/auth-tls-secret` + `auth-tls-verify-client` + `auth-tls-error-page` + `auth-tls-cert-header`. The chart looks up the referenced `kubernetes.io/tls` Secret, writes its `ca.crt` field to `ssl/<ns>-<secret>-client-ca.pem` via the file registry, and registers per-host config in a new shared-state map `globalFeatures.clientCertVerifyHosts`. The ssl.yaml `features-150-ssl-crtlist` snippet now groups each TLS cert's SNIs by their (ca-file, verify-mode) tuple and emits one crt-list line per group with `[ca-file <path> verify <mode>]` — the same cert can appear multiple times in the crt-list with different per-line options, which HAProxy supports. The error-page and cert-passthrough annotations attach `http-request redirect` and `http-request set-header` directives gated on `ssl_c_verify` / `ssl_fc_has_crt`. Verify modes `on`/`optional`/`optional_no_ca`/`off` map to HAProxy's `verify required`/`optional`/`optional` (no distinct mode for "verify but accept invalid")/no-op respectively. `nginx.ingress.kubernetes.io/auth-tls-verify-depth` and `haproxy-ingress.github.io/auth-tls-strict` are intentionally not wired separately — HAProxy's crt-list has no per-line verify-depth, and `auth-tls-strict` overlaps with `auth-tls-verify-client: optional`.
- nginx-ingress template library for `nginx.ingress.kubernetes.io/*` annotation compatibility (disabled by default)

### Fixed

- `templates/validatingwebhookconfiguration.yaml` now sources `watchedResources` from the merged template libraries (`haptic.mergeLibraries`) instead of iterating raw `.Values.controller.config.watched_resources`. The old form silently produced no `ValidatingWebhookConfiguration` for chart users whose watched resources were declared via libraries (e.g. `libraries/ingress.yaml: enableValidationWebhook: true`) rather than via raw helm-values overrides — meaning the admission webhook was effectively disabled, and malformed Ingresses (e.g. conflicting `cookie-persistence` + `cookie-persistence-no-dynamic` annotations) reached the controller where they failed render and stalled the reconcile pipeline for *all* other Ingresses. This is the same merging path `haproxytemplateconfig.yaml` uses, ensuring the webhook scope matches what the controller actually validates.
- `features-160-ssl-redirect-map` no longer uses the cross-render `first_seen` cache to dedupe hosts; it now uses a per-snippet `seen` map keyed by `(code, host)`. The previous form produced an inconsistent render under high resource churn — the snippet would skip registering `ssl-redirect-<code>.map` while the paired `frontend-filters-050-ssl-redirect` snippet still emitted the rule referencing it. Result: HAProxy reload failed with `failed to open pattern file <maps/ssl-redirect-<code>.map>` once the orchestrator post-config phase deleted the (correctly-) unreferenced map file. The fix keeps the two snippets in lockstep regardless of how often `redirectHosts` is observed.
- `haproxy.org/pod-maxconn` now only counts Running and Ready HAProxy pods (previously counted all pods including Pending, SysctlForbidden, CrashLoopBackOff)

## [0.1.0] - 2026-03-09

### Added

- Initial Helm chart deploying the controller and HAProxy pods (2 replicas by default)
- Separate controller Service (ClusterIP for operational endpoints) and HAProxy Service (configurable LoadBalancer/ClusterIP)
- Default NetworkPolicy for HAProxy instances
- Leader election support with configurable replica count
- Default SSL certificate configuration via `controller.defaultSSLCertificate`
- Modular template library system with composable libraries merged at Helm render time (enable/disable via `controller.templateLibraries.<name>.enabled`):
  - `base.yaml`: Core HAProxy template structure with extension points
  - `ingress.yaml`: Kubernetes Ingress support (path types: Exact, Prefix, ImplementationSpecific; TLS termination; default backend)
  - `gateway.yaml`: Gateway API support — HTTPRoute and GRPCRoute are watched and routed; traffic splitting, request/response header modification, URL rewrites, and Gateway/Route status patches are emitted. TLS/TCP/UDP listeners are reflected in each Gateway's `supportedKinds` status but TLSRoute/TCPRoute/UDPRoute resources are not watched or routed
  - `haproxytech.yaml`: `haproxy.org/*` annotation compatibility (backend config snippets, SSL passthrough, CORS, basic auth)
  - `ssl.yaml`: TLS/SSL features
  - `haproxy-ingress.yaml`: 56 `haproxy-ingress.github.io/*` annotation compatibility (enabled by default)
- Gateway API status reporting: Gateway conditions (Accepted, Programmed), listener status, HTTPRoute/GRPCRoute parent status with Accepted and ResolvedRefs conditions
- Ingress status reporting: LoadBalancer addresses propagated to Ingress `.status.loadBalancer`
- HAProxy built-in Prometheus exporter enabled by default on the status frontend (`/metrics` on port 8404)
- Grafana dashboard annotations for leader transitions and controller pod starts
- Auto-generated Dataplane API credentials stored in a Secret (deterministic 32-char SHA256 of release-name + namespace; preserved across upgrades from the existing Secret)
- `haproxy.sysctls` for setting kernel parameters on HAProxy pods via pod-level securityContext
- `haproxy.podAnnotations` for custom pod annotations on HAProxy pods (supports Helm template expressions)
- `haproxy.shareProcessNamespace` to enable process namespace sharing between containers (required for signal-based sidecar reload, e.g., SPIFFE/SPIRE mTLS agents)
- `haproxy.shmStats.enabled` to persist stats counters across HAProxy reloads via shared memory (requires HAProxy 3.3+); automatically provisions `/dev/shm` emptyDir volume with auto-calculated size
- `haproxy.nbthread` to control HAProxy thread count (auto-calculated from CPU requests by default)
- `haproxy.dataplane.validateConfig` to control server-side config validation
- `haproxy.dataplane.debugSocketPath` to enable Unix socket for runtime profiling of the Dataplane API sidecar
- `controller.config.dataplane.maxParallel` to limit concurrent Dataplane API operations
- `controller.statusPatches.enabled` to disable status patch writes during migration from another ingress controller
- `extraDeploy` for deploying arbitrary Kubernetes resources alongside the chart (supports Helm templating)
- `extraEnv`, `haproxy.extraEnv`, `haproxy.dataplane.extraEnv` for custom environment variables on all containers
- `global-settings-*`, `defaults-settings-*`, and `frontend-extra-*` extension points for customizing HAProxy global/defaults sections and early frontend directives via template snippets
- `status-patches-*` and `status-extra-*` extension points for custom status and Prometheus endpoint configuration

### Changed

- Dataplane API credentials consolidated into `credentials.dataplane` section; auto-generated if not provided
- Basic auth userlists are named `auth_<secretNs>_<secretName>` and deduplicated per Secret; each Ingress references its userlist via `http_auth()`. Differs from the official HAProxy Ingress Controller's per-Ingress `{namespace}-{ingressName}` naming so multiple Ingresses sharing the same Secret produce a single userlist (significant speedup for bcrypt hashes)
- Production-ready default resource requests and limits: controller (100m CPU / 512Mi memory), HAProxy (250m CPU / 1Gi memory), dataplane sidecar (50m CPU / 256Mi memory)
- `sidecars`, `extraVolumes`, `extraVolumeMounts` and their `haproxy.*` counterparts support Helm template expressions
