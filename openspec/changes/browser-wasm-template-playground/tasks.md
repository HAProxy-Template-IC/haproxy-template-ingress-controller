## 2. Milestone 1 — Client-native severance (DEFERRED — will not do)

Investigation concluded this is not worth doing (see design.md D5). Findings:

- The bundled chart's **typed** `currentConfig.ServerIndex[...]` access (`charts/haptic/libraries/base.yaml`) forces the wasm to keep `client-native/models` to compile — so full severance (the original ~5.8 MB target) is **impossible**.
- The achievable partial cut is 27 of 30 client-native packages (keep `models`) for a corrected floor of **~6 MB brotli, not 5.8**.
- Achieving it requires a multi-package refactor of the correctness-critical HAProxy deploy path (split `pkg/dataplane` *and* `pkg/dataplane/client`, interface-seam `currentconfigstore`, inline the store builder) for a sub-1 MB win that still leaves the module in the "multiple MB" range.

**Decision: defer.** Size is managed via brotli transport + immutable per-version caching (Milestone 5), not a deploy-code refactor. Realistic module floor: ~6–7 MB brotli (measured 7.3 MB at M0).

- [ ] 2.1 (deferred) Revisit only if module size becomes a hard blocker *and* Milestone 5 transport/caching proves insufficient — then via full leaf-package extraction (no build-tag drift), gated on the full controller test suite.

## 3. Milestone 2 — Warm engine + worker protocol

> **Done and browser-verified.** The wasm API is split into `hapticLoadConfig(config, schemas, haproxyVersion)` (parse → typebootstrap → compile → build `RenderService`, held in a wasm-global `warm`) and `hapticRender(resources)` (bucket resources → stores → `RenderService.Render` against the warm engine). The worker speaks a two-message protocol (`load` = recompile+render, `render` = warm render); the UI sends `load` on config/schema/version/preset changes and `render` for resource-only edits. **Measured win** (ingress chart): `hapticLoadConfig` ≈ 336 ms vs. a warm `hapticRender` ≈ 25 ms median — ~13× faster, ~311 ms of compile+bootstrap skipped per resource edit. Verified in-browser via a compile-count probe (`loadCount`): two resource edits kept `loadCount=1` while the diff-glow still fired; a config edit incremented it to 2; errors still surface and last-good output is kept.

- [x] 3.1 Two-message worker protocol (`load` recompile+render, `render` warm), each carrying a monotonic `seq` — *`init`/`version` folded in: version changes send `load` since capabilities are baked into the service; warming version without recompile is a possible future optimization*
- [x] 3.2 Hold the compiled `RenderService` (+ engine, runner, byKey) as wasm-global `warm` state; recompile only on `load`, render-only on `render`
- [x] 3.3 `seq` staleness (drop results older than the newest) verified; compile-count probe confirms resource edits skip recompilation (`loadCount` unchanged across resource edits, +1 on config edit)
