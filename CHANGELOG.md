# Changelog

All notable changes to HAPTIC — the controller and its Helm chart — are
documented in this file. Controller changes are listed first; chart changes
(values, templates, chart defaults) follow under each release's "Helm chart"
subsection.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- A browser playground for `HAProxyTemplateConfig` runs the controller's production render path entirely client-side in WebAssembly — nothing is uploaded, so real secrets and cluster resources are safe to paste. It shows the exact `haproxy.cfg`, map files, decoded certificates, status patches, and rendered Kubernetes resources a config produces, with per-line provenance back to the template that emitted each line, a reload-vs-runtime impact verdict against a pinned baseline, and an annotation-migration report. It is published per version on the docs site at `/playground/<version>/` (and a moving `/playground/dev/` from `main`).
- The playground runs a config's `spec.validationTests` in the browser via a **tests** tab, reporting each test and assertion as pass or fail with the failure message. Because a browser has no `haproxy` binary, `haproxy_valid` assertions fall back to the pure-Go syntax + schema check and are labelled `syntax + schema`; every other assertion type behaves identically to `haptic-controller validate`.
- The user docs and landing page embed the playground inline: how-to pages carry runnable, editable examples — including challenges with revealable solutions — that render live in the browser via the same engine, each with an "open in the full playground" link. An embed can spotlight any output tab, auxiliary file, or line range. Links can deep-link a specific example with `/playground/?preset=<id>`.
- `haptic-controller migrate-check` audits another ingress controller's Ingresses before you switch to HAPTIC: it classifies every source-controller annotation as supported, different, dropped, failing, or unknown, and renders each Ingress through the real template pipeline to catch rejections. With no arguments it uses the image-embedded chart, live-cluster schemas, and live Ingresses; `-f`/`--resources`/`--schema-dir`/`-n`/`--output text|json|markdown` switch inputs offline. Exit codes: `0` clean, `1` differences or unknowns, `2` blockers. Coverage is declared per source by the template libraries (`spec.migrationCoverage`), so no controller or annotation name is hardcoded.
- Fleet-convergence and config-staleness metrics — `haptic_haproxy_fleet_size`, `haptic_haproxy_fleet_converged`, `haptic_last_full_sync_timestamp_seconds`, and `haptic_deployment_consecutive_failures` — give a noise-free "is the fleet converged, and for how long has it not been" signal to alert on instead of the now-self-healing deploy error counter.
- The docs site serves every page as raw Markdown at the page URL plus `index.md`, with `llms.txt` and `llms-full.txt` indexes, so AI agents and scripts can consume the docs without parsing themed HTML. Every page also carries an edit link and a report-a-problem link that prefills a GitLab issue.
- New `recordEvent(resource, reason, message)` template function emits a Kubernetes `Warning` Event against any resource (resource-agnostic — pass the watched-resource object itself and its `apiVersion`/`kind`/`namespace`/`name` are read off it, so it works for any watched resource or CRD with no typed client). The controller forwards template-recorded events to the API server on the leader, so they surface under `kubectl describe` / `kubectl get events`; identical events collapse and age out via standard Event aggregation. The playground shows recorded events in a new **events** output tab.
- New `renderMode` template global (`"admission"` for a webhook dry-run of a proposed change, `"reconcile"` for the live config and the load gate) lets a validation check fail loud under the admission webhook while only warning during a live reconcile, so one bad already-present resource can't abort the whole config render.
- Admission responses now surface template-recorded Warning events as AdmissionReview warnings (capped at 10 plus a suppressed-count summary), so `kubectl apply` prints consequences like "this route will fail closed with 503" at the moment of the change instead of leaving them only in Kubernetes Events.
- New `admissionSubject` template global identifies the single watched resource under admission review (`{store, namespace, name}`, controller-set from the webhook overlay; empty map otherwise). Route-scoped template checks use it to hard-fail only the violating resource's own admission while violations elsewhere degrade to per-route handling, so a pre-existing bad resource can no longer deny unrelated admissions or `HAProxyTemplateConfig` updates.
- New `currentFiles` template global exposes the controller's previously-rendered general auxiliary files (filename → content), letting a template read its own prior output as an input. Paired with a new `randBytes(n)` function (cryptographically-random bytes), a template can self-rotate on-disk state on a schedule with no external component. Validation tests seed the prior state with a per-test `currentFiles` fixture.

### Changed

- A validation test's per-test `extraContext` now deep-merges into the global `templatingSettings.extraContext` (nested maps merge key by key, per-test leaves win) instead of replacing whole top-level subtrees. Overriding one key of a subtree no longer clobbers its siblings; a test that previously relied on replacement to clear a sibling key must now override that key explicitly. A map carrying `__replace__: true` opts back into wholesale replacement for that subtree (sentinel stripped), for tests that need an exact key set in a map-valued registry.

### Fixed

- The controller now honors the chart's `WEBHOOK_PORT` environment value instead of always binding `9443`, so changing `controller.ports.webhook` moves the process listener together with the pod, Service target, and NetworkPolicy. Invalid metrics/webhook environment ports now fail startup clearly instead of silently falling back.
- `HAProxyTemplateConfig` admission now gives embedded `validationTests` the same suite-size-scaled budget as the load gate, capped by the remaining configurable config-admission deadline. The bundled chart's own test suite is fully checked instead of timing out at a hardcoded five seconds and emitting a warning on every update.
- Normal configuration reloads no longer emit a false `Metrics component failed: context canceled` error when the previous controller iteration shuts down gracefully.
- `HAProxyTemplateConfig` admission no longer turns an internal render timeout into an explicit denial that can block the very config update needed for recovery. It now has a separate configurable deadline, admits timed-out checks with a warning for the authoritative load gate to enforce, and keeps the webhook HTTP write deadline long enough to return the result; watched-resource admission retains its tighter fail-closed budget.
- Routes no longer silently 404 for 15–30 seconds after a deploy reports success under churn (#84). The runtime-bypass fast path used to push the whole pending render (with `skip_version`), which could overwrite a concurrent reload deploy's config on disk before HAProxy's master re-exec read it — activating a pre-route config while the status advanced — or park new backends on disk un-reloaded, which the next deploy's empty diff then "successfully" skipped. The bypass now pushes the last reload-activated config patched with only the runtime-eligible server changes (endpoint updates stay instant and reload-free), a structural deploy verifies the on-disk config after its reload and fails retryably on divergence (counted as `haptic_deploy_runtime_divergence_total`), a headerless on-disk config always forces a reload even for runtime-only deltas, and a superseded render abandons its retry-across-reload storm instead of re-pushing a stale body.
- The docs site's changelog page is now generated from `CHANGELOG.md` at build time, so `/docs/dev/` always shows the current `[Unreleased]` changes; previously the page was only synced at release time and showed an empty `[Unreleased]` section between releases.
- The live config gate's validationTests budget now scales with suite size (25s floor + ~100ms per test) instead of a fixed 25s cap, and the validation coordinator's deadline is derived from the same formula — an all-passing large suite (e.g. the chart's 362 tests under CI contention) is no longer rejected as "partially-validated" purely because the clock ran out; fail-closed on genuinely incomplete runs is unchanged (#77).
- The admission webhook now validates the EFFECTIVE HAProxyTemplateConfig — resolving watched-resource versions against live discovery and stripping `requires`/`requiresFields`-unsatisfied snippets and tests, exactly like the controller's load gate. Previously it compiled the raw proposed spec, so on clusters without an optional watched resource's CRDs (e.g. no Gateway API) every config update was denied with a template compile error while the running controller accepted the same config (#79). If resolution itself fails transiently, the webhook admits with a warning and defers to the load gate.
- A failed or timed-out deployment now invalidates the deploy scheduler's lane baseline, so a queued runtime-only render re-dispatches as a full structural sync instead of silently restamping the config version header over structural content the HAProxy workers never loaded — previously this could defeat the fast retry with a 0-op "success" and leave new listeners parked unreloaded until the next unrelated change (#76).
- A runtime server update against a backend the loaded config doesn't yet have (`No such backend`/`No such server`) is no longer misclassified as a transient reload and retried futilely for up to 2 seconds per apply; it now fails fast to the scheduled structural deploy that actually creates the backend, so convergence isn't delayed by the retry storm.
- A retryable deploy failure now self-reschedules with bounded exponential backoff (capped, then handed off to the 60s drift backstop) instead of waiting up to a full minute for the periodic drift check, and a fully-failed deploy now reports `Programmed=False` with a reason instead of freezing the last-known status (#72).

### Helm chart

#### Added

- New `defaultSSLCertificate.ecdsaSecretName` optional companion makes the **default** certificate dual: point `secretName` at the primary (RSA) Secret and `ecdsaSecretName` at an ECDSA one for the same names, and HAProxy serves ECDSA to modern clients and RSA to the rest on the no-SNI / unmatched-SNI path (both emitted as `*` default crt-list lines — the empty-SNI form breaks the RSA fallback). Aimed at wildcard-default setups where one cert fronts many teams' hosts. Per-host dual certs (Ingress `spec.tls`, Gateway listener `certificateRefs`) already worked; the docs now cover all three cases.
- Reusable WAF policies gain a structured, self-service-safe `ruleExclusions` field for tuning CRS false positives without an administrator. Each entry supplies numeric CRS rule IDs (`rules`) and/or CRS rule tags (`tags`), an optional exact target variable (`excludeTarget`), and an optional literal path scope (`onPathPrefix`/`onPathContains`/`onPathExact`/`onPathSuffix`); the chart lowers them to `SecRuleRemoveById`/`SecRuleUpdateTargetById`/`SecRuleUpdateTargetByTag` (global) or a chart-owned `SecRule` + `ctl:ruleRemove[Target]ById`/`ByTag` (path-scoped), so no tenant-authored regex ever runs on the request path. The CRS setup, anomaly-scoring, and correlation rule ranges are reserved so an exclusion can't disable enforcement itself, and regex collection keys are rejected. Available in self-service catalogs (no SecLang grant needed) — a namespace can now tune its own false positives, e.g. disabling CRS rule 930130 on `.git/` paths so git-over-HTTP stops false-positiving.
- The bundled coraza SPOA plugin was updated to v0.7.0, adding per-matched-rule metrics (`plugin_coraza_rule_hits_total{phase, rule_id, severity, app}`) that count every rule that fired — including on allowed traffic, which is the signal a detect-mode policy needs before flipping to deny. The docs gain a "Tune a WAF policy from detect to deny" workflow covering the new metrics, the Coraza JSON audit-log sink, and turning classified hits into `ruleExclusions` or `allowedMethods` widening.
- Reusable WAF policies gain structured CRS tuning fields: `allowedMethods` (HTTP method allowlist), `paranoiaLevel` (1-4), and `anomalyThreshold.inbound`/`.outbound`. They lower to crs-setup-position `SecAction`s spliced before the CRS rules include in the route's Coraza application — the position where CRS actually reads these variables, which raw policy `secLang` (injected after the include) structurally cannot reach. Because they are validated structured values rather than rule code, self-service catalogs may use them, so a namespace team can widen the method allowlist for its own REST API without any admin grant.
- Reusable WAF policies gain a `crsSettings` field for fine-tuning a CRS rule's *inputs* instead of disabling the rule — the preferred first response to a false positive. `allowedRequestContentTypes` merges media types into the standard CRS content-type allowlist (the chart carries the CRS default, which upstream ships commented out, and emits the full `|type|`-wrapped list as a REPLACE — so rule 920420 stays active for every other type); `maxFileSize`, `maxNumArgs`, and `totalArgLength` set a bounded scalar. Values lower to one crs-setup-position `SecAction`; the chart owns the full target variable, so tenants never write a collection prefix (and can't reach the writable `GLOBAL`/`IP`/`SESSION` state collections) and each token is charset-validated against `setvar` injection. Self-service-safe (no SecLang grant). Canonical use: a git host allowlists `application/x-git-upload-pack-request` so CRS 920420 keeps inspecting every other content type, where disabling the rule would switch content-type inspection off entirely.
- Namespaced self-service WAF policy authoring (`controller.config.templatingSettings.extraContext.waf.policies.selfService`): with `enabled: true`, every namespace may define Coraza policies for its own Ingresses in a well-known `waf-policies` ConfigMap in that namespace (name/key configurable) and select them with `haproxy-haptic.org/waf-policy` — no per-namespace admin registration. Safe by construction: policies are namespace-scoped (invisible to other namespaces; trusted-catalog names are resolved first and collisions are rejected loudly, never silently shadowed), a broken catalog or policy fails only that namespace's selecting routes closed with `503` plus `WafPolicyCatalogInvalid`/`WafPolicyInvalid` Warning Events (the admission webhook rejects changes that would introduce the breakage; the global render is never aborted), `secLang` requires the separate `selfService.allowSecLang` grant, per-namespace and total policy budgets cut deterministically, `defaultPolicy` resolves in the trusted catalog only, and a self-service `detect` policy cannot weaken a `default-on`/`deny` baseline. Discovery uses a dedicated ConfigMap watch scoped by field selector to the well-known name, so only the catalogs are retained in memory. Also changed: an unknown or unavailable `waf-policy` selection on an already-present Ingress now fails that route closed (`503` + `WafPolicyUnavailable` Event) during a live render instead of aborting the whole render; the admission webhook still rejects it at apply time.
- Misconfigured routing/presentation annotations on an already-present Ingress now warn instead of bricking the fleet: a bad redirect code/port, a malformed rewrite, an invalid CORS/canary/mirror/compression/fixed-response value records a `Warning` Event (reason `InvalidAnnotationValue` or `InvalidAnnotation`) on the Ingress and skips just that feature during a live reconcile, while the admission webhook still rejects the change when you apply or edit it. Security features (authentication, client/backend mTLS, WAF, rate limiting, request-body validation, `X-Forwarded-For`) still hard-fail in every mode, so a misconfigured security control is never silently skipped (no fail-open). Applies across the native and vendor annotation libraries. Chart authors reject watched-resource input via the new `WebhookRejectOrWarn` helper.
- Cross-family annotation-collision guard: an Ingress that configures the same feature through annotations from two different families — for example `haproxy-haptic.org/waf-policy` together with `haproxy-ingress.github.io/waf`, or `haproxy-haptic.org/cors-enable` with `nginx.ingress.kubernetes.io/enable-cors` — is now caught with a message naming the feature, the families, and the colliding annotations. The admission webhook rejects a new or edited conflicting Ingress; an Ingress that already carries a conflict records a `Warning` Event (reason `AnnotationFamilyConflict`) and keeps serving rather than failing the render, so one bad Ingress can't block config updates for the whole fleet or crash-loop the controller at startup. The check fires even when the two values agree, because the effective result would otherwise depend on library render order. Different features across families stay allowed (WAF from one family, CORS from another), as do genuinely different parameters of the same category (two different timeout parameters). Only annotation families whose template library is enabled are considered.
- New `haptic-annotations` template library exposes HAPTIC's native `haproxy-haptic.org/*` annotation vocabulary — a best-of-breed superset of the haproxytech, haproxy-ingress, and nginx-ingress libraries, with one clean annotation per capability (adopting the strongest semantics of each: haproxytech pod-aware maxconn and request capture, haproxy-ingress agent checks / OAuth2-proxy / config-section injection, nginx-ingress canary, request mirroring, and bandwidth throttling). Enabled by default (`controller.templateLibraries.hapticAnnotations.enabled`); the recommended vocabulary for new configs. The vendor libraries remain for migrating existing annotations.
- API-gateway annotations on the native `haproxy-haptic.org/*` library (pure HAProxy config, no plugin): API-key authentication (`api-key-secret`/`api-key-header`/`api-key-query`/`api-key-consumer-header`) backed by a reload-free key→consumer map that establishes a shared consumer identity; stateless request gating (`allowed-methods` → 405, `require-content-type` → 415, `require-headers` → 400, `mock-response`, `fixed-response`); and request correlation IDs (`request-id`/`request-id-header`/`request-id-accept-inbound`).
- JWT, HMAC, and consumer-group annotations on the native library: asymmetric JWT verification (`jwt-secret`/`jwt-algorithm`/`jwt-issuer`/`jwt-audience`/`jwt-required-claims`/`jwt-forward-claims`) with an alg-confusion guard, `exp`/`iss`/`aud`/required-claim checks, and a `sub`-derived consumer identity (fails closed with 503 when the key Secret is absent); HMAC request-signature verification (`hmac-secret`/`hmac-algorithm`/`hmac-header`/`hmac-signed-string`); and consumer-group authorization (`consumer-groups-secret`/`allowed-consumer-groups`) that denies 403 unless the authenticated consumer is in an allowed group.
- Response compression annotations on the native library (`compress-enable`/`compress-algorithm`/`compress-types`): per-Ingress HAProxy-side compression with `gzip`/`deflate`/`raw-deflate`; `brotli`/`zstd` fail the render (unavailable in the community HAProxy build).
- Shared response cache: an opt-in, chart-deployed Varnish tier (`cache.varnish.enabled`) that HAProxy shards by URL with bounded-load consistent hashing, so the cache is shared across the whole HAProxy fleet (loopback origin — on a miss Varnish fetches back through HAProxy, which routes to the app). Deployed as a StatefulSet (or Deployment) + headless Service + static VCL via the controller's `k8sResources` (Server-Side Apply, GC'd on uninstall), with a PodDisruptionBudget, soft node spreading, and a release-scoped NetworkPolicy by default. The policy admits only same-release HAProxy cache requests and permits Varnish egress only to DNS plus the same HAProxy HTTP origin. Per-route control via native annotations: `cache-enable`, `cache-ttl`, `cache-key` (vary by consumer/header/cookie/query/src — making it safe to cache authenticated content per consumer), `cache-exclude-content-types`, `cache-exclude-paths`, and `cache-max-object-size`. Cached responses carry an `X-Cache: HIT`/`MISS` header. Source-verified Varnish miss loopbacks bypass shared rate limiting because the external request was already counted. The tier can autoscale via an optional HorizontalPodAutoscaler (`cache.varnish.autoscaling`) — bounded-load consistent hashing keeps per-shard load even, so average CPU is a sound signal; a generous scale-down window guards cache warmth. The controller Role grants `statefulsets`/`configmaps`/`poddisruptionbudgets` (and `horizontalpodautoscalers` when autoscaling is on) only when the tier is enabled.
- Shared request-rate limiting: opt-in native `haproxy-haptic.org/rate-limit-requests` annotations enforce one budget across the HAProxy fleet through the bundled rate-limit SPOA plugin. The chart-managed default is HA Valkey with Sentinel (three pods, one writable primary, failover, PodDisruptionBudget, NetworkPolicy) and operators can still bring their own Redis/Valkey/Sentinel/Cluster store via `rateLimit.shared.externalStore.urls`; annotated routes fail closed on missing plugin verdicts, exact store checks use configurable short default timeouts, and the default lease mode bounds local key state and store work for DoS-facing use.
- JSON request-body validation: opt-in native `haproxy-haptic.org/request-schema-*` annotations validate POST/PUT/PATCH bodies against JSON Schemas from ConfigMaps or Secrets through the bundled api-gateway SPOA plugin. HAProxy rejects oversized bodies before the SPOE roundtrip; the plugin compiles schemas at reload and validates bounded JSON in memory on the request path. `controller.config.templatingSettings.extraContext.requestBodyInspection.haproxyBuffer` configures the HAProxy buffer capacity shared by request-body inspectors.
- Reusable Coraza WAF policies for native Ingress annotations: HAPTIC administrators can define bounded policies in chart values or exact, RBAC-protected cross-namespace ConfigMaps, while Ingress authors select one with `haproxy-haptic.org/waf-policy` and optionally override enforcement with `haproxy-haptic.org/waf-mode`. Policies support request-body modes, enforcement, structured CRS tuning (method allowlist, paranoia level, anomaly thresholds, rule exclusions), and advanced SecLang. Optional immutable defaults cannot be removed or replaced by an Ingress; mode, vendor compatibility rule snippets, and raw HAProxy escape hatches are centrally authorized and default-deny where they could weaken enforcement. Shared policies compile once across routes, while nginx-compatible per-Ingress rule applications have configurable count and byte bounds.
- Each vendor annotation library (nginx-ingress, haproxy-ingress, haproxytech) now declares machine-readable migration coverage for its source controller's annotations — surfaced on `spec.migrationCoverage` and used to generate the per-source annotation-support tables in the [migration guide](./docs/site/docs/migrating.md). Only enabled libraries contribute.
- `HAProxyFleetDiverged` PrometheusRule alert (toggleable) and a Grafana fleet-convergence panel, built on the new fleet-convergence metrics.
- New `haproxy.org/cors-respond-to-options` annotation: when `"true"`, HAProxy answers the CORS preflight (OPTIONS) with a 204 instead of forwarding it to the backend, matching the upstream HAProxy Kubernetes Ingress Controller.
- New `extraContext.tls.hsts.enabled` opt-in (default off, declared by the SSL library) sends `Strict-Transport-Security` on every TLS response, matching ingress-nginx's and haproxy-ingress's global HSTS default; `tls.hsts.maxAge`/`tls.hsts.includeSubdomains`/`tls.hsts.preload` tune the value, and a per-Ingress `hsts` annotation still overrides it per host. Because HSTS is only effective over HTTPS, the rendered config emits a warning when it is enabled without an HTTP→HTTPS redirect. The nginx-ingress and haproxy-ingress migration coverage now points to this knob.
- New `extraContext.ingressDefaultSSLRedirect` opt-in (default off): redirects every HTTPS-served Ingress host from HTTP to HTTPS with a single global toggle, complementing the per-host `ssl-redirect` annotations. Only hosts actually served over HTTPS are redirected (the default-HTTPS bind is on, or the host has `spec.tls`), so it never points a client at a closed port. `ingressDefaultSSLRedirectCode` (default `308`) sets the status code.
- New `extraContext.tls` cipher/protocol policy (declared by the SSL library) sets a global forward-secret default on every HTTPS bind — `tls.ciphers` (a cert-agnostic superset spanning the ECDSA, RSA, and DHE families), `tls.ciphersuites` (TLS 1.3), and `tls.minVersion` (TLS 1.2 floor), rendered as `ssl-default-bind-ciphers`/`-ciphersuites` and `ssl-min-ver`. The same list serves RSA-only, ECDSA-only, or dual RSA+ECDSA deployments — HAProxy offers only the suites it has a certificate for — and a host serves dual certificates by referencing two TLS Secrets for it (HAProxy picks ECDSA-first with RSA fallback per client). Each sub-key is overridable (empty string omits its directive) to widen coverage for legacy static-RSA clients.
- New `extraContext.tls.sessionTickets.enabled` toggle (default off, a sibling of the cipher policy and `tls.hsts`) turns on fleet-wide TLS session resumption: every HAProxy pod shares one session-ticket encryption key (STEK), so a ticket issued by any pod resumes on any other — covering both TLS 1.2 (RFC 5077) and TLS 1.3 (RFC 8446 PSK). The SSL library emits the shared key file and the bind `tls-ticket-keys` option, and self-rotates the key daily through a 3-key sliding window with one hitless reload. Keys are full-entropy random values generated in-cluster (a new `randBytes` template function), read back each render via the `currentFiles` global to decide when a day has elapsed — no external rotation component and no static secret.

#### Changed

- The shared Varnish cache now uses the canonical HAProxy+Varnish "sandwich" topology: Varnish fetches cache misses from a dedicated internal HAProxy backend-fetch frontend (`cache.varnish.loopbackPort`, default `8090`, fronted by the `haptic-cache-origin` ClusterIP Service) instead of looping back through the client-facing frontend. The WAF, rate limiter, external auth, and routing now run exactly once per request — on the client leg — and never re-run on a cache miss (previously the Coraza WAF re-evaluated every miss, roughly doubling its CPU and latency on cache+WAF routes). The backend-fetch frontend routes each loopback to the same backend the client leg selected via the internal `X-Haptic-Backend` header (set and stripped-of-client-copies in the `varnish_cache` backend), so rewritten and weighted routes stay correct. This replaces the source-IP loop-break map, which churned with Varnish pod IPs, raced pod restarts, and broke under kube-proxy SNAT (`--masquerade-all`). The dedicated port is internal-only (never on the LoadBalancer) and restricted to Varnish by the HAProxy NetworkPolicy. New values: `cache.varnish.loopbackPort` and `cache.varnish.originServiceName`.
- **BREAKING**: Controller workload values moved under `controller.*` (`image`, `replicaCount`, `deploymentAnnotations`, probes, `resources`, `serviceAccount`, `rbac`, `service`, `securityContext`, `extraEnv`/volumes/sidecars/rollout keys, `autoscaling`, `podDisruptionBudget`, `monitoring`, `networkPolicy`, `webhook`); a value left at its old root-level path fails the render with a message pointing at the new path. Flat `extraContext` keys are restructured into `diagnostics`/`statusPatches`/`annotationCompatibility`/`tls` trees — the routing diagnostic response headers (formerly `debug`, on by default) are now opt-in via `diagnostics.routingHeaders.enabled`, and `controller.statusPatches.enabled` moved to `extraContext.statusPatches.enabled`.
- **BREAKING**: chart values now have one owner per runtime setting. Rename `controller.crdName` to `controller.configName`; `controller.debugPort` to `controller.ports.healthz`; `controller.config.dataplane.port` to `haproxy.ports.dataplane`; `controller.config.routing.regexMatchOrder` to `controller.config.templatingSettings.extraContext.routing.regexMatchOrder`; `controller.defaultSSLCertificate` to top-level `defaultSSLCertificate`; and `spoaHub.mirrorStaticMinSlots` to `spoaHub.haproxy.mirror.minMessageSlots`. Remove the no-op `controller.config.controller.healthzPort` and `metricsPort` values. `controller.ports.metrics` now configures the process listener as well as its pod and Service port. Legacy paths fail with an explicit migration error instead of being ignored or drifting.
- **BREAKING**: `haproxy.enterprise.version` was removed. `haproxyVersion` now selects the controller compatibility series, Enterprise image revision, and derived binary path together. An empty `haproxy.image.repository` derives the community or Enterprise registry from `haproxy.enterprise.enabled`; Enterprise mode fails clearly when the selected series has no tested revision pin.
- The unreleased shared-cache and rate-limit values were realigned: Varnish deployment settings live under `cache.varnish`, HAProxy cache balancing under `cache.haproxy`, shared limiting under `rateLimit.shared`, and the bundled Valkey topology under `rateLimit.shared.managedStore`. Varnish and Valkey image pull policies are configurable.
- `spoaHub.plugins.<name>.enabled` template strings must now resolve to exactly `true` or `false`; any other resolved string, or a non-boolean value, fails the render instead of being silently coerced to disabled.
- **BREAKING**: The vendor annotation libraries (`haproxytech`, `haproxyIngress`, `nginxIngress`) are now **disabled by default** — the native `haproxy-haptic.org/*` library is the only annotation library on by default. Operators who use `haproxy.org/*`, `haproxy-ingress.github.io/*`, or `nginx.ingress.kubernetes.io/*` annotations must now explicitly enable the matching library (`--set controller.templateLibraries.<haproxytech|haproxyIngress|nginxIngress>.enabled=true`). The native vocabulary is a superset of all three, so configs written from scratch need no vendor library, and prefixes from different families can coexist on the same Ingress as long as each *feature* is configured through a single family (see the cross-family guard below).
- Ingress is now served over HTTPS by default: any Ingress binds the chart's https port (`haproxy.ports.https`, default `443`) and terminates TLS with the default certificate — no `spec.tls` required (previously the https port stayed closed until a resource requested TLS). A `spec.tls` entry still layers a host-specific certificate on top. Set `extraContext.ingressDefaultHTTPS: false` to keep Ingress plaintext-only, or disable the default certificate (`defaultSSLCertificate.enabled=false`) for HTTP-only mode.

#### Fixed

- The `haproxy-haptic.org/cache-ttl` and `cache-max-object-size` annotations now reject a unit suffix at admission instead of silently disabling caching. A value like `cache-ttl: "60s"` previously passed validation (the integer check used `toint`, which parses `"60s"` to `0`) and was written verbatim into the cache-TTL map, where the Varnish VCL computed `std.duration("60s"+"s")` = a zero TTL — so the route never cached and nothing said why. Both annotations now require a bare integer (`"60"`, `"1048576"`) and fail loudly on a suffix.
- A reusable WAF policy carrying structured CRS tuning fields (`allowedMethods`, `paranoiaLevel`, `anomalyThreshold`) no longer fails the whole config render — and the daemon load gate — when it is defined in the catalog but selected by no route, or when coraza runs a CRS-less ruleset. The requirement that the coraza directives contain an `Include @owasp_crs` anchor (needed to splice the tuning SecActions before the rules) is now checked per-route at policy-application time and fails only that route closed, instead of at policy registration where an unused deployment-wide policy aborted every render.
- The structured CRS tuning fields (`allowedMethods`, `paranoiaLevel`, `anomalyThreshold`) were rejected at `helm template` time with "unknown field": the chart's Helm-level pre-validation of inline policies was never extended alongside the render-time validator, so values using the new fields could not deploy at all. The allowlists are synced, the Helm layer validates the new fields' shapes, and the template test script now renders the full inline-policy field surface so the two validation layers can't drift apart silently again.
- The bundled rate-limit SPOA plugin was updated to v0.2.0, making `burst` real in the default token-bucket (lease) mode: an empty local lease pool now escalates to one bounded, per-key-coalesced reservation against the authoritative store bucket before denying, so a browser page load fanning out tens of parallel requests is admitted within the configured burst instead of mass-429'd from a `rate x 200ms` local pool. Lease sizes adapt to observed demand (recurring bursts are pre-stocked locally), a flood costs the store at most one round-trip per sync interval, `fail_open` is now honored when the store is unreachable and the pool is empty (previously a drained pool with an open circuit breaker denied indefinitely), and the `x-ratelimit-remaining`/`reset` headers report the real budget instead of the local lease pool.
- WAF governance violations on existing Ingresses no longer wedge the cluster: previously, once any Ingress carried annotations a governance gate forbids (a `waf-mode` override without `allowEnforcementOverride`, or an `nginx.ingress.kubernetes.io/modsecurity-snippet` under `allowCustomRules=false` — the state every ingress-nginx migration starts in), every render aborted AND, because the webhook live-renders each admission, every config update and every Ingress fix was denied. Governance and per-route annotation violations now fail closed per-route instead — the violating route returns 503 with a Warning Event naming the missing grant, everything else keeps rendering — and hard-fail only the violating resource's own admission. A route rejected mid-registration also no longer overwrites another library's Coraza application, and a broken route with a dangling `waf-mode` fails closed instead of being served with the annotation ignored.
- Defining any inline WAF policy no longer makes the admission webhook deny every subsequent `HAProxyTemplateConfig` update: the baked unknown-policy validationTest asserted the exact available-policies list, but deployment-defined inline policies deep-merge into its pinned catalog and join that list. The assertion now tolerates deployment-defined policies alongside the pinned one.
- Defining a reusable WAF policy (which activates WAF governance) no longer fails the daemon load gate on the bundled validation tests. The `haptic-annotations` config-injection, custom-WAF-rule, and shared-rate-limit tests now declare their own `extraContext.waf.ingressPermissions`, so activating governance no longer forces an operator to loosen `allowRawHAProxyConfig`/`allowCustomRules`/`allowEnforcementOverride` cluster-wide just to keep the controller from crash-looping.
- Shared source-IP rate limits now run before Coraza and request-schema validation, so rejected floods do not consume expensive API-gateway processing; consumer-keyed quotas now run after native API-key/JWT authentication instead of silently falling back to source IP before the consumer identity existed.
- Admission timeout values are now configurable as `controller.webhook.timeoutSeconds` (watched resources, default `10`) and `controller.webhook.haproxyTemplateConfig.timeoutSeconds` (prospective config, default `30`); the chart validates Kubernetes' limit and derives one-second-shorter controller deadlines automatically.
- **Security:** API-key authentication and consumer-group authorization now fail closed with `503` while their referenced Secrets are absent from the controller watch cache. Previously each map producer skipped a missing Secret while its backend directive still referenced the unregistered map, rejecting an Ingress during Secret propagation races instead of admitting a fail-closed route.
- EndpointSlices that do not expose a Service's requested named target port are no longer rendered as HAProxy servers using the Service port; this prevents unrelated pods matched by a broad Service selector from receiving application traffic.
- The default HAProxy bootstrap configuration now applies the same configurable `extraContext.hardStopAfter` drain bound as the controller-rendered configuration, so the initial worker cannot remain stuck after the first reload.
- The bundled SPOA hub was updated to v0.7.4 so removing Coraza or another native plugin during a config reload no longer crashes the sidecar with SIGSEGV / exit 139 during `dlclose`; retired plugin instances are still drained and destroyed, while native library mappings remain safe for the process lifetime.
- Generated HAProxy configurations no longer emit `haproxy -c` warnings from proxy-mode mismatches or unsupported TLS settings: TCP frontends explicitly use `tcplog`, `forwardfor` is scoped to HTTP traffic frontends, the quiet status endpoint retains a log target with normal logs suppressed, and the AWS-LC-incompatible `tune.ssl.default-dh-param` default was removed.
- **Security:** external-auth response headers (`nginx.ingress.kubernetes.io/auth-response-headers`, `haproxy-ingress.github.io/auth-headers-succeed`, and the oauth2-proxy desugaring) are now stripped from the inbound request on auth-protected routes before the auth plugin's value is set. Previously the `set-header` was skipped when the auth reply omitted a listed header, so a client-supplied copy (e.g. `X-Auth-Groups: admin`) survived to the backend on an otherwise-successful auth — an identity/privilege-escalation vector on backends that trust those headers. Now a `del-header` precedes each `set-header`, matching ingress-nginx's always-overwrite semantics. An Ingress that combines `haproxy-ingress.github.io/auth-url` with `ssl-passthrough` also gets an `AuthIgnored` `Warning` event, since external auth can't run on undecrypted L4 traffic.
- `nginx.ingress.kubernetes.io/proxy-ssl-secret` client certificates now deploy under the correct path — the rendered `crt` value is the bare filename (resolved against HAProxy's `crt-base`) instead of a `ssl/`-prefixed path that doubled to `ssl/ssl/<name>` and made HAProxy reject the config (`unable to stat SSL certificate`), denying the Ingress at admission. Only affected upstream mTLS via this annotation.
- When two Ingresses claim the same host, path, and path type, the route is now resolved deterministically to the older Ingress (by `creationTimestamp`, tiebroken by namespace/name) instead of the previous arbitrary render-order winner — matching ingress-nginx's oldest-wins, so an Ingress that was there first is never hijacked by a later conflicting one. `Prefix` and `ImplementationSpecific` share a routing slot and resolve together; `Exact` is separate. An nginx canary Ingress no longer competes for its main's base route — the main Ingress owns the route and the canary only overlays its traffic split (previously the canary could win the base map by render order, sending non-canary traffic to the canary backend). The Ingress that loses a route now gets a `RouteConflict` `Warning` Event naming the winner, so the dropped route is visible via `kubectl describe ingress`.

- Installing without cert-manager now works out of the box: when cert-manager provisioning is enabled (the default) but its API is absent, the chart generates a self-signed `default-ssl-cert` Secret (10-year validity) instead of silently skipping the `Certificate` — previously the controller failed every render (`TLS Secret not found`) and the HAProxy pods never became ready. A Secret that already exists (external-secrets, manual) is left untouched, the generated one survives upgrades, and manual mode (`certManager.enabled=false`) keeps its provide-your-own contract (#78).
- The `nginx.ingress.kubernetes.io/enable-cors` and `haproxy-ingress.github.io/cors-enable` annotations now answer the CORS preflight (OPTIONS) request in HAProxy with a synthetic 204 carrying the `Access-Control-*` headers, matching ingress-nginx — previously the preflight was forwarded to the backend, which then had to handle OPTIONS itself. Both annotations are now marked `supported` in the migration coverage.
- The `haproxy.org/cors-*` annotations now mirror the upstream HAProxy Kubernetes Ingress Controller: a non-wildcard `cors-allow-origin` is treated as a regex matched against the request Origin and the `Access-Control-Allow-Origin` header echoes the matched origin (previously the value was emitted verbatim, so a regex or multi-origin allow-list produced an invalid header). CORS headers are now added via `http-after-response` (so they also apply to the preflight response), and the `cors-allow-methods` / `cors-allow-headers` / `cors-max-age` defaults now track upstream (`*` / `*` / `5s`).
- The `nginx.ingress.kubernetes.io/cors-allow-origin` and `haproxy-ingress.github.io/cors-allow-origin` annotations now accept a comma-separated allow-list with single-level `*.` subdomain wildcards, match it against the request `Origin`, and echo the matched origin back (adding `Vary: Origin` for non-wildcard lists) — matching ingress-nginx. Previously the annotation value was emitted verbatim as the `Access-Control-Allow-Origin` header, so a multi-origin list or a wildcard produced an invalid header. A malformed origin now fails the render.
- `haproxy-ingress.github.io/auth-secret` now also parses an `auth`-key htpasswd Secret (haproxy-ingress's and ingress-nginx's native format — one `user:hash` line each, `user::plain` for insecure), so a Secret migrated from those controllers authenticates. The previous base64-hash-per-username Secret shape still works.
- `haproxy.org/auth-realm` now normalizes spaces to dashes (matching the upstream HAProxy Kubernetes Ingress Controller) instead of failing the render, and its default realm is now `Protected-Content` (was `RestrictedArea`). The `sanitize_auth_realm` toggle is removed (normalization is unconditional).
- The Gateway API template library no longer requires the Ingress library. Its shared hostname-to-map-key helper (`MapKeyForHost`) moved into the always-loaded base library (renamed `util-ingress-host-key` → `util-host-key`), so `controller.templateLibraries.gateway` can be enabled with `ingress` disabled without a template-compilation error.

### Added

### Changed

- Leader-election timing defaults raised from 15s/10s/2s to 30s/20s/5s (`leaseDuration`/`renewDeadline`/`retryPeriod`): more headroom against apiserver or CPU-starvation stalls, at the cost of slower crash-failover (up to ~35s; voluntary handoffs still release the lease immediately). Tune via `spec.controller.leaderElection` (#57).
- Config validation now runs asynchronously with latest-wins coalescing: rapid successive `HAProxyTemplateConfig` edits validate only the newest change, and an in-flight validation no longer blocks config processing or leaves a new leader without a config (#55).
- `store: on-demand` watched resources keep far less memory resident: the informer cache strips object bodies down to index and identity fields; templates still read the full object, fetched live on access. See [ADR-0012](./docs/adr/0012-on-demand-projection-and-access-gated-reconcile.md).
- All log output now shares one structured logfmt format (client-go and other third-party lines included), and routine per-request/per-reconcile success lines moved from INFO to DEBUG — failures, denials, config changes, and leadership transitions stay at INFO. Set `LOG_LEVEL=DEBUG` for the previous verbosity.
- Runtime-eligible server changes (pod-IP rotation, port, admin state) now reach the live HAProxy workers in milliseconds via a runtime fast path instead of waiting for the next scheduled deploy; structural changes still take the rate-limited reload path. See [ADR-0011](./docs/adr/0011-no-haproxy-server-state-file.md). The reconciler-level debounce was removed — batching is per-watcher via `spec.watchedResources.<name>.debounceInterval` (default raised from 100ms to 2s; `"0"` fires on every change).
- Content-only changes now apply to the live HAProxy workers via the runtime API without a reload: map files, TLS certificates (HAProxy 3.2+), SSL CA files (HAProxy 3.2+, e.g. frequent trust-bundle rotation), and frontend `maxconn`. Adding or removing files and all other structural changes still reload, and a failed runtime apply falls back to a reload, so the result always converges.
- `controller validate` now requires `--schema-dir` (or `HAPTIC_SCHEMA_DIR`) for typed-access templates; the embedded Gateway schema fallback was removed. Production (live apiserver) is unaffected.

### Fixed

- Fixed controller crash-loop and Gateway status-apply failures on clusters running older Gateway API releases (v1.1–v1.5) whose schemas lack fields the bundled chart exercises (#59).
- A replica that loses the leader-election lease now reinitializes and re-enters the election loop instead of running as a permanent follower — on single-replica deployments, a missed lease renewal could previously stall deployments until a pod restart (#57).
- Runtime map updates are now verified by read-back and fall back to a reload when the live map did not converge — a map write acknowledged but lost by HAProxy could previously latch stale routing until an unrelated reload (#48).
- Eliminated intermittent 503s during rolling restarts of single-replica backends: a newly-Ready pod's endpoint change reaches the live workers within `option redispatch`'s rescue window even when it coincides with an in-flight structural deploy, runtime applies retry across a concurrent reload, and deleting an unreferenced certificate no longer schedules a stray second reload that briefly blacked out the runtime socket (#67).
- Reloads are bounded to one per `minDeploymentInterval` under concurrent churn, and auxiliary-file updates batch into the main config sync's single reload instead of triggering separate DataPlane API auto-reloads.
- Resource status no longer goes stale: statuses are written even when a change produces no config diff (a Gateway with no attached routes no longer sticks at `Programmed=Unknown`), and sustained event bursts no longer drop status or deployment events.
- `HAProxyCfg.status.deployedToPods` now reflects reality: a failed deploy keeps the pod's last successfully-deployed checksum plus a `lastError` instead of reading as converged, failed deployments are retried on the next reconcile instead of waiting for the drift timer, and a startup race no longer leaves a deployed pod unreported.
- Cross-pod config drift is now detected and repaired: the deployer tracks each pod's actual post-sync state, and a render race no longer leaves a newer render undeployed.
- Credentials-Secret rotation now takes effect immediately, and content updates to watched Secrets/ConfigMaps are no longer dropped.
- gRPC: requests hitting the default backend get a proper trailers-only `grpc-status: 12` response instead of a connection-breaking 404, GRPCRoute method matching works on TLS + ALPN h2 and plaintext h2c, and gRPC over h2c multiplexes with HTTP/1.1 on the same bind.
- Gateway TLS listeners on non-default ports now bind correctly.
- The renderer fails fast when the config references a map file it didn't register (previously the file was deleted as unreferenced, breaking every subsequent reload), and each render sees one consistent snapshot of the watched-resource stores.
- `store: on-demand` resources no longer trigger a full list or one API fetch per resource on per-key reads, drift cycles, and the `/debug/vars` endpoints.
- Ingress `pathType: Exact` now preserves trailing slashes (`/foo/` no longer matches `/foo`).
- `controller validate` renders with the same context as production (`capabilities`, `extraContext` promotion), so a template can no longer pass validation yet render differently in production.
- HAProxy 3.3 configs are now validated against the v3.3 DataPlane API schema (was v3.2), and DataPlane API versions newer than the newest bundled client clamp down to it instead of falling back to the oldest v3.0 client.
- Watched-resource admission (e.g. Ingress) now gets the same ~9s internal validation deadline as `HAProxyTemplateConfig` admission (was 5s), so large-config dry-runs aren't prematurely admitted without validation.

- Hardened component lifecycle: re-acquired leadership no longer stacks orphaned event subscriptions (previously endless "critical drops" log spam), event-loop panics recover instead of silently killing the loop, and the controller no longer schedules a spurious iteration restart right after startup.

- The gateway library now supports every Gateway API release, resolved at runtime: each Gateway kind is an optional watched resource with an ordered `apiVersions` candidate list (core kinds v1/v1beta1, GRPCRoute v1/v1alpha2, TLSRoute v1/v1alpha3/v1alpha2, TCPRoute v1/v1alpha2, ReferenceGrant v1/v1beta1, BackendTLSPolicy v1/v1alpha3). Installing or upgrading Gateway API CRDs activates support at runtime — no `helm upgrade` needed; features whose fields don't exist in an older release's schemas stay inactive there. The Helm-render-time `.Capabilities` gate is removed.
- The GatewayClass object is now created at runtime by the controller (Server-Side Apply, owned by the `HAProxyTemplateConfig`) instead of by a Helm template, so it exists exactly when the `gatewayclasses` CRD is served. **Upgrade note:** `helm upgrade` removes the previously Helm-owned GatewayClass and the controller recreates it within one reconcile; existing Gateways are unaffected.
- Per-route annotation policies are now applied by shared frontend rules reading per-backend/per-host map files instead of inline per-backend/per-ingress rules: `proxy-body-size`, upstream header overrides (`set-host`, `upstream-vhost`, `x-forwarded-prefix`, `connection-proxy-header`), literal `rewrite-target`, `ssl-redirect`/`force-ssl-redirect`, host redirects (`redirect-to`, `request-redirect`, `permanent-redirect`/`temporal-redirect`), HSTS, `app-root`, `auth-tls-error-page`, `from-to-www-redirect`, `default-backend-redirect`, and `ssl-redirect-port`. Adding or changing these is now a map-only, reload-free update; behavior, status codes, and config-injection guards are unchanged (`app-root`, `auth-tls-error-page`, and `hsts-max-age` gain previously missing injection guards).
- The deployed DataPlane API now addresses storage (maps/certs/general files) by relative paths resolved against the HAProxy base dir — the same identifiers HAProxy uses — so map content changes apply via the runtime API without a reload. The `dataplane.mapsDir`/`sslCertsDir`/`generalStorageDir` values are unchanged.
- The auto-generated DataPlane API password (`credentials.dataplane.password` left empty) is now a random 32-char value instead of a deterministic hash of release name and namespace. Existing installs are unaffected (the password is preserved from the existing Secret on `helm upgrade`). **GitOps note:** under ArgoCD/Flux (no cluster lookup at render time), an empty password regenerates on every sync — set `credentials.dataplane.password` explicitly for those setups.
- The validating admission webhook now provisions its own self-signed TLS certificate by default (`webhook.certManager.enabled` defaults to `false`; validity via `webhook.selfSigned.certValidityDays`, default 10y, reused across upgrades), so admission validation works out of the box without cert-manager. cert-manager stays opt-in and is recommended for production (automatic rotation); the self-signed cert is not auto-rotated. **Upgrade note:** a release that used the previous cert-manager default holds a webhook Secret without Helm ownership metadata; before upgrading, either keep cert-manager (`--set webhook.certManager.enabled=true`) or delete the old Secret (`kubectl delete secret <release>-webhook-cert -n <namespace>`) so the chart can recreate it.
- Default `haproxyVersion` is now `3.4` (was `3.2`); the controller and HAProxy pod images default to the HAProxy 3.4 series. Override `haproxyVersion` to stay on an older series.
- Template libraries (`gateway`, `nginx-ingress`, `haproxy-ingress`, `haproxytech`) are now packaged as conditional subcharts: a release stores only the source of the libraries it enables, so an install with all libraries enabled no longer exceeds the Kubernetes 1 MiB release-Secret limit. No values changes (the same `controller.templateLibraries.<x>.enabled` flags), and the rendered `HAProxyTemplateConfig` is byte-identical.
- The controller's startup probe is now enabled by default (30 × 10s budget): startup runs the config's embedded `validationTests`, so time-to-first-healthy can exceed the liveness budget on slow or contended nodes — previously the liveness probe could kill the controller mid-initialization.
- `haproxy.ports.http`/`https` defaults shift from `8080`/`8443` to `80`/`443` so `dst_port` equals the Gateway listener port; explicit overrides are kept.
- Dataplane `minDeploymentInterval` default raised to `5s` (was `2s`), throttling reload-inducing structural deploys; endpoint changes still apply instantly via the controller's runtime fast path. EndpointSlice watches keep `debounceInterval: "0"` for instant rolling-restart reaction.
- **HAProxy `defaults` `timeout connect` lowered from `5000` to `100` (100 ms).** Backends are pod IPs over the CNI; 100 ms fails fast on a SYN to a just-terminated pod so `option redispatch` retries. Operators on slow networks restore `5000` via `extraContext.timeout_connect`.
- gateway library: the cluster-wide `configmaps` watch now defaults to `store: on-demand` (it is only read by name for BackendTLSPolicy CA bundles), keeping references instead of every ConfigMap body resident.
- `extraDeploy` now accepts both list and dict formats.
- `haproxy.org/pod-maxconn` quantizes the pod count to the next power of 2 to avoid reload cascades on scaling.
- Compound resource names (derived from `haptic.fullname`) now truncate to the 63-char label limit; releases with very long names will see affected resources renamed on upgrade (run `helm diff upgrade` first).
- Removed the "TLS Certificate Expiry" Grafana dashboard panel — the controller no longer emits `haptic_webhook_cert_expiry_timestamp_seconds` (the webhook cert is hot-reloaded; see the controller section above).

#### Security

- Annotation values interpolated into the HAProxy config — CIDR lists (allow/deny lists, rate-limit and `satisfy` whitelists) and single-value annotations (upstream header overrides, `proxy-ssl-*`, `proxy-cookie-domain`/`-path`, the auth realm) — are now validated against strict charsets, closing a config-injection vector where a crafted annotation containing a newline could inject arbitrary HAProxy directives into the rendered config.

#### Fixed

- Fixed controller crash-loop and Gateway status-patch failures on clusters running older Gateway API releases (v1.1–v1.5) or Standard-channel installs without the TCPRoute CRD (#59).
- Named Service-port references (`port.name`) in Ingress, HTTPRoute, GRPCRoute, and SSL-passthrough backends now resolve to the correct numeric port (previously silent 503s or empty backends). When the referenced Service isn't in the controller's store yet, the backend renders degraded (placeholder slots, 503 for that route) and converges once the Service appears, instead of failing the whole render and denying the Ingress at admission (#50); a Service that exists but lacks the named port still fails loudly.
- `defaults` now sets `option redispatch` and `base.yaml` filters out not-ready/terminating endpoints, eliminating the single-replica rolling-restart 503 windows.
- Reserved-slot server addresses are now config-driven across reloads (removed the HAProxy server-state-file machinery); placeholders use the unroutable `192.0.2.1:1` sentinel. See [ADR-0011](./docs/adr/0011-no-haproxy-server-state-file.md).
- `haproxy.dataplane.validateConfig: false` now actually skips the dataplane's `haproxy -c` (the flag was misplaced), cutting raw-config push time ~130ms → ~18ms.
- haproxytech: `haproxy.org/check`, `check-interval`, and `scale-server-slots` are now honored instead of silently ignored, and IP access control reads the canonical `haproxy.org/allow-list`/`deny-list` annotations (deprecated `whitelist`/`blacklist` honored as fallback) — the real annotations previously emitted no ACL.
- haproxy-ingress: `maxconn-server`, `maxqueue-server`, `initial-weight`, `backend-check-interval`, and `health-check-port`/`-fall-count`/`-rise-count` now render their `default-server` keywords (previously validated but never emitted), the deprecated `whitelist-source-range` alias is honored, and the `path-type` annotation now actually routes.
- Gateway TLS: an unspecified `tls.mode` defaults to `Terminate` per spec (the listener was previously skipped silently), and a BackendTLSPolicy with no resolvable CA returns 503 instead of downgrading to plaintext.
- The bundled `validationTests` now pass in any release namespace (the shared SSL fixture no longer hardcodes `haproxy-haptic`/`default`).
- The chart fails fast at install with actionable guidance when `webhook.certManager.enabled=true` but the cert-manager CRDs are absent, instead of leaving the controller pod stuck in `ContainerCreating`.
- Basic-auth snippets no longer fail when the referenced auth Secret is briefly absent from the render snapshot.
- PrometheusRule default alerts `HAProxyControllerHighQueueDepth`/`HAProxyControllerNoLeader` now reference metrics the controller actually emits (the old expressions never fired).
- `networkPolicy.ingress.webhook.from` and `networkPolicy.egress.kubernetesApi` defaults switched to `ipBlock` `0.0.0.0/0` + `::/0`, so a host-network apiserver can reach the webhook on clusters enforcing NetworkPolicy (previously silent admission failures).
- The validating-webhook configuration now sources `watchedResources` from the merged libraries, so library-declared resources are actually validated.

## [0.1.0] - 2026-03-09

### Added

- **Template-driven HAProxy configuration**: Generate HAProxy configs using Scriggo templates (Go-based, Jinja2-like syntax) with full access to Kubernetes resources, built-in utility functions, and modular template snippets
- **Embedded validation tests**: Declarative test fixtures and assertions for testing HAProxy configurations within template libraries; run via `haptic-controller validate --test <name>`
- **Dry-run validation webhook**: Admission webhook that intercepts CREATE/UPDATE on opted-in watched resources (Ingress, HTTPRoute, GRPCRoute by default), renders templates with the proposed object overlaid on the live store, and rejects the write if rendering or HAProxy validation fails
- **Multi-architecture container images**: `linux/amd64`, `linux/arm64`, `linux/arm/v7`
- **HAProxy version support**: 3.0, 3.1, 3.2, 3.3 — version-specific images tagged accordingly
- **Supply chain security**: Container images, binaries, and Helm charts signed with Cosign (keyless OIDC); SBOM attestations in SPDX format
- **Prometheus metrics**: Reconciliation timing, template rendering duration, validation results, and Kubernetes API latencies
- **Leader election for high availability**: Multiple controller replicas with automatic leader election; hot-standby replicas continue watching and validating; configurable failover timing
- **Stall detection**: Components detect when blocked and report unhealthy via `/healthz`, enabling automatic pod restart via Kubernetes liveness probes
- **Configurable deployment timeout**: `deploymentTimeout` in dataplane config (default: 30s) to recover from stuck deployments
- **Server slot preservation**: Preserve HAProxy server slots during rolling deployments to enable zero-reload runtime API updates via `currentConfig` template context
- **HAProxy Ingress annotation compatibility**: 56 `haproxy-ingress.github.io/*` annotations via the haproxy-ingress template library
- **Dataplane API concurrency limiting**: `maxParallel` config option to limit concurrent API operations, preventing timeouts for large configurations
- **CRD content compression**: HAProxyCfg content compressed with zstd when exceeding `configPublishing.compressionThreshold` (default 1 MiB), reducing etcd storage
- **HAProxyGeneralFile CRD**: Publish general files (error pages, etc.) as Kubernetes custom resources with compression support
- **HAProxyCRTListFile CRD**: Publish crt-list files as Kubernetes custom resources with compression support
- **`semver_gte` template filter**: Version comparison for gating features on HAProxy version (e.g., `semver_gte(haproxyVersion, "3.3")`)
- **Template-driven status patches**: Templates can register status patches for any Kubernetes resource via `statusPatch()` function, with outcome-keyed variants (`rendered`, `deployed`, `renderFailed`, `deployFailed`) applied automatically based on pipeline phase
- **Backend diff field diagnostics**: Reconciliation log now includes which BackendBase fields caused backend updates, aiding diagnosis of false diffs from parser round-trip asymmetries
- **Status patch helper functions**: `condition()`, `transitionTime()`, and `toJSON()` template functions for building Kubernetes status conditions with stable transition timestamps

### Changed

- **Reconciliation triggering**: Leading-edge triggering with a 5s refractory period; no latency for isolated changes, bursts during that window are batched into a single reconciliation
- **Parallel Dataplane API operations**: Operations execute in parallel within each priority group, reducing sync time for large configurations
- **Balance directive**: `balance roundrobin` moved to `defaults` section to prevent silent behavior change when upgrading to HAProxy 3.3 (which changed the default balance algorithm from `roundrobin` to `random`)
- **Go runtime 1.26.1**: Green Tea GC replaces manual GOGC tuning
