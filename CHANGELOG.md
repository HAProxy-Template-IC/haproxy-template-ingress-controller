# Changelog

All notable changes to HAPTIC — the controller and its Helm chart — are
documented in this file. Controller changes are listed first; chart changes
(values, templates, chart defaults) follow under each release's "Helm chart"
subsection.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Traces now carry a span per request phase, modelled on the official HAProxy OpenTelemetry filter: a `SERVER` span for the request and a `Server session` `CLIENT` span for the upstream call, which the backend's own span nests inside. Phase timings (`handshake`, `request`, `queue`, `connect`, `response`, `retries`) ride along as attributes rather than child spans, because a log-derived pipeline has no intra-request event times and nesting derived offsets would present them as measurements. Empty span attributes are dropped, following `vector.omitEmptyLogFields`.
- New `HAProxyValidationTests` resource carries a configuration's `validationTests` in a companion object. `HAProxyTemplateConfig.spec.validationTestsSelector` selects which ones join the config's inline tests, and the controller runs the union — at startup, on every live config change, and at admission, so a configuration is admitted against the same suite it will be loaded with. Inline `spec.validationTests` remains fully supported and nothing is required to move; the split exists because tests dominate the object's size while being needed only when the configuration is validated, never when it is rendered. A test name may appear in only one source (a collision is an error naming both objects, rather than one definition silently replacing the other), while the reserved `_global` baseline is unioned across sources as several template libraries each contribute part of it. New `spec.requireValidationTests` refuses to load a configuration that ends up with no tests at all — an empty suite otherwise passes unconditionally, so a selector typo or a missing RBAC rule would look identical to a configuration that genuinely has none.
- `--crd-name` / `CRD_NAME` now accept an ordered list (repeatable flag, or comma-separated env var). The controller fetches every named `HAProxyTemplateConfig`, merges them later-wins, and runs the whole existing pipeline — structural validation, effective-config resolution, the fail-closed load gate — against the merged result. Startup waits for **all** of them, since a partial set is as unusable as none. Each object gets its own watcher and a change to any one re-merges against the others, so a library change still loses to your override. A single name behaves exactly as before. The merge uses the same primitive Helm's `mustMergeOverwrite` does, so a chart-rendered set assembles to what a chart-side merge would have produced; `migrationCoverage` accumulates across the set instead of being overwritten, and a `templateSnippets` name defined by more than one object is logged (`Template snippet overridden by a later config`) instead of resolving silently.
- New `haptic-controller config view --input` prints the merged **input** configuration — every object named in `CRD_NAME`, merged the way the controller does — as opposed to the rendered HAProxy output `config view` shows. Since a Helm install now spreads the configuration across one object per template library, no single object shows the whole picture.
- `haptic-controller validate -f` is repeatable and accepts multi-document files, merging every `HAProxyTemplateConfig` it finds in order. `helm template … | yq 'select(.kind == "HAProxyTemplateConfig")' > all.yaml && haptic-controller validate -f all.yaml` therefore validates exactly what the controller would assemble. New `--dump-merged` prints the merged spec and exits without running tests. A single file holding a single document still accepts a bare spec.
- `HAProxyTemplateConfig.status` now reports `observedGeneration` and a standard `Validated` condition (each carrying its own `observedGeneration`), so `kubectl get`/`describe haproxytemplateconfig`, GitOps tools, and CI can tell exactly which spec generation the controller has accepted — and whether it's behind — without reading controller logs. A new `Observed` printer column surfaces it in `kubectl get`. This is the Kubernetes-native way to track controller-vs-spec skew, so no controller-version field is stamped onto the config.
- When the fatal startup load gate rejects a config (the embedded `validationTests` run on a fresh or upgraded controller pod), the controller now records the rejection on the `HAProxyTemplateConfig` status — `Validated=False` with reason `LoadGateFailed`, the failing tests, and `observedGeneration` — *before* it crash-loops, so operators see *why* via `kubectl get`/`describe` instead of only in a `CrashLoopBackOff` pod's logs. The gate stays fail-closed by design (the pod still crash-loops, so a rolling upgrade stalls on the old, good pods and never serves a config that fails its own tests).
- A browser playground for `HAProxyTemplateConfig` runs the controller's production render path entirely client-side in WebAssembly — nothing is uploaded, so real secrets and cluster resources are safe to paste. It shows the exact `haproxy.cfg`, map files, decoded certificates, status patches, and rendered Kubernetes resources a config produces, with per-line provenance back to the template that emitted each line, a reload-vs-runtime impact verdict against a pinned baseline, and an annotation-migration report. It is published per version on the docs site at `/playground/<version>/` (and a moving `/playground/dev/` from `main`).
- The playground runs a config's `spec.validationTests` in the browser via a **tests** tab, reporting each test and assertion as pass or fail with the failure message. Because a browser has no `haproxy` binary, `haproxy_valid` assertions fall back to the pure-Go syntax + schema check and are labelled `syntax + schema`; every other assertion type behaves identically to `haptic-controller validate`.
- The user docs and landing page embed the playground inline: how-to pages carry runnable, editable examples — including challenges with revealable solutions — that render live in the browser via the same engine, each with an "open in the full playground" link. An embed can spotlight any output tab, auxiliary file, or line range. Links can deep-link a specific example with `/playground/?preset=<id>`.
- `haptic-controller migrate-check` audits another ingress controller's Ingresses before you switch to HAPTIC: it classifies every source-controller annotation as supported, different, dropped, failing, or unknown, and renders each Ingress through the real template pipeline to catch rejections. With no arguments it uses the image-embedded chart, live-cluster schemas, and live Ingresses; `-f`/`--resources`/`--schema-dir`/`-n`/`--output text|json|markdown` switch inputs offline. Exit codes: `0` clean, `1` differences or unknowns, `2` blockers. Coverage is declared per source by the template libraries (`spec.migrationCoverage`), so no controller or annotation name is hardcoded.
- Fleet-convergence and config-staleness metrics — `haptic_haproxy_fleet_size`, `haptic_haproxy_fleet_converged`, `haptic_last_full_sync_timestamp_seconds`, and `haptic_deployment_consecutive_failures` — give a noise-free "is the fleet converged, and for how long has it not been" signal to alert on instead of the now-self-healing deploy error counter.
- The docs site serves every page as raw Markdown at the page URL plus `index.md`, with `llms.txt` and `llms-full.txt` indexes, so AI agents and scripts can consume the docs without parsing themed HTML. Every page also carries an edit link and a report-a-problem link that prefills a GitLab issue.
- New `recordEvent(resource, reason, message)` template function emits a Kubernetes `Warning` Event against any resource (resource-agnostic — pass the watched-resource object itself and its `apiVersion`/`kind`/`namespace`/`name` are read off it, so it works for any watched resource or CRD with no typed client). The controller forwards template-recorded events to the API server on the leader, so they surface under `kubectl describe` / `kubectl get events`; identical events collapse and age out via standard Event aggregation. The playground shows recorded events in a new **events** output tab.
- New `renderMode` template global (`"admission"` for a webhook dry-run of a proposed change, `"reconcile"` for the live config and the load gate) lets a validation check fail loud under the admission webhook while only warning during a live reconcile, so one bad already-present resource can't abort the whole config render.
- Admission responses now surface template-recorded Warning events as AdmissionReview warnings (capped at 10 plus a suppressed-count summary), so `kubectl apply` prints consequences like "this route will fail closed with 503" at the moment of the change instead of leaving them only in Kubernetes Events.
- New `admissionSubject` template global identifies the single watched resource under admission review (`{store, namespace, name}`, controller-set from the webhook overlay; empty map otherwise). Route-scoped template checks use it to hard-fail only the violating resource's own admission while violations elsewhere degrade to per-route handling, so a pre-existing bad resource can no longer deny unrelated admissions or `HAProxyTemplateConfig` updates.
- New `currentFiles` template global exposes the controller's currently-deployed auxiliary files — map files, general files, and crt-lists — keyed by base filename, in every render (main config, map, and file templates) so one self-referential snippet works from any template type. This lets a template read its own prior output as an input; paired with a new `randBytes(n)` function (cryptographically-random bytes), a template can self-rotate on-disk state on a schedule with no external component. The controller reads `currentFiles` back from the published aux-file CRDs (watched, the same way `currentConfig` is read back from `HAProxyCfg` for slot preservation), so self-rotating state (e.g. TLS session-ticket keys) survives a controller restart, config reload, or leader promotion instead of bootstrapping fresh and breaking session resumption. SSL certificates and CA files are excluded — their content includes private keys and is published as Secrets. Validation tests seed the prior state with a per-test `currentFiles` fixture. In the browser playground, `currentFiles` is fed from the reload-impact baseline (the pinned set if you pinned one, otherwise the last render), so successive renders read their own prior output and pinning a set of files fixes future renders against them — self-rotating demos (e.g. ticket keys) behave exactly as in the controller.
- New `haptic-controller apply-crds` subcommand server-side applies the CRDs bundled in the image-embedded chart (or `--chart` / `$HAPTIC_CHART_DIR`). Helm never upgrades CRDs it installed from a chart's `crds/` directory, so this closes the gap for additive CRD schema changes (new fields, printer columns, validation) on `helm upgrade` or GitOps sync. It uses server-side apply — idempotent, never deletes, and immune to the last-applied-configuration size limit — and never touches CRD `.status`, so it can't disturb the API server's stored-version bookkeeping.

### Changed

- The JSON access log's `ts` is now microsecond precision (`accept_date(us)`/`us_utime`) instead of milliseconds. It anchors the derived trace spans, and since every HAProxy timer is already whole milliseconds, a millisecond anchor discarded the only sub-millisecond precision available.
- The `HAProxyTemplateConfig` admission webhook now validates the **merged** configuration — the object being applied substituted into the controller's configured set — rather than the object alone, which with a split configuration is generally incomplete on its own. An object the controller does not merge is still validated on its own, exactly as before. A transient failure to fetch the others admits with a warning; the fail-closed load gate remains authoritative.
- A validation test's per-test `extraContext` now deep-merges into the global `templatingSettings.extraContext` (nested maps merge key by key, per-test leaves win) instead of replacing whole top-level subtrees. Overriding one key of a subtree no longer clobbers its siblings; a test that previously relied on replacement to clear a sibling key must now override that key explicitly. A map carrying `__replace__: true` opts back into wholesale replacement for that subtree (sentinel stripped), for tests that need an exact key set in a map-valued registry.

### Fixed

- Fixed a trace span with a negative duration when HAProxy logs `Ta = -1` for an aborted transaction: the end clamped to the request start while the queue and request-receive timers pushed the upstream span's start past it. Most OTLP consumers reject or mis-render such a span.
- Trace spans now end at the transaction's exact end (`te_us`, epoch microseconds stamped when the log line is written) instead of `request + Ta`. Every HAProxy timer is whole milliseconds, so closing on `Ta` discarded up to 1ms — measured 0.824ms on a live trace, enough for an instrumented backend's span to overrun HAProxy's own.
- Fixed the upstream trace span ending at the response headers rather than the last byte, so an instrumented backend's own span overran it — by ~40ms for a 40ms response body. `%Tr` covers only up to the complete response headers; the payload transfer is `%Td`. The span now ends where the request span ends, which is exact by HAProxy's own identity `Td = Ta - (TR+Tw+Tc+Tr)`, and `connect`/`response`/`transfer` remain available as attributes.
- Fixed every HAPTIC span being anchored to the connection accept rather than the request, so a span started one TLS handshake (plus keep-alive idle) too early and could end before the backend it waited on — visible as a gap in the waterfall where the proxy's span finished before its upstream began.
- Fixed docs advertising OpenTelemetry export as a `spoa-hub` plugin capability. That plugin was removed when tracing moved into HAProxy itself; the hub has no part in tracing.
- The chart's own webhook serving certificate Secret is named `<release>-webhook-tls` instead of `<release>-webhook-cert`. 0.1.0 provisioned the latter through cert-manager, so it carries no Helm ownership metadata and every upgrade from that release failed with `invalid ownership metadata` before applying anything. This removes the manual pre-step that was previously documented for it — no `kubectl delete secret`, no forced `certManager.enabled=true`. Neither an in-chart repair works: Helm validates ownership before running pre-upgrade hooks, and a template `lookup` is empty under `helm template`, `--dry-run` and GitOps server-side renders. 0.1.0's Secret is left behind unreferenced and can be deleted at leisure; `controller.webhook.secretName` still overrides the name.
- Fixed `helm upgrade` from 0.1.0 failing outright with `Secret "…-webhook-cert" … cannot be imported into the current release: invalid ownership metadata`. 0.1.0 provisioned the webhook certificate through cert-manager, so that Secret is not Helm-owned and Helm refuses to adopt it. The chart now detects an existing cert-manager managed webhook certificate and stays in cert-manager mode, preserving the setup (and its rotation) instead of contending for the Secret. Fresh installs are unchanged and still self-sign.
- Fixed a bundled validationTest left behind by the per-test `extraContext` deep-merge change above: it cleared the vector sidecar's subtree with `vector: null`, which only worked while a per-test subtree replaced the global one wholesale. Under deep-merge the sidecar stayed enabled, the test failed, and because the startup load gate is fail-closed the controller crash-looped instead of merely reporting a red test. It now disables the sidecar with an explicit `vector.enabled: false`, and the template gate honours that alongside the existing presence check.

- Two haproxytech validation tests no longer crash-loop the controller when the Varnish cache tier is enabled alongside the haproxytech library. Both asserted the ABSENCE of a string across the whole rendered config (`default-server check`, and a `server SRV_6` slot line) to check a property of their own backend, so any other backend that legitimately health-checks or has more server slots falsified them — and the load gate turns a failed validation test into a crash-loop. One is now scoped to its own backend; the other pins the config surface its assertion depends on.
- `TestIngressAuthURLRegexPath` now actually runs. It needs the nginx-ingress and haproxy-ingress libraries at the same time, and no per-vendor e2e shard enabled both, so it silently skipped everywhere — the combination that regression covers (an `auth-url` check firing on a regex-matched path) was untested.
- Enabling several vendor annotation libraries at once no longer exceeds Kubernetes' per-object size limit. The combination previously failed to install with a bare `etcdserver: request is too large`, and was worked around by a documented "enable at most one" restriction. A new `make cr-size-check` gate measures every rendered object on each chart-test run, so the ceiling can no longer be crossed silently — nothing checked it before, which is why it surfaced as an unexplained end-to-end test failure rather than a lint error.
- The `HAProxyTemplateConfig` validating webhook no longer blocks a rolling `helm upgrade` that adds a new template builtin. During the rollout an older controller pod can still serve admission and hard-deny the new config with a template compile/render error its engine doesn't recognize (`undefined: <newBuiltin>`), which `failurePolicy: Ignore` can't rescue because it's an explicit deny. The webhook now detects version skew — the prospective config's `app.kubernetes.io/version` label differs from the same label on the controller's currently-running config (both chart-stamped, so they match in steady state and diverge only on a real chart-version change) — and admits such template compile/render failures with a warning, deferring to the target controller's authoritative, fail-closed load gate. Steady-state applies (matching versions) still deny template errors so typos are caught early, and `haproxy -c` and `validationTests` failures always deny (they're engine-version-independent).
- `haptic-controller benchmark` gains `--schema-dir` / `HAPTIC_SCHEMA_DIR` and resolves the effective spec + runs the offline type bootstrap like `validate`, so it can benchmark configs that use typed-resource access (`gateways`, typed `resources.<name>.List()`) — the bundled chart does. Previously any typed-access template failed to compile in the benchmark path, and the benchmark render skipped the per-test / `_global` extraContext baseline (so a custom `defaultSSLCertificate` name failed there too).
- A custom `defaultSSLCertificate.secretName` (or the new `ecdsaSecretName`) no longer crash-loops the controller at startup. The bundled `validationTests` render against synthetic fixture stores, but the default-certificate lookup used the operator's real Secret name — which exists only live in the cluster, never in a fixture — so the load gate failed every test and rejected the config. A validation test's shared `_global` block now contributes an isolated `extraContext` baseline (folded under each test, below any per-test override), so the SSL library can pin a synthetic default certificate that every test resolves regardless of the configured names; the real default-cert Secret is still validated by the live render at reconcile.
- The controller now honors the chart's `WEBHOOK_PORT` environment value instead of always binding `9443`, so changing `controller.ports.webhook` moves the process listener together with the pod, Service target, and NetworkPolicy. Invalid metrics/webhook environment ports now fail startup clearly instead of silently falling back.
- `HAProxyTemplateConfig` admission now gives embedded `validationTests` the same suite-size-scaled budget as the load gate, capped by the remaining configurable config-admission deadline. The bundled chart's own test suite is fully checked instead of timing out at a hardcoded five seconds and emitting a warning on every update.
- Normal configuration reloads no longer emit a false `Metrics component failed: context canceled` error when the previous controller iteration shuts down gracefully.
- `HAProxyTemplateConfig` admission no longer turns an internal render timeout into an explicit denial that can block the very config update needed for recovery. It now has a separate configurable deadline, admits timed-out checks with a warning for the authoritative load gate to enforce, and keeps the webhook HTTP write deadline long enough to return the result; watched-resource admission retains its tighter fail-closed budget.
- Routes no longer silently 404 for 15–30 seconds after a deploy reports success under churn (#84). The runtime-bypass fast path used to push the whole pending render (with `skip_version`), which could overwrite a concurrent reload deploy's config on disk before HAProxy's master re-exec read it — activating a pre-route config while the status advanced — or park new backends on disk un-reloaded, which the next deploy's empty diff then "successfully" skipped. The bypass now pushes the last reload-activated config patched with only the runtime-eligible server changes (endpoint updates stay instant and reload-free), a structural deploy verifies the on-disk config after its reload and fails retryably on divergence (counted as `haptic_deploy_runtime_divergence_total`), a headerless on-disk config always forces a reload even for runtime-only deltas, and a superseded render abandons its retry-across-reload storm instead of re-pushing a stale body.
- The docs site's changelog page is now generated from `CHANGELOG.md` at build time, so `/docs/dev/` always shows the current `[Unreleased]` changes; previously the page was only synced at release time and showed an empty `[Unreleased]` section between releases.
- The live config gate's validationTests budget now scales with suite size (25s floor + ~100ms per test) instead of a fixed 25s cap, and the validation coordinator's deadline is derived from the same formula — an all-passing large suite (e.g. the chart's 362 tests under CI contention) is no longer rejected as "partially-validated" purely because the clock ran out; fail-closed on genuinely incomplete runs is unchanged (#77).
- That suite-size budget now *adds* the 25s floor to the per-test allowance instead of taking the larger of the two, closing a false rejection at the crossover. Taking the maximum pinned every suite below 250 tests to exactly 25s — a floor sized as headroom for a *small* suite silently became the entire budget for a suite doing ten times the work — so the bundled chart's ~249-test effective suite (what survives `requires` stripping on a cluster without Gateway API CRDs) needed 27.3s against a computed 24.9s that clamped to 25s, and a perfectly good default config was rejected as partially-validated on a default install. Additive is also what the shipped formula description always said.
- The admission webhook now validates the EFFECTIVE HAProxyTemplateConfig — resolving watched-resource versions against live discovery and stripping `requires`/`requiresFields`-unsatisfied snippets and tests, exactly like the controller's load gate. Previously it compiled the raw proposed spec, so on clusters without an optional watched resource's CRDs (e.g. no Gateway API) every config update was denied with a template compile error while the running controller accepted the same config (#79). If resolution itself fails transiently, the webhook admits with a warning and defers to the load gate.
- A failed or timed-out deployment now invalidates the deploy scheduler's lane baseline, so a queued runtime-only render re-dispatches as a full structural sync instead of silently restamping the config version header over structural content the HAProxy workers never loaded — previously this could defeat the fast retry with a 0-op "success" and leave new listeners parked unreloaded until the next unrelated change (#76).
- A runtime server update against a backend the loaded config doesn't yet have (`No such backend`/`No such server`) is no longer misclassified as a transient reload and retried futilely for up to 2 seconds per apply; it now fails fast to the scheduled structural deploy that actually creates the backend, so convergence isn't delayed by the retry storm.
- A retryable deploy failure now self-reschedules with bounded exponential backoff (capped, then handed off to the 60s drift backstop) instead of waiting up to a full minute for the periodic drift check, and a fully-failed deploy now reports `Programmed=False` with a reason instead of freezing the last-known status (#72).

### Helm chart

#### Added

- New `controller.config.templatingSettings.extraContext.proxyProtocol` (`enabled`, `httpPort` default 8081, `httpsPort` default 8444) adds HTTP and HTTPS binds that require a PROXY protocol header, for HAPTIC behind a layer-4 load balancer that would otherwise hide every client behind its own address — leaving `client_ip`, `src`-keyed rate limiting, the WAF, and IP ACLs seeing one client. Enabling adds the ports to the HAProxy Service, the container ports, and the NetworkPolicy. They are additional listeners: `haproxy.ports.http`/`https` stay open and unchanged, because HAProxy has no "PROXY header optional" bind and requiring it on the main ports would reject direct, in-cluster, and NodePort traffic. With TLS-Passthrough configured the HTTPS bind attaches to the SNI-routing frontend instead of `frontend https`, so passthrough hosts keep their routing. Distinct from the `haproxy-haptic.org/proxy-protocol` annotation, which makes HAProxy *send* a header to a backend.
- New `HAProxyAccessLogRecordsDropped` alert (`controller.monitoring.prometheusRule.defaultRules.accessLogDropped`, on by default) fires when HAProxy discards access-log records. HAProxy reaches the Vector sidecar over a UNIX datagram socket, so if Vector stops draining it — a topology reload, a GC pause, CPU starvation — HAProxy drops records rather than blocking traffic. Measured on HAProxy 3.4.2: with the receiver stalled, 3000 requests delivered 167 records and `haproxy_process_dropped_logs_total` reported exactly the 2833 lost; with the receiver draining, zero. The socket absorbs only ~167 records at the default 212992-byte `rmem`, which is ~170 ms of stall at 1000 req/s. Documented as a property of the access-log path.
- New Vector sidecar on every HAProxy pod, **enabled by default** (`vector.enabled`). It receives the HAProxy access log over a mounted UNIX datagram socket (`vector.socketPath`, default `/run/vector/haproxy.sock`) and prints it to stdout, so the records now surface under `kubectl logs <pod> -c vector` instead of `-c haproxy`. It also re-exports HAProxy's Prometheus exporter and the SPOA hub's metrics alongside its own on one port (`vector.metricsPort`, default 9598), so `vector.podMonitor.enabled=true` gives Prometheus a single target per pod in place of the two the hub PodMonitor declares — and lets `spoaHub.hub.metricsAddr` stay on its loopback-only default, since vector scrapes it from inside the pod. Set `vector.enabled=false` to restore the previous behaviour exactly. The image tag is pinned (`vector.image.tag`) and Renovate-tracked.
- The vector config follows the same delivery path as the SPOA hub's: HAPTIC renders it and pushes it through the dataplane API into the shared general-storage volume, where vector's `--watch-config` picks it up and reloads without a restart. A bootstrap ConfigMap seeds the file so the log socket exists before HAProxy starts — a UNIX datagram sender gets no error when nothing is listening, so records would otherwise be silently dropped. The sidecar's readiness probe only passes once the rendered config has been pushed: it targets the metrics port, and only the rendered config declares the exporter that serves it, mirroring how HAProxy's own `/ready` answers only for a pushed config.
- The Vector sidecar's merged metrics endpoint is shaped to a size Prometheus can hold. Measured on a real 2-pod fleet, a single scrape was 2.45 MB and 16,046 series, 94% of it `haproxy_`. Three changes cut that to roughly a third: the re-export no longer stamps an `instance` label (it carried the *scraped* target, `127.0.0.1:8404`, identical on every pod, and Prometheus adds its own `instance` from the pod target — so Vector's copy surfaced as a duplicate `exported_instance` on 15,116 series, costing 393 KB per scrape); new `vector.excludeMaintServerMetrics` (default `true`) passes HAProxy's `?no-maint` so reserved server slots with no backing pod stop reporting a full metric set of zeros each — 159 of 193 slots were empty, 67% of all series; and new `vector.excludeMetrics` takes regexes matched against the metric name, defaulting to `haproxy_*_max_*`, whose "since the process started" maxima never reset and can't be aggregated across pods. `haproxy_backend_agg_*` and `haproxy_*_average_seconds` are deliberately kept — the first is the only remaining free-slot census, and HAProxy's exporter publishes no histogram, summary, `_sum` or `_count`, so the averages are its only latency signal. No metric **name** disappears, so dashboards and rules that select by name are unaffected. `honor_labels` still preserves HAProxy's own `proxy`/`server`/`code`/`state` labels.
- Access-log records no longer carry fields whose value is empty, so a line shows only what actually happened (`vector.omitEmptyLogFields`, on by default). A feature that didn't fire still cost its field on every line: on a measured fleet `trace_id`, `denied_by`, `waf_matched_var`, `consumer` and `cache` were empty in **100%** of records, and dropping every empty made records **27% smaller** — 815 to 595 bytes on average. Sending nothing rather than an empty value is also what Elastic Common Schema and OpenTelemetry recommend. HAProxy can't do this itself: its JSON encoder's whole option set is `M`/`Q`/`X`/`E`/`bin`/`json`/`cbor`, unknown options are silently ignored, and the nearest one (`+M`) does the opposite by substituting `-` — so the Vector sidecar strips them in a `remap` transform. The transform rewrites the line rather than re-encoding it, which keeps the field order the log-format chose (re-encoding sorts keys alphabetically and would bury `ts`, the field that exists because `format raw` drops the syslog timestamp). Numbers are untouched, so a genuine `queue_time_ms: 0` is kept, and HAProxy's process messages on the same stream still pass through byte-for-byte. Set `vector.omitEmptyLogFields=false` if you feed a strongly typed index or have queries written as `field == ""`, where a stable field set matters more than the bytes.
- **BREAKING** (pre-release only): the access-log timing fields are renamed `t_request`/`t_queue`/`t_connect`/`t_response`/`t_total` → `request_time_ms`/`queue_time_ms`/`connect_time_ms`/`response_time_ms`/`total_time_ms`. The `t_` prefix saved 30 bytes on an 800-byte record while hiding the unit, and the ecosystem disagrees on it — nginx's `$request_time` is seconds, Prometheus convention is seconds, HAProxy's are milliseconds — so the unit now lives in the name. Documented alongside two facts that were previously only in code comments: a timer is `-1` when its phase never happened (HAProxy's own convention, so `connect_time_ms: -1` is a signal, not a bad reading), and `total_time_ms` excludes keep-alive idle time on HTTP frontends while covering the whole session on TCP frontends.
- New opt-in distributed tracing, owned by HAProxy itself rather than by a sidecar (`controller.config.templatingSettings.extraContext.tracing`). With `tracing.enabled=true`, HAProxy adopts a valid inbound W3C `traceparent` (same trace, the caller's span becomes the parent, its sampling decision is honoured), mints a trace id and span id otherwise, takes an edge sampling decision (`tracing.sampleRate`, root requests only), and sets `traceparent` on the request **before** it reaches the backend — so your services join the trace. No SPOA hop is involved, so it works with the hub disabled, and `span_id`, `parent_span_id` and `trace_flags` join the access log. Set `tracing.otlp.endpoint` to also export HAPTIC's own spans: the Vector sidecar turns access-log records into OTLP/HTTP spans, which covers **every** request including HAProxy-generated 502/503/504s, denials, redirects and errorfiles — transactions a SPOE-based exporter structurally cannot see, because `http-response` rules never run for them. Off by default: it changes what backends receive and there is no sensible default destination for traces. Minted ids deliberately use only UUID groups 1, 2 and 5 — a whole UUID pins byte 8 to the variant nibble, which drives every `TraceIdRatioBased` sampler to 0% at ratios of 50% or below, in every downstream service.
- New `listener_port` access-log field: the port the routing lookup was keyed on. Host and path map keys are scoped by it (`<host>:<port>/...`), so a route that matches nothing is now distinguishable from one that matched a different listener's keys — previously a miss showed only as `backend=default_backend` and needed the pod's on-disk `host.map` to diagnose. For a Gateway listener it is the per-Gateway pod port the chart allocated, not `spec.listeners[].port`; it is empty on frontends that run no routing logic (`status`, the cache-origin leg). Logged as a JSON string on every frontend, deliberately: the value is a number when it comes straight from `dst_port` and a string once a listener-port library remaps it, and an unstable type splits a typed log index. If you added your own `accessLog.fields.listener_port`, remove it — a field colliding with a built-in name is rejected at render time, which the load gate turns into a crash-loop.
- New opt-in `controller.config.templatingSettings.extraContext.accessLog.suppress.successful` drops access-log records for 2xx/3xx requests that no gate denied, keeping every denial, 4xx and 5xx. Off by default on purpose: retaining a full log is lawful under legitimate interest (GDPR Art. 6(1)(f)), and the successful requests either side of a failure are what make a customer's report diagnosable — a record is ~740 bytes, so reach for this when volume forces it, not for privacy. Emitted as `http-after-response`, because `http-response` rules never run for HAProxy-generated responses and a WAF deny would slip the condition.
- New `haproxy.dataplane.logLevel` (default `info`) replaces a hardcoded `trace` for the Dataplane API sidecar, which logs a line per file operation — ~671 lines for a single startup plus config cycle. Raise it to `debug` or `trace` when diagnosing a config push the controller reports as failing but HAProxy accepts.
- New `waf_matched_var` access-log field naming the request fields a WAF rule matched on — `ARGS_GET:id,REQUEST_LINE` — never their values. Paired with `waf_rule_id` it gives both halves of a false positive (which rule, on what) from the access log alone, so tuning a policy no longer needs Coraza's audit log, which writes the client IP, every request header and the matched bytes to the sidecar's stdout. Only request-derived variables are reported, deduplicated and capped at five, with the reported rule's own targets first. Bundled coraza plugin bumped to v0.8.0.
- Hub log lines now correlate with the access log. Every SPOE message carries `req_id=unique-id`, and spoa-hub v0.11.0 adopts it — so a hub warning and the JSON access-log record for the request that caused it share one key (`span.req_id` in the hub's output, `req_id` in the access log). Previously the hub's identity was a synthetic per-frame value nothing outside the hub could join on. Nothing to configure. Bundled hub bumped to v0.11.0; an older hub ignores the argument, and an older chart gets hub-generated ids, so neither side is a hard dependency of the other.
- New `controller.config.templatingSettings.extraContext.accessLog.targets` routes the JSON access log away from the container's stdout. The access log carries a `client_ip` field — personal data — and in a typical cluster stdout is scraped into a general-purpose log store; this sends it to an access-controlled destination instead. Each entry renders one HAProxy `log` line (so several fan out, which a collector migration needs) and takes an `address` (`stdout`, `stderr`, `fd@<n>`, `<host>:<port>`, a socket path, or `ring@<name>`), `format`, `facility` and `level`, or a `ring` block for a buffered TCP client. HAProxy's own process and alert messages keep a separate stdout target, so `kubectl logs` stays useful while only the personal-data-bearing stream moves. A ring queues records in memory while the collector is down and flushes on reconnect — measured with the collector stopped, 25 of 25 requests were served with no errors and all 25 records arrived afterwards, where a plain UDP target would have dropped them. `ring.serverOptions` is appended verbatim to the ring's `server` line, which reaches TLS or any other server keyword without the chart modelling each one. Target combinations HAProxy accepts at config check and then ignores, dies on, or silently gets wrong are rejected at render time instead: a `level` stricter than `info` (access records are emitted at info, so `notice` and above drop the entire stream), a Unix-socket ring server (fatal on HAProxy 3.4, accepted on 3.0), a `ring@<name>` naming no declared ring (HAProxy refuses to start with `unknown ring named`), two targets rendering the same `log` line (every request logged twice), an empty target list (which would fall back to the stdout this setting exists to move records off), a ring buffer too small to hold one `maxLineBytes` record (HAProxy caps the ring's record length to the buffer minus its header and truncates every longer record into invalid JSON, warning but not failing), and a port outside 1–65535 in either address.
- Structured JSON access logs. Every HAProxy frontend now emits one JSON object per request (or per connection, for the TCP-mode frontends) using HAProxy's native `%{+json}o` encoding, with the log target switched to `format raw` so records carry no syslog prefix and a collector can parse lines directly. The core record covers request identity, the five HAProxy timers, retries, the termination state, `resource` (the `<namespace>/<name>` of the Ingress/HTTPRoute/CRD that owns the matched route), and `denied_by` — which names the gate that blocked a request, because six mechanisms can produce a 401, three a 403 and three a 429. HAProxy's own process and health-check lines on that stream are not JSON, so a collector must tolerate non-JSON lines.
- Template libraries contribute access-log fields for the features you actually configure, through a new `log-fields-*` extension point: WAF action/rule id/anomaly score/matched-rule count, shared rate-limit verdict and remaining budget, external-auth status, request-schema outcome, cache `HIT`/`MISS` plus the intended application backend, the authenticated consumer, TLS version/SNI/resumption, mTLS verify result and CN, the matched Gateway route rule, captured request headers, and the real TCP peer behind a forwarding header. A field is emitted only when its feature is in use, so an unused feature costs no bytes per record. With those fields on every request, tuning a WAF policy no longer needs Coraza's audit log — which writes the client IP and request headers to the sidecar's stdout — so the WAF tuning guide now leads with the access log and the plugin's hashed rule-match log, and treats the audit log as a last resort.
- New `controller.config.templatingSettings.extraContext.accessLog.fields` adds custom JSON fields from a YAML hash (field name → one HAProxy sample expression, captured at request time so `req.hdr(X-Tenant)` works; `str(prod-eu)` for a constant label), and `accessLog.maxLineBytes` (default `16384`) bounds the record before HAProxy truncates it. Field names and expressions are validated in both Helm and the render, so a typo or an injection attempt fails with a message naming the field.
- New `spoaHub.monitoring.podMonitor` (default off) renders a Prometheus PodMonitor for the HAProxy pod, scraping the SPOA hub's data-path metrics (`spoa_*`, `plugin_coraza_*`) plus HAProxy's backend timers (`:8404`) — the pod the bundled controller ServiceMonitor/PodMonitor don't cover. Because the hub binds metrics on loopback by default, enabling it requires `spoaHub.hub.metricsAddr` set to a non-loopback bind (e.g. `0.0.0.0:9095`); the chart fails rendering with that guidance rather than emit an unreachable scrape target. A hub image with the latency-observability metrics adds histograms for the in-flight-gate wait (`spoa_backpressure_wait_seconds`) and the return-path ACK writer's flush time and batch coalescing (`spoa_ack_flush_duration_seconds`, `spoa_ack_batch_size`), plus gauges for the adaptive-concurrency controller's moving ceiling and baseline (`spoa_plugin_adaptive_limit`, `spoa_plugin_adaptive_baseline_rtt_seconds`).
- The SPOA hub sidecars now set Go-runtime GC env for their embedded Go runtime (the coraza plugin): `GOGC` from a new `spoaHub.hub.goGCPercent` value (default `300`) and `GOMEMLIMIT` auto-derived as a soft cap at 90% of the container memory limit (omitted when no limit is set). Raising GOGC above Go's default 100 trims GC frequency under load — fewer stop-the-world pauses and less GC-assist CPU stealing on the request path — for a lower p99 tail, while GOMEMLIMIT keeps the larger heap bounded. Set `spoaHub.hub.goGCPercent: 100` to restore Go's default.
- New `spoaHub.plugins.<name>.adaptiveConcurrency` plugin field (default false). When true, the hub runs a latency-feedback controller (`haproxy-spoa-hub` ADR-0002) that resizes the plugin's admission semaphore at runtime to track its service time, and `maxConcurrency` becomes the controller's ceiling rather than a fixed limit — so the concurrency need not be hand-tuned per environment. Requires a hub image with adaptive support; off by default, and the rendered config is byte-identical to before the feature unless a plugin opts in.
- Org-wide policy guardrails (`controller.config.templatingSettings.extraContext.governance.*`): cluster admins declare generic, JSONPath-driven rules that namespace teams cannot omit. Each rule targets a watched resource by name (`ingresses`, `httproutes`, or any custom CRD) and, per matching resource, either **injects** a configured `default` when a value is absent (the injected value flows into the same render, so downstream snippets emit config for it — e.g. a default `rate-limit-rps` activates the rate limiter) or **validates** the present value with `required`, `min`/`max` (with `onViolation: clamp` to rewrite out-of-bounds values to the cap, or `reject`), `allowed` (enum), `pattern` (regex), `anyOf` (one-of-many paths present), or `satisfiedBy: tls` (`spec.tls` or chart-wide default HTTPS). `enforcement: reject` denies a new or edited violating resource at the admission webhook (scoped to the offending resource's own admission, so one pre-existing violator never wedges an unrelated apply) and records a `GovernanceViolation` Warning Event for already-present violators; `enforcement: audit` warns only. `exemptNamespaces` skips infra namespaces. Disabled by default; pure render/admission logic (no Kubernetes resources), so it lives under `extraContext` rather than a root-level values block. Backed by three generic, resource-agnostic template helpers (`resource(name)`, `jsonpathGet`, `jsonpathSet`) so a single snippet governs any watched resource with no per-annotation hand-coding.
- A `pre-install`/`pre-upgrade` hook Job now applies the bundled CRDs on every install and upgrade (`crds.upgradeJob.enabled`, default true), running `haptic-controller apply-crds` with server-side apply. This makes `helm upgrade` and GitOps sync actually pick up additive CRD schema changes, which Helm otherwise never applies for CRDs in `crds/`. The Job runs under its own scoped RBAC — a ServiceAccount plus a ClusterRole limited to `customresourcedefinitions` (`get`/`list`/`create`/`patch`, never `delete`) — and is removed on success (kept on failure for inspection). Disable it if you manage CRDs out-of-band or lack cluster-scoped CRD write permission at upgrade time.
- New `defaultSSLCertificate.ecdsaSecretName` optional companion makes the **default** certificate dual: point `secretName` at the primary (RSA) Secret and `ecdsaSecretName` at an ECDSA one for the same names, and HAProxy serves ECDSA to modern clients and RSA to the rest on the no-SNI / unmatched-SNI path (both emitted as `*` default crt-list lines — the empty-SNI form breaks the RSA fallback). Aimed at wildcard-default setups where one cert fronts many teams' hosts. Per-host dual certs (Ingress `spec.tls`, Gateway listener `certificateRefs`) already worked; the docs now cover all three cases.
- Reusable WAF policies gain a structured, self-service-safe `ruleExclusions` field for tuning CRS false positives without an administrator. Each entry supplies numeric CRS rule IDs (`rules`) and/or CRS rule tags (`tags`), an optional exact target variable (`excludeTarget`), and an optional literal path scope (`onPathPrefix`/`onPathContains`/`onPathExact`/`onPathSuffix`); the chart lowers them to `SecRuleRemoveById`/`SecRuleUpdateTargetById`/`SecRuleUpdateTargetByTag` (global) or a chart-owned `SecRule` + `ctl:ruleRemove[Target]ById`/`ByTag` (path-scoped), so no tenant-authored regex ever runs on the request path. The CRS setup, anomaly-scoring, and correlation rule ranges are reserved so an exclusion can't disable enforcement itself, and regex collection keys are rejected. Available in self-service catalogs (no SecLang grant needed) — a namespace can now tune its own false positives, e.g. disabling CRS rule 930130 on `.git/` paths so git-over-HTTP stops false-positiving.
- The bundled coraza SPOA plugin was updated to v0.7.0, adding per-matched-rule metrics (`plugin_coraza_rule_hits_total{phase, rule_id, severity, app}`) that count every rule that fired — including on allowed traffic, which is the signal a detect-mode policy needs before flipping to deny. The docs gain a "Tune a WAF policy from detect to deny" workflow covering the new metrics, the Coraza JSON audit-log sink, and turning classified hits into `ruleExclusions` or `allowedMethods` widening.
- Reusable WAF policies gain structured CRS tuning fields: `allowedMethods` (HTTP method allowlist), `paranoiaLevel` (1-4), and `anomalyThreshold.inbound`/`.outbound`. They lower to crs-setup-position `SecAction`s spliced before the CRS rules include in the route's Coraza application — the position where CRS actually reads these variables, which raw policy `secLang` (injected after the include) structurally cannot reach. Because they are validated structured values rather than rule code, self-service catalogs may use them, so a namespace team can widen the method allowlist for its own REST API without any admin grant.
- Reusable WAF policies gain a `crsSettings` field for fine-tuning a CRS rule's *inputs* instead of disabling the rule — the preferred first response to a false positive. `allowedRequestContentTypes` merges media types into the standard CRS content-type allowlist (the chart carries the CRS default, which upstream ships commented out, and emits the full `|type|`-wrapped list as a REPLACE — so rule 920420 stays active for every other type); `maxFileSize`, `maxNumArgs`, and `totalArgLength` set a bounded scalar. Values lower to one crs-setup-position `SecAction`; the chart owns the full target variable, so tenants never write a collection prefix (and can't reach the writable `GLOBAL`/`IP`/`SESSION` state collections) and each token is charset-validated against `setvar` injection. Self-service-safe (no SecLang grant). Canonical use: a git host allowlists `application/x-git-upload-pack-request` so CRS 920420 keeps inspecting every other content type, where disabling the rule would switch content-type inspection off entirely.
- Namespaced self-service WAF policy authoring (`controller.config.templatingSettings.extraContext.waf.policies.selfService`): with `enabled: true`, every namespace may define Coraza policies for its own Ingresses in a well-known `waf-policies` ConfigMap in that namespace (name/key configurable) and select them with `haproxy-haptic.org/waf-policy` — no per-namespace admin registration. Safe by construction: policies are namespace-scoped (invisible to other namespaces; trusted-catalog names are resolved first and collisions are rejected loudly, never silently shadowed), a broken catalog or policy fails only that namespace's selecting routes closed with `503` plus `WafPolicyCatalogInvalid`/`WafPolicyInvalid` Warning Events (the admission webhook rejects changes that would introduce the breakage; the global render is never aborted), `secLang` requires the separate `selfService.allowSecLang` grant, per-namespace and total policy budgets cut deterministically, `defaultPolicy` resolves in the trusted catalog only, and a self-service `detect` policy cannot weaken a `default-on`/`deny` baseline. Discovery uses a dedicated ConfigMap watch scoped by field selector to the well-known name, so only the catalogs are retained in memory. Also changed: an unknown or unavailable `waf-policy` selection on an already-present Ingress now fails that route closed (`503` + `WafPolicyUnavailable` Event) during a live render instead of aborting the whole render; the admission webhook still rejects it at apply time.
- Misconfigured routing/presentation annotations on an already-present Ingress now warn instead of bricking the fleet: a bad redirect code/port, a malformed rewrite, an invalid CORS/canary/mirror/compression/fixed-response value records a `Warning` Event (reason `InvalidAnnotationValue` or `InvalidAnnotation`) on the Ingress and skips just that feature during a live reconcile, while the admission webhook still rejects the change when you apply or edit it. Security features (authentication, client/backend mTLS, WAF, rate limiting, request-body validation, `X-Forwarded-For`) still hard-fail in every mode, so a misconfigured security control is never silently skipped (no fail-open). Applies across the native and vendor annotation libraries. Chart authors reject watched-resource input via the new `WebhookRejectOrWarn` helper.
- Cross-family annotation-collision guard: an Ingress that configures the same feature through annotations from two different families — for example `haproxy-haptic.org/waf-policy` together with `haproxy-ingress.github.io/waf`, or `haproxy-haptic.org/cors-enable` with `nginx.ingress.kubernetes.io/enable-cors` — is now caught with a message naming the feature, the families, and the colliding annotations. The admission webhook rejects a new or edited conflicting Ingress; an Ingress that already carries a conflict records a `Warning` Event (reason `AnnotationFamilyConflict`) and keeps serving rather than failing the render, so one bad Ingress can't block config updates for the whole fleet or crash-loop the controller at startup. The check fires even when the two values agree, because the effective result would otherwise depend on library render order. Different features across families stay allowed (WAF from one family, CORS from another), as do genuinely different parameters of the same category (two different timeout parameters). Only annotation families whose template library is enabled are considered.
- New `haptic-annotations` template library exposes HAPTIC's native `haproxy-haptic.org/*` annotation vocabulary — a best-of-breed superset of the haproxytech, haproxy-ingress, and nginx-ingress libraries, with one clean annotation per capability (adopting the strongest semantics of each: haproxytech pod-aware maxconn and request capture, haproxy-ingress agent checks / OAuth2-proxy / config-section injection, nginx-ingress canary, request mirroring, and bandwidth throttling). Enabled by default (`controller.templateLibraries.hapticAnnotations.enabled`); the recommended vocabulary for new configs. The vendor libraries remain for migrating existing annotations.
- API-gateway annotations on the native `haproxy-haptic.org/*` library (pure HAProxy config, no plugin): API-key authentication (`api-key-secret`/`api-key-header`/`api-key-query`/`api-key-consumer-header`) backed by a reload-free key→consumer map that establishes a shared consumer identity; stateless request gating (`allowed-methods` → 405, `require-content-type` → 415, `require-headers` → 400, `mock-response`, `fixed-response`); and request correlation IDs (`request-id`/`request-id-header`/`request-id-accept-inbound`).
- JWT, HMAC, and consumer-group annotations on the native library: asymmetric JWT verification (`jwt-secret`/`jwt-algorithm`/`jwt-issuer`/`jwt-audience`/`jwt-required-claims`/`jwt-forward-claims`) with an alg-confusion guard, `exp`/`iss`/`aud`/required-claim checks, and a `sub`-derived consumer identity (fails closed with 503 when the key Secret is absent); HMAC request-signature verification (`hmac-secret`/`hmac-algorithm`/`hmac-header`/`hmac-signed-string`); and consumer-group authorization (`consumer-groups-secret`/`allowed-consumer-groups`) that denies 403 unless the authenticated consumer is in an allowed group.
- Response compression annotations on the native library (`compress-enable`/`compress-algorithm`/`compress-types`): per-Ingress HAProxy-side compression with `gzip`/`deflate`/`raw-deflate`; `brotli`/`zstd` fail the render (unavailable in the community HAProxy build).
- Shared response cache: an opt-in, chart-deployed Varnish tier (`cache.varnish.enabled`) that HAProxy shards by URL with bounded-load consistent hashing, so the cache is shared across the whole HAProxy fleet (loopback origin — on a miss Varnish fetches back through HAProxy, which routes to the app). Deployed as a StatefulSet (or Deployment) + headless Service + static VCL via the controller's `k8sResources` (Server-Side Apply, GC'd on uninstall), with a PodDisruptionBudget, soft node spreading, and a release-scoped NetworkPolicy by default. The policy admits only same-release HAProxy cache requests and permits Varnish egress only to DNS plus the same HAProxy HTTP origin. Per-route control via native annotations: `cache-enable`, `cache-ttl`, `cache-key` (vary by consumer/header/cookie/query/src — making it safe to cache authenticated content per consumer), `cache-exclude-content-types`, `cache-exclude-paths`, and `cache-max-object-size`. Cached responses carry an `X-Cache: HIT`/`MISS` header. Source-verified Varnish miss loopbacks bypass shared rate limiting because the external request was already counted. The tier can autoscale via an optional HorizontalPodAutoscaler (`cache.varnish.autoscaling`) — bounded-load consistent hashing keeps per-shard load even, so average CPU is a sound signal; a generous scale-down window guards cache warmth. The controller Role grants `statefulsets`/`configmaps`/`poddisruptionbudgets` (and `horizontalpodautoscalers` when autoscaling is on) only when the tier is enabled.
- Shared request-rate limiting: opt-in native `haproxy-haptic.org/rate-limit-requests` annotations enforce one budget across the HAProxy fleet through the bundled rate-limit SPOA plugin. The chart-managed default is HA Valkey with Sentinel (three pods, one writable primary, failover, PodDisruptionBudget, NetworkPolicy) and operators can still bring their own Redis/Valkey/Sentinel/Cluster store via `rateLimit.shared.externalStore.urls`; annotated routes fail closed on missing plugin verdicts, exact store checks use configurable short default timeouts, and the default lease mode bounds local key state and store work for DoS-facing use.

HAProxy rejects oversized bodies before the SPOE roundtrip; the plugin compiles schemas at reload and validates bounded JSON in memory on the request path. `controller.config.templatingSettings.extraContext.requestBodyInspection.haproxyBuffer` configures the HAProxy buffer capacity shared by request-body inspectors.
- Reusable Coraza WAF policies for native Ingress annotations: HAPTIC administrators can define bounded policies in chart values or exact, RBAC-protected cross-namespace ConfigMaps, while Ingress authors select one with `haproxy-haptic.org/waf-policy` and optionally override enforcement with `haproxy-haptic.org/waf-mode`. Policies support request-body modes, enforcement, structured CRS tuning (method allowlist, paranoia level, anomaly thresholds, rule exclusions), and advanced SecLang. Optional immutable defaults cannot be removed or replaced by an Ingress; mode, vendor compatibility rule snippets, and raw HAProxy escape hatches are centrally authorized and default-deny where they could weaken enforcement. Shared policies compile once across routes, while nginx-compatible per-Ingress rule applications have configurable count and byte bounds.
- Each vendor annotation library (nginx-ingress, haproxy-ingress, haproxytech) now declares machine-readable migration coverage for its source controller's annotations — surfaced on `spec.migrationCoverage` and used to generate the per-source annotation-support tables in the [migration guide](./docs/site/docs/migrating.md). Only enabled libraries contribute.
- `HAProxyFleetDiverged` PrometheusRule alert (toggleable) and a Grafana fleet-convergence panel, built on the new fleet-convergence metrics.
- New `haproxy.org/cors-respond-to-options` annotation: when `"true"`, HAProxy answers the CORS preflight (OPTIONS) with a 204 instead of forwarding it to the backend, matching the upstream HAProxy Kubernetes Ingress Controller.
- New `extraContext.tls.hsts.enabled` opt-in (default off, declared by the SSL library) sends `Strict-Transport-Security` on every TLS response, matching ingress-nginx's and haproxy-ingress's global HSTS default; `tls.hsts.maxAge`/`tls.hsts.includeSubdomains`/`tls.hsts.preload` tune the value, and a per-Ingress `hsts` annotation still overrides it per host. Because HSTS is only effective over HTTPS, the rendered config emits a warning when it is enabled without an HTTP→HTTPS redirect. The nginx-ingress and haproxy-ingress migration coverage now points to this knob.
- New `extraContext.ingressDefaultSSLRedirect` opt-in (default off): redirects every HTTPS-served Ingress host from HTTP to HTTPS with a single global toggle, complementing the per-host `ssl-redirect` annotations. Only hosts actually served over HTTPS are redirected (the default-HTTPS bind is on, or the host has `spec.tls`), so it never points a client at a closed port. `ingressDefaultSSLRedirectCode` (default `308`) sets the status code.
- New `extraContext.tls` cipher/protocol policy (declared by the SSL library) sets a global forward-secret default on every HTTPS bind — `tls.ciphers` (a cert-agnostic superset spanning the ECDSA, RSA, and DHE families), `tls.ciphersuites` (TLS 1.3), and `tls.minVersion` (TLS 1.2 floor), rendered as `ssl-default-bind-ciphers`/`-ciphersuites` and `ssl-min-ver`. The same list serves RSA-only, ECDSA-only, or dual RSA+ECDSA deployments — HAProxy offers only the suites it has a certificate for — and a host serves dual certificates by referencing two TLS Secrets for it (HAProxy picks ECDSA-first with RSA fallback per client). Each sub-key is overridable (empty string omits its directive) to widen coverage for legacy static-RSA clients.
- New `extraContext.tls.sessionTickets.enabled` toggle (default off, a sibling of the cipher policy and `tls.hsts`) turns on fleet-wide TLS session resumption: every HAProxy pod shares one session-ticket encryption key (STEK), so a ticket issued by any pod resumes on any other — covering both TLS 1.2 (RFC 5077) and TLS 1.3 (RFC 8446 PSK). The SSL library emits the shared key file and the bind `tls-ticket-keys` option, and self-rotates the key daily through a 3-key sliding window with one hitless reload. Keys are full-entropy random values generated in-cluster (a new `randBytes` template function), read back each render via the `currentFiles` global to decide when a day has elapsed — no external rotation component and no static secret.

- New `extraContext.requestBuffering` (`enabled`, default **on**; `waitTimeout`, default `10s`) makes HAProxy wait for the request body before taking a backend connection, so a client that trickles its upload holds an HAProxy buffer instead of a backend server slot — the standard slow-POST defence. HAProxy releases the request once the body is complete *or* `tune.bufsize` is full, so a large upload is never fully buffered. Only requests declaring a `Content-Length` are held: nothing that streams can declare its length upfront, so gRPC (which sends neither `Content-Length` nor `Transfer-Encoding`, for unary and streaming calls alike) and chunked streaming uploads are excluded by construction rather than by a media-type list. Set `enabled: false` to restore the previous behaviour.
- New `haproxy-haptic.org/request-buffering` annotation (`on`/`off`) overrides the fleet-wide buffering default per route via a reload-free map. Use `off` for a route whose clients declare a `Content-Length` but still expect a response before the body ends.

#### Removed

- **BREAKING**: the `otel` SPOA hub plugin is gone, along with `spoaHub.plugins.otel`. Distributed tracing no longer needs it: HAProxy mints and propagates W3C trace context itself and the Vector sidecar derives OTLP spans from the access log, which covers the same ground without a SPOE round-trip per request on the data path — and without a second place for the trace pipeline to be configured. Remove `spoaHub.plugins.otel` from your values: the chart now fails the render with a message naming the replacement, because a leftover block would otherwise be written into the hub's `config.toml` for a plugin the image no longer contains and fail at runtime instead of at install. The bundled hub image ships eight plugins instead of nine.

#### Changed

- **BREAKING**: the chart now renders one `HAProxyTemplateConfig` per enabled template library, named `<controller.configName>-<library>`, plus `<controller.configName>` for your own `controller.config`. The controller merges them at startup in the order it is given via `CRD_NAME`, later wins, so your config still overrides every library and the effective configuration is unchanged — verified byte-identical to the previous single-object output for the default, `+nginx-ingress` and all-libraries profiles. Anything that post-processes `helm template` output expecting exactly one `HAProxyTemplateConfig`, or reads the whole config out of one object, must be updated: `haptic-controller config view --input` prints the merged config, and `haptic-controller validate -f` accepts a multi-document stream. Only the operator object is yours to edit — the library objects are chart output that `helm upgrade` overwrites; override a snippet by name under `controller.config.templateSnippets` instead. Applying a single hand-written config without Helm is unaffected. The split exists because the single merged object had reached 1,564,098 bytes with `nginx-ingress` enabled — 99.4% of the ~1.5 MiB limit Kubernetes enforces per object, with 8,766 bytes of headroom; the largest object is now ~35% of it with every library enabled. See ADR-0014.
- **BREAKING**: `credentialsSecretRef`, `podSelector`, `watchedResources` and `haproxyConfig` are no longer required by the CRD schema. A single object in a merged set legitimately carries only `templateSnippets`, so the merged result — not any one object — is the unit of completeness. The controller enforces the first three after merging exactly as before (the fourth it never reads), and the admission webhook still rejects an incomplete config at apply time; what changes is that a hand-written config missing one of them is now refused by the controller rather than by `kubectl apply`.
- **BREAKING**: the access log is now JSON on every frontend. `option httplog` / `option tcplog` output is gone and the log target uses `format raw` (no syslog prefix), so any pipeline that parses the previous text line shape must be updated. Records carry their own `ts` field in place of the syslog timestamp. To keep a text format, override `util-log-format-http` / `util-log-format-tcp` via `controller.config.templateSnippets`.
- **BREAKING**: request correlation IDs are now opaque RFC 9562 UUIDv7 values (`unique-id-format %[uuid(7)]`), emitted for every request rather than only when an Ingress opts into the `request-id` annotation. The previous `%ci:%cp_%fi:%fp_%Ts_%rt:%pid` format embedded the client IP — personal data under GDPR Article 4(1) and Recital 30 — and the frontend's own address in a value that is forwarded upstream, echoed to clients, and copied into application logs and support tickets; with the address inside the id, dropping the `client_ip` field no longer redacts it. Anything parsing `X-Request-ID` for those fields must be updated, and `request-id-accept-inbound` now preserves a client-supplied id only when it matches `^[A-Za-z0-9._:-]{1,128}$` so a client cannot choose an arbitrary or oversized correlation id for the backend's logs. `unique-id-format` moved from the `haptic-annotations` library to `base.yaml`; use a `defaults-settings-*` snippet above band 150 for `%[uuid()]` (v4) or a custom format.
- The internal h2c demultiplexer frontend (`http-tcp`) now sets `option dontlog-normal`. Every connection it accepts is handed to an inner HTTP frontend that logs the request itself, so its normal lines were a second, near-information-free record per connection. Abnormal terminations still log.
- Bumped the bundled SPOA hub image to `v0.10.0`, which activates the SPOE data-path latency metrics the new `spoaHub.monitoring.podMonitor` scrapes: histograms for the in-flight-gate wait (`spoa_backpressure_wait_seconds`) and the ACK writer's flush/batch (`spoa_ack_flush_duration_seconds`, `spoa_ack_batch_size`), gauges for the adaptive controller's moving ceiling and baseline (`spoa_plugin_adaptive_limit`, `spoa_plugin_adaptive_baseline_rtt_seconds`), and refined `spoa_message_duration_seconds`/`spoa_plugin_duration_seconds` buckets that resolve the WAF p99 across the 1–10ms band.
- The coraza (WAF) and api-gateway plugins now default to **adaptive concurrency** (`adaptiveConcurrency: true`, ADR-0002) with a **memory-derived ceiling** — so WAF concurrency needs no manual tuning across small and large deployments. The hub finds the right concurrency from live request latency (filling available CPU without over-subscribing), and `maxConcurrency` becomes a ceiling derived from the sidecar's memory (`spoaHub.resources`, ~16 at the 256Mi default, scaling up with more memory — concurrency is realised as blocking threads, so memory is the binding resource, not cores). Give the sidecar more memory and the ceiling rises; the operator never sets a concurrency number. Set `adaptiveConcurrency: false` or a literal `maxConcurrency` to opt out. Full adaptivity needs a hub image with adaptive support; an older hub ignores the flag and runs the derived ceiling as a fixed cap (still an improvement over the previous fixed 16).
- The chart's cluster-scoped objects — the controller `ClusterRole`/`ClusterRoleBinding`, the `ValidatingWebhookConfiguration`, and the new CRD-upgrade hook's RBAC — are now named with the release namespace appended (`<fullname>-<namespace>`), so the same release name can be installed into two namespaces without colliding on shared cluster-wide names. Namespaced objects (the webhook `Service`) and cluster singletons that are a user-facing API (the `IngressClass`, the CRDs) keep their stable names. `helm upgrade` recreates the renamed objects transparently (create-before-delete within the release); only external references to the old `ClusterRole`/webhook-config names (uncommon) need updating.
- The shared Varnish cache now uses the canonical HAProxy+Varnish "sandwich" topology: Varnish fetches cache misses from a dedicated internal HAProxy backend-fetch frontend (`cache.varnish.loopbackPort`, default `8090`, fronted by the `haptic-cache-origin` ClusterIP Service) instead of looping back through the client-facing frontend. The WAF, rate limiter, external auth, and routing now run exactly once per request — on the client leg — and never re-run on a cache miss (previously the Coraza WAF re-evaluated every miss, roughly doubling its CPU and latency on cache+WAF routes). The backend-fetch frontend routes each loopback to the same backend the client leg selected via the internal `X-Haptic-Backend` header (set and stripped-of-client-copies in the `varnish_cache` backend), so rewritten and weighted routes stay correct. This replaces the source-IP loop-break map, which churned with Varnish pod IPs, raced pod restarts, and broke under kube-proxy SNAT (`--masquerade-all`). The dedicated port is internal-only (never on the LoadBalancer) and restricted to Varnish by the HAProxy NetworkPolicy. New values: `cache.varnish.loopbackPort` and `cache.varnish.originServiceName`.
- **BREAKING**: Controller workload values moved under `controller.*` (`image`, `replicaCount`, `deploymentAnnotations`, probes, `resources`, `serviceAccount`, `rbac`, `service`, `securityContext`, `extraEnv`/volumes/sidecars/rollout keys, `autoscaling`, `podDisruptionBudget`, `monitoring`, `networkPolicy`, `webhook`); a value left at its old root-level path fails the render with a message pointing at the new path. Flat `extraContext` keys are restructured into `diagnostics`/`statusPatches`/`annotationCompatibility`/`tls` trees — the routing diagnostic response headers (formerly `debug`, on by default) are now opt-in via `diagnostics.routingHeaders.enabled`, and `controller.statusPatches.enabled` moved to `extraContext.statusPatches.enabled`.
- **BREAKING**: chart values now have one owner per runtime setting. Rename `controller.crdName` to `controller.configName`; `controller.debugPort` to `controller.ports.healthz`; `controller.config.dataplane.port` to `haproxy.ports.dataplane`; `controller.config.routing.regexMatchOrder` to `controller.config.templatingSettings.extraContext.routing.regexMatchOrder`; and `controller.defaultSSLCertificate` to top-level `defaultSSLCertificate`. Remove the no-op `controller.config.controller.healthzPort` and `metricsPort` values. `controller.ports.metrics` now configures the process listener as well as its pod and Service port. Legacy paths fail with an explicit migration error instead of being ignored or drifting.
- **BREAKING**: `haproxy.enterprise.version` was removed. `haproxyVersion` now selects the controller compatibility series, Enterprise image revision, and derived binary path together. An empty `haproxy.image.repository` derives the community or Enterprise registry from `haproxy.enterprise.enabled`; Enterprise mode fails clearly when the selected series has no tested revision pin.
- The unreleased shared-cache and rate-limit values were realigned: Varnish deployment settings live under `cache.varnish`, HAProxy cache balancing under `cache.haproxy`, shared limiting under `rateLimit.shared`, and the bundled Valkey topology under `rateLimit.shared.managedStore`. Varnish and Valkey image pull policies are configurable.
- `spoaHub.plugins.<name>.enabled` template strings must now resolve to exactly `true` or `false`; any other resolved string, or a non-boolean value, fails the render instead of being silently coerced to disabled.
- **BREAKING**: The vendor annotation libraries (`haproxytech`, `haproxyIngress`, `nginxIngress`) are now **disabled by default** — the native `haproxy-haptic.org/*` library is the only annotation library on by default. Operators who use `haproxy.org/*`, `haproxy-ingress.github.io/*`, or `nginx.ingress.kubernetes.io/*` annotations must now explicitly enable the matching library (`--set controller.templateLibraries.<haproxytech|haproxyIngress|nginxIngress>.enabled=true`). The native vocabulary is a superset of all three, so configs written from scratch need no vendor library, and prefixes from different families can coexist on the same Ingress as long as each *feature* is configured through a single family (see the cross-family guard below).
- Ingress is now served over HTTPS by default: any Ingress binds the chart's https port (`haproxy.ports.https`, default `443`) and terminates TLS with the default certificate — no `spec.tls` required (previously the https port stayed closed until a resource requested TLS). A `spec.tls` entry still layers a host-specific certificate on top. Set `extraContext.ingressDefaultHTTPS: false` to keep Ingress plaintext-only, or disable the default certificate (`defaultSSLCertificate.enabled=false`) for HTTP-only mode.
- HAProxy `nbthread` is now derived from the CPU *limit*, not the CPU *request*. With no CPU limit (the default), the directive is omitted so HAProxy auto-detects all node cores from its CPU affinity — using every core on a static on-prem node without raising CPU requests (which only reserve node CPU from other pods). When `haproxy.resources.limits.cpu` is set, the chart renders `nbthread = ceil(limit)` so threads match the CFS quota. Previously `nbthread = ceil(cpu_request)`, which pinned the default 250m-request pod to a single thread and could only be widened by inflating the request. Set `haproxy.nbthread` to pin an explicit value.
- The bundled SPOA hub was updated to v0.9.0. It processes pipelined SPOE NOTIFY frames concurrently instead of one-at-a-time per connection, and bounds total in-flight frames to the sidecar's usable CPU cores with a process-wide backpressure gate — when the gate is full, HAProxy is backpressured (the excess queues in HAProxy's buffers) instead of the hub shedding 503s under saturation on a capacity-limited box. This makes the adaptive-concurrency default fully effective and removes the fixed-cap 503 cliff under load bursts (homelab-verified 0% 503 across a c=16→96 heavy-POST WAF saturation sweep). The hub also cuts per-frame dispatch allocation (~15% less overhead on WAF-sized request bodies). New hub metrics: `spoa_inflight_frames`, `spoa_inflight_gate_capacity`, `spoa_backpressure_waits_total`.
- Request mirroring no longer allocates a per-target SPOE message slot. The mirror plugin now uses a single static `mirror` message + `mirror-group`; each mirror source (Gateway `RequestMirror` filter, `mirror-target` Ingress annotation) appends its target to a per-request list (`txn.gw_mirror_targets`) that the message ships to the plugin, and the plugin fans out to every entry. Adding or removing a mirror target now changes only the HAProxy frontend — never `spoe.conf` or the hub TOML — so it no longer triggers a SPOA-hub config reload, and there is no cap or `fail()` on the number of mirror targets. Removed the `spoaHub.haproxy.mirror.minMessageSlots` value (the slots it floored no longer exist). Requires the bundled SPOA-hub image with mirror plugin v0.6.0+.

#### Fixed

- The chart no longer deploys the shared rate-limit store when the shared limiter is off. `rateLimit.shared.managedStore.enabled` defaults to `true` while `rateLimit.shared.enabled` defaults to `false`, and the store's render gate consulted only the former — so **a default install** rendered a 3-replica Valkey StatefulSet, a PodDisruptionBudget and two Services that nothing consumed. Worse, `templates/role.yaml` grants `apps/statefulsets` and `policy/poddisruptionbudgets` only when *both* flags are set, so the controller had no permission to apply what it had rendered: it retried the forbidden Server-Side Apply on every reconciliation, logging at `ERROR` roughly 9.5 times a second indefinitely (704 failures in 74 seconds on a real cluster), with no backoff, no metric and no status condition. Enabling the Varnish cache tier only partially masked it — that grants `apps` through an or-combined rule, leaving the PodDisruptionBudget still failing. The store's gate now requires both flags, matching the RBAC gate. On upgrade, orphan cleanup deletes the leftover Services (and the StatefulSet and PodDisruptionBudget where a Varnish-enabled install managed to create them); nothing consumed them, since the plugin's `store_url`, the NetworkPolicy and the plugin itself already required the shared limiter to be on. `scripts/test-helm-defaults.sh` now fails (exit 11) if the controller logs any failure to apply a rendered `k8sResources` entry, which is what makes this class of chart-RBAC gap visible in CI at all.
- A single mirrored route no longer breaks every gRPC route on the same frontend. An HTTPRoute with a `RequestMirror` filter, or an Ingress with `haproxy-haptic.org/mirror-target` / `nginx.ingress.kubernetes.io/mirror-target`, emitted a frontend-wide `option http-buffer-request` so the mirror plugin would see `req.body` — but that frontend is shared with every other route, including GRPCRoutes. Buffering deadlocks a gRPC stream: the client waits for a response HAProxy hasn't forwarded yet, so the backend never sees the call, and the stream dies with a `408` after `timeout http-request` with `<NOSRV>` in the log. All three sites now emit a `Content-Length`-gated `http-request wait-for-body` instead, which no streaming request can match, and consult the same per-backend override map as the base rule so a route's `haproxy-haptic.org/request-buffering: off` is not silently defeated by an unrelated mirrored route on the same frontend. A chunked request body (no `Content-Length`) is no longer mirrored, and neither is the body of a mirrored route that opts out of buffering.
- A body-inspecting WAF policy on an Ingress that declares a gRPC backend is now rejected at admission instead of failing at runtime. Coraza buffers a complete body and ships no protobuf processor, so a gRPC stream can never satisfy a `requestBody.mode` of `any`/`json`: client-streaming and bidirectional calls time out with `408` while unary calls keep working, which hides the breakage until someone opens a stream. The check keys on the unambiguous gRPC declarations (`haproxy-haptic.org/backend-protocol: grpc`/`grpcs`, nginx-compat `GRPC`/`GRPCS`) — plain `h2` backends are equally often bounded REST and are left alone. A route that already carries the combination records a `Warning` Event (`WafBodyPolicyOnGRPCRoute`) and keeps serving rather than being taken down, since the runtime already refuses the uninspectable calls.
- WAF detect (shadow) mode no longer blocks gRPC streaming. A policy with a body-inspecting `requestBody.mode` waited for a complete body regardless of enforcement mode, but a streaming request declares no `Content-Length` and keeps its body open until the peer is done — so the wait ran to `policies.requestBody.waitTimeout` and HAProxy answered `408` with the backend never contacted, on a mode documented as observing without blocking live traffic. Detect mode now waits only for a body whose length is declared and leaves an unbounded one uninspected, matching how every other body-contract rule already degrades in detect. A declared body is still buffered in detect, so shadow verdicts stay faithful. Enforce mode is unchanged and still refuses a body it cannot bound; the resulting `408` on a streaming route is fail-closed by design and is now documented.
- Forcing `spoaHub.enabled=true` while every plugin under `spoaHub.plugins.*` stays disabled is now rejected at render time instead of installing a broken combination. That state deployed the SPOA hub sidecar and its bootstrap `spoa-hub-config.toml`, but left the template library dormant (no plugin means no SPOE message, and HAProxy rejects an `spoe-agent` without one), so the library rendered no runtime TOML — and the controller's general-file sync then orphan-deleted the sidecar's config out from under the running hub. It also auto-wired a `spoa-hub` pluggable-validator entry pointing at a file no render produced. The error names the two ways out: enable a plugin, or leave `spoaHub.enabled` unset so a plugin turns the sidecar on.

- The API-gateway request-schema scan (`util-820-api-gateway-schemas`) now serialises through `shared.ComputeIfAbsent`, matching the WAF `util-*-coraza-scan` snippets. It mutates the shared `globalFeatures` map in place, and its two callers — `request-schema.map` and the SPOA hub's runtime TOML — were kept apart only by render ordering that nothing documented or enforced; had both gone cold in the same render they would have written the map concurrently from the parallel auxiliary-file errgroup, which Go turns into a process-killing `fatal error: concurrent map writes`. No behaviour change.

- Creating a Gateway can no longer move an existing Gateway's per-pod listener port. Same-slot hash collisions were resolved in key order, so an arriving Gateway whose key sorted first evicted the incumbent — and the incumbent's vacated port was taken over by the newcomer's `bind` in the same render. Any client still addressing the old pod port (an established keep-alive connection pinned by conntrack, or a port-forward that resolved `targetPort` earlier) was then silently scoped to a *different* Gateway's routes: a 404 through `default_backend`, or a match against that Gateway's catch-all, which crosses tenants. Slots are now handed out oldest-first (ascending Gateway `creationTimestamp`, key as tie-break), so a Gateway's port depends only on its own key and the keys of older Gateways. Deleting the older member of a collision pair can still let the younger move down, but that vacates a port instead of handing it over, so stale clients get a clean connection refusal and reconnect.

- Gateway API traffic now reports the correct owning resource. `base.yaml`'s owner-identity cascade read `var(req.gw_rule_id)` — a variable scope nothing ever writes — so the Gateway branch never fired and requests fell through to the backend-name split, yielding `txn.resource_id = "gtw/<namespace>"`. Every per-resource feature map is looked up with that value (WAF policy, external auth, shared rate limit, cache, request-schema validation), and the caching library's per-route comparisons and the WAF fail-closed deny compare against it directly. Now that Gateway routes resolve to `<namespace>/<name>`, an Ingress and an HTTPRoute that share a namespace/name also share that key — inherent to kind-less keying, and strictly better than matching on `gtw/<namespace>`.
- The coraza (WAF) and api-gateway SPOA plugins now default to `maxConcurrency: 16` instead of `2`. A cap of 2 with no queue fails **closed** under load bursts — the plugin admission gate rejects excess calls and HAProxy returns 503 — even though each check uses only ~10% of a CPU and the CPU sits mostly idle (measured on a homelab bench: 25–44% of requests 503'd, p99 latency to ~600ms, once offered concurrency exceeded 2). 16 gives burst headroom while still bounding hostile traffic. (`haproxy-spoa-hub` ADR-0002 covers an adaptive alternative that auto-sizes this.)
- Enabling the org-wide governance guardrails no longer breaks the daemon's config load gate. The daemon runs the bundled `validationTests` on every config load, and a global rule (e.g. "every Ingress must set a WAF policy") emitted `GovernanceViolation` events on the fixtures of unrelated synthetic tests — the tests that assert on events then failed, and the operator's whole config was rejected at the load gate. Governance is now pinned OFF in the `validationTests._global` baseline, so an operator's live governance can't leak into the bundled suite; the governance-specific tests re-enable it per-test. The template test script renders the full suite with governance enabled so the isolation can't silently regress.
- The `haproxy-haptic.org/cache-ttl` and `cache-max-object-size` annotations now reject a unit suffix at admission instead of silently disabling caching. A value like `cache-ttl: "60s"` previously passed validation (the integer check used `toint`, which parses `"60s"` to `0`) and was written verbatim into the cache-TTL map, where the Varnish VCL computed `std.duration("60s"+"s")` = a zero TTL — so the route never cached and nothing said why. Both annotations now require a bare integer (`"60"`, `"1048576"`) and fail loudly on a suffix.
- A reusable WAF policy carrying structured CRS tuning fields (`allowedMethods`, `paranoiaLevel`, `anomalyThreshold`) no longer fails the whole config render — and the daemon load gate — when it is defined in the catalog but selected by no route, or when coraza runs a CRS-less ruleset. The requirement that the coraza directives contain an `Include @owasp_crs` anchor (needed to splice the tuning SecActions before the rules) is now checked per-route at policy-application time and fails only that route closed, instead of at policy registration where an unused deployment-wide policy aborted every render.
- The structured CRS tuning fields (`allowedMethods`, `paranoiaLevel`, `anomalyThreshold`) were rejected at `helm template` time with "unknown field": the chart's Helm-level pre-validation of inline policies was never extended alongside the render-time validator, so values using the new fields could not deploy at all. The allowlists are synced, the Helm layer validates the new fields' shapes, and the template test script now renders the full inline-policy field surface so the two validation layers can't drift apart silently again.
- The bundled rate-limit SPOA plugin was updated to v0.2.0, making `burst` real in the default token-bucket (lease) mode: an empty local lease pool now escalates to one bounded, per-key-coalesced reservation against the authoritative store bucket before denying, so a browser page load fanning out tens of parallel requests is admitted within the configured burst instead of mass-429'd from a `rate x 200ms` local pool. Lease sizes adapt to observed demand (recurring bursts are pre-stocked locally), a flood costs the store at most one round-trip per sync interval, `fail_open` is now honored when the store is unreachable and the pool is empty (previously a drained pool with an open circuit breaker denied indefinitely), and the `x-ratelimit-remaining`/`reset` headers report the real budget instead of the local lease pool.
- WAF governance violations on existing Ingresses no longer wedge the cluster: previously, once any Ingress carried annotations a governance gate forbids (a `waf-mode` override without `allowEnforcementOverride`, or an `nginx.ingress.kubernetes.io/modsecurity-snippet` under `allowCustomRules=false` — the state every ingress-nginx migration starts in), every render aborted AND, because the webhook live-renders each admission, every config update and every Ingress fix was denied. Governance and per-route annotation violations now fail closed per-route instead — the violating route returns 503 with a Warning Event naming the missing grant, everything else keeps rendering — and hard-fail only the violating resource's own admission. A route rejected mid-registration also no longer overwrites another library's Coraza application, and a broken route with a dangling `waf-mode` fails closed instead of being served with the annotation ignored.
- Defining any inline WAF policy no longer makes the admission webhook deny every subsequent `HAProxyTemplateConfig` update: the baked unknown-policy validationTest asserted the exact available-policies list, but deployment-defined inline policies deep-merge into its pinned catalog and join that list. The assertion now tolerates deployment-defined policies alongside the pinned one.
- Defining a reusable WAF policy (which activates WAF governance) no longer fails the daemon load gate on the bundled validation tests. The `haptic-annotations` config-injection, custom-WAF-rule, and shared-rate-limit tests now declare their own `extraContext.waf.ingressPermissions`, so activating governance no longer forces an operator to loosen `allowRawHAProxyConfig`/`allowCustomRules`/`allowEnforcementOverride` cluster-wide just to keep the controller from crash-looping.
- Shared source-IP rate limits now run before Coraza and request-schema validation, so rejected floods do not consume expensive API-gateway processing; consumer-keyed quotas now run after native API-key/JWT authentication instead of silently falling back to source IP before the consumer identity existed.
- Admission timeout values are now configurable as `controller.webhook.timeoutSeconds` (watched resources, default `10`) and `controller.webhook.haproxyTemplateConfig.timeoutSeconds` (prospective config, default `30`); the chart validates Kubernetes' limit and derives one-second-shorter controller deadlines automatically.
- **Security:** API-key authentication and consumer-group authorization now fail closed with `503` while their referenced Secrets are absent from the controller watch cache. Previously each map producer skipped a missing Secret while its backend directive still referenced the unregistered map, rejecting an Ingress during Secret propagation races instead of admitting a fail-closed route.
- EndpointSlices that do not expose a Service's requested named target port are no longer rendered as HAProxy servers using the Service port; this prevents unrelated pods matched by a broad Service selector from receiving application traffic.
- The default HAProxy bootstrap configuration now applies the same configurable `extraContext.hardStopAfter` drain bound as the controller-rendered configuration, so the initial worker cannot remain stuck after the first reload.
- The bundled SPOA hub was updated to v0.7.4 so removing Coraza or another native plugin during a config reload no longer crashes the sidecar with SIGSEGV / exit 139 during `dlclose`; retired plugin instances are still drained and destroyed, while native library mappings remain safe for the process lifetime.
- Generated HAProxy configurations no longer emit `haproxy -c` warnings from proxy-mode mismatches or unsupported TLS settings: TCP frontends explicitly use `tcplog`, `forwardfor` is scoped to HTTP traffic frontends, the quiet status endpoint retains a log target with normal logs suppressed, and the AWS-LC-incompatible `tune.ssl.default-dh-param` default was removed.
- **Security:** external-auth response headers (`nginx.ingress.kubernetes.io/auth-response-headers`, `haproxy-ingress.github.io/auth-headers-succeed`, and the oauth2-proxy desugaring) are now stripped from the inbound request on auth-protected routes before the auth plugin's value is set. Previously the `set-header` was skipped when the auth reply omitted a listed header, so a client-supplied copy (e.g. `X-Auth-Groups: admin`) survived to the backend on an otherwise-successful auth — an identity/privilege-escalation vector on backends that trust those headers. Now a `del-header` precedes each `set-header`, matching ingress-nginx's always-overwrite semantics. An Ingress that combines `haproxy-ingress.github.io/auth-url` with `ssl-passthrough` also gets an `AuthIgnored` `Warning` event, since external auth can't run on undecrypted L4 traffic.
- `nginx.ingress.kubernetes.io/proxy-ssl-secret` client certificates now deploy under the correct path — the rendered `crt` value is the bare filename (resolved against HAProxy's `crt-base`) instead of a `ssl/`-prefixed path that doubled to `ssl/ssl/<name>` and made HAProxy reject the config (`unable to stat SSL certificate`), denying the Ingress at admission. Only affected upstream mTLS via this annotation.
- When two Ingresses claim the same host, path, and path type, the route is now resolved deterministically to the older Ingress (by `creationTimestamp`, tiebroken by namespace/name) instead of the previous arbitrary render-order winner — matching ingress-nginx's oldest-wins, so an Ingress that was there first is never hijacked by a later conflicting one. `Prefix` and `ImplementationSpecific` share a routing slot and resolve together; `Exact` is separate. An nginx canary Ingress no longer competes for its main's base route — the main Ingress owns the route and the canary only overlays its traffic split (previously the canary could win the base map by render order, sending non-canary traffic to the canary backend). The Ingress that loses a route now gets a `RouteConflict` `Warning` Event naming the winner, so the dropped route is visible via `kubectl describe ingress`.

- Installing without cert-manager now works out of the box: when cert-manager provisioning is enabled (the default) but its API is absent, the chart generates a self-signed `default-ssl-cert` Secret (10-year validity) instead of silently skipping the `Certificate` — previously the controller failed every render (`TLS Secret not found`) and the HAProxy pods never became ready. A Secret that already exists (external-secrets, manual) is left untouched, the generated one survives upgrades, and manual mode (`certManager.enabled=false`) keeps its provide-your-own contract (#78).
- The `nginx.ingress.kubernetes.io/enable-cors` and `haproxy-ingress.github.io/cors-enable` annotations now answer the CORS preflight (OPTIONS) request in HAProxy with a synthetic 204 carrying the `Access-Control-*` headers, matching ingress-nginx — previously the preflight was forwarded to the backend, which then had to handle OPTIONS itself. Both annotations are now marked `supported` in the migration coverage.
- The `haproxy.org/cors-*` annotations now mirror the upstream HAProxy Kubernetes Ingress Controller: a non-wildcard `cors-allow-origin` is treated as a regex matched against the request Origin and the `Access-Control-Allow-Origin` header echoes the matched origin (previously the value was emitted verbatim, so a regex or multi-origin allow-list produced an invalid header). CORS headers are now added via `http-after-response` (so they also apply to the preflight response), and the `cors-allow-methods` / `cors-allow-headers` / `cors-max-age` defaults now track upstream (`*` / `*` / `5s`).
- The `nginx.ingress.kubernetes.io/cors-allow-origin` and `haproxy-ingress.github.io/cors-allow-origin` annotations now accept a comma-separated allow-list with single-level `*.` subdomain wildcards, match it against the request `Origin`, and echo the matched origin back (adding `Vary: Origin` for non-wildcard lists) — matching ingress-nginx. Previously the annotation value was emitted verbatim as the `Access-Control-Allow-Origin` header, so a multi-origin list or a wildcard produced an invalid header. A malformed origin now fails the render.
- `haproxy-ingress.github.io/auth-secret` now also parses an `auth`-key htpasswd Secret (haproxy-ingress's and ingress-nginx's native format — one `user:hash` line each, `user::plain` for insecure), so a Secret migrated from those controllers authenticates. The previous base64-hash-per-username Secret shape still works.
- `haproxy.org/auth-realm` now normalizes spaces to dashes (matching the upstream HAProxy Kubernetes Ingress Controller) instead of failing the render, and its default realm is now `Protected-Content` (was `RestrictedArea`). The `sanitize_auth_realm` toggle is removed (normalization is unconditional).
- The Gateway API template library no longer requires the Ingress library. Its shared hostname-to-map-key helper (`MapKeyForHost`) moved into the always-loaded base library (renamed `util-ingress-host-key` → `util-host-key`), so `controller.templateLibraries.gateway` can be enabled with `ingress` disabled without a template-compilation error.

### Added

- Support for every Gateway API release, adapted at runtime: `watchedResources` entries accept an ordered `apiVersions` candidate list and an `optional` flag, `templateSnippets`/`validationTests` accept `requires`/`requiresFields` (features whose resources or schema fields aren't served are stripped at config load), and a CRD watch reinitializes the controller when a watched CRD is installed, upgraded, or removed — no Helm operation or pod restart needed. Resolved versions are exposed via `resources.<name>.APIVersion()` and `/debug/vars/effectiveConfigResolution`; `controller validate` resolves the same way against `--schema-dir`. A required resource with no served version fails startup with a clear error instead of hanging.
- The config's embedded `validationTests` are now enforced at every gate: the admission webhook denies a failing `HAProxyTemplateConfig` at `kubectl apply`, and the controller rejects a failing config at startup and on every change — the last-good config keeps serving, and failing test names surface on `status.validationErrors`. Previously only the `controller validate` CLI ran them.
- Kubernetes Events on the `HAProxyTemplateConfig`: a `Warning`/`ValidationFailed` Event when a config change fails validation and a `Normal`/`Validated` Event on recovery, so failures surface in `kubectl describe` and `kubectl get events`.
- HAProxy 3.4 support: the controller is built, validated, and released for HAProxy 3.4.
- Typed watched resources: chart templates access watched resources through compile-time typed top-level globals (e.g. `gateways`, `httproutes`), type-checked at controller startup against schemas from the live apiserver or `--schema-dir`. See [ADR-0010](./docs/adr/0010-typed-watched-resources.md).
- `spec.k8sResources` declares full Kubernetes resources reconciled via Server-Side Apply, owned by the `HAProxyTemplateConfig` CR (garbage-collected on uninstall); a partial-ownership mode (`haproxy-haptic.org/ownership: partial`) lets chart-owned and haptic-owned entries coexist on one resource.
- `spec.validators` declares pluggable validator sidecars consulted by the admission webhook (per-entry socket, file-glob routing, timeout); `/healthz` reports each socket's reachability.
- The admission webhook hot-reloads its TLS certificate from the mounted Secret, so a cert-manager renewal is served within about a minute without a controller restart. The `--webhook-cert-secret-name` flag is replaced by `--webhook-cert-dir` (env `WEBHOOK_CERT_DIR`).
- Gateway API `RequestMirror` filters, including multiple and percentage/fraction mirrors, backed by the bundled mirror SPOA plugin.
- Ingress `spec.defaultBackend` support, both rules-less (catch-all) and combined with `spec.rules`.
- HAProxy responses now carry a `Server: haptic` header.
- New metrics: `haptic_haproxy_reloads_total` (the canonical reload/SLO signal), `haptic_dataplane_api_operations_total`, runtime fast-path counters (`haptic_runtime_fast_path_*`), and per-plugin SPOA metrics via the hub's `/metrics` endpoint.
- `spec.dataplane.configPublishInterval`, `reloadVerificationTimeout`, and `syncTimeout` are now tunable; `spec.watchedResources.<name>.debounceInterval` adds a per-resource batching override.
- New `spoa-hub` container image bundling the SPOE hub plus seven plugin libraries (mirror, coraza, external-auth, fingerprinting, maxmind, otel, sso-auth), Cosign-signed with a CycloneDX SBOM.
- External authentication (`auth-url`-style annotations) wired end to end via the spoa-hub external-auth plugin.

### Changed

- Leader-election timing defaults raised from 15s/10s/2s to 30s/20s/5s (`leaseDuration`/`renewDeadline`/`retryPeriod`): more headroom against apiserver or CPU-starvation stalls, at the cost of slower crash-failover (up to ~35s; voluntary handoffs still release the lease immediately). Tune via `spec.controller.leaderElection` (#57).
- Config validation now runs asynchronously with latest-wins coalescing: rapid successive `HAProxyTemplateConfig` edits validate only the newest change, and an in-flight validation no longer blocks config processing or leaves a new leader without a config (#55).
- `store: on-demand` watched resources keep far less memory resident: the informer cache strips object bodies down to index and identity fields; templates still read the full object, fetched live on access. See [ADR-0012](./docs/adr/0012-on-demand-projection-and-access-gated-reconcile.md).
- All log output now shares one structured logfmt format (client-go and other third-party lines included), and routine per-request/per-reconcile success lines moved from INFO to DEBUG — failures, denials, config changes, and leadership transitions stay at INFO. Set `LOG_LEVEL=DEBUG` for the previous verbosity.
- Runtime-eligible server changes (pod-IP rotation, port, admin state) now reach the live HAProxy workers in milliseconds via a runtime fast path instead of waiting for the next scheduled deploy; structural changes still take the rate-limited reload path. See [ADR-0011](./docs/adr/0011-no-haproxy-server-state-file.md). The reconciler-level debounce was removed — batching is per-watcher via `spec.watchedResources.<name>.debounceInterval` (default raised from 100ms to 2s; `"0"` fires on every change).
- Content-only changes now apply to the live HAProxy workers via the runtime API without a reload: map files, TLS certificates (HAProxy 3.2+), SSL CA files (HAProxy 3.2+, e.g. frequent trust-bundle rotation), and frontend `maxconn`. Adding or removing files and all other structural changes still reload, and a failed runtime apply falls back to a reload, so the result always converges.
- `controller validate` now requires `--schema-dir` (or `HAPTIC_SCHEMA_DIR`) for typed-access templates; the embedded Gateway schema fallback was removed. Production (live apiserver) is unaffected.

### Fixed

- Fixed controller crash-loop and Gateway status-apply failures on clusters running older Gateway API releases (v1.1–v1.5) whose schemas lack fields the bundled chart exercises (#59).
- A replica that loses the leader-election lease now reinitializes and re-enters the election loop instead of running as a permanent follower — on single-replica deployments, a missed lease renewal could previously stall deployments until a pod restart (#57).
- Runtime map updates are now verified by read-back and fall back to a reload when the live map did not converge — a map write acknowledged but lost by HAProxy could previously latch stale routing until an unrelated reload (#48).
- Eliminated intermittent 503s during rolling restarts of single-replica backends: a newly-Ready pod's endpoint change reaches the live workers within `option redispatch`'s rescue window even when it coincides with an in-flight structural deploy, runtime applies retry across a concurrent reload, and deleting an unreferenced certificate no longer schedules a stray second reload that briefly blacked out the runtime socket (#67).
- Reloads are bounded to one per `minDeploymentInterval` under concurrent churn, and auxiliary-file updates batch into the main config sync's single reload instead of triggering separate DataPlane API auto-reloads.
- Resource status no longer goes stale: statuses are written even when a change produces no config diff (a Gateway with no attached routes no longer sticks at `Programmed=Unknown`), and sustained event bursts no longer drop status or deployment events.
- `HAProxyCfg.status.deployedToPods` now reflects reality: a failed deploy keeps the pod's last successfully-deployed checksum plus a `lastError` instead of reading as converged, failed deployments are retried on the next reconcile instead of waiting for the drift timer, and a startup race no longer leaves a deployed pod unreported.
- Cross-pod config drift is now detected and repaired: the deployer tracks each pod's actual post-sync state, and a render race no longer leaves a newer render undeployed.
- Credentials-Secret rotation now takes effect immediately, and content updates to watched Secrets/ConfigMaps are no longer dropped.
- gRPC: requests hitting the default backend get a proper trailers-only `grpc-status: 12` response instead of a connection-breaking 404, GRPCRoute method matching works on TLS + ALPN h2 and plaintext h2c, and gRPC over h2c multiplexes with HTTP/1.1 on the same bind.
- Gateway TLS listeners on non-default ports now bind correctly.
- The renderer fails fast when the config references a map file it didn't register (previously the file was deleted as unreferenced, breaking every subsequent reload), and each render sees one consistent snapshot of the watched-resource stores.
- `store: on-demand` resources no longer trigger a full list or one API fetch per resource on per-key reads, drift cycles, and the `/debug/vars` endpoints.
- Ingress `pathType: Exact` now preserves trailing slashes (`/foo/` no longer matches `/foo`).
- `controller validate` renders with the same context as production (`capabilities`, `extraContext` promotion), so a template can no longer pass validation yet render differently in production.
- HAProxy 3.3 configs are now validated against the v3.3 DataPlane API schema (was v3.2), and DataPlane API versions newer than the newest bundled client clamp down to it instead of falling back to the oldest v3.0 client.
- Watched-resource admission (e.g. Ingress) now gets the same ~9s internal validation deadline as `HAProxyTemplateConfig` admission (was 5s), so large-config dry-runs aren't prematurely admitted without validation.
- Status patches, admission overlays, and owned-resource applies resolve a resource's plural via the cluster RESTMapper, so a CRD with an irregular plural no longer targets a nonexistent GroupVersionResource.
- Hardened component lifecycle: re-acquired leadership no longer stacks orphaned event subscriptions (previously endless "critical drops" log spam), event-loop panics recover instead of silently killing the loop, and the controller no longer schedules a spurious iteration restart right after startup.
- HTTP content stores no longer misclassify an empty `200 OK` as `304 Not Modified` (stale content), SSL-certificate Secret publishing retries on write conflicts, and backends whose only change is on the `default-server` line now update instead of staying stale.
- HAProxy file paths in rendered configs use slash-only semantics regardless of host OS, fixing the controller binary on Windows (no-op on Linux).
- Bundled SPOA hub updated to v0.7.3: config reloads quiesce in-flight SPOE dispatches before retiring the old plugin set, fixing lost mirror/OTLP work around reloads (#47); unhandled SPOE messages surface via a WARN log and `spoa_messages_unhandled_total`.

### Removed

- The dormant webhook-cert-rotation pipeline and its `haptic_webhook_cert_expiry_timestamp_seconds` / `haptic_webhook_cert_rotations_total` metrics (it never rotated certs) — replaced by the webhook-cert hot-reload above.
- `namespaceSelector` on `watchedResources` entries (was never wired up). Scope via `labelSelector` or separate controller instances.
- Management of HAProxy `program` sections — HAProxy removed the section in 3.3 and `client-native` dropped the model. Rendered configs may still contain `program` sections on older HAProxy versions, but the controller no longer parses, diffs, or normalizes them.

- **Configurable deployment timeout**: `deploymentTimeout` in dataplane config (default: 30s) to recover from stuck deployments
- **Server slot preservation**: Preserve HAProxy server slots during rolling deployments to enable zero-reload runtime API updates via `currentConfig` template context
- **HAProxy Ingress annotation compatibility**: 56 `haproxy-ingress.github.io/*` annotations via the haproxy-ingress template library
- **Dataplane API concurrency limiting**: `maxParallel` config option to limit concurrent API operations, preventing timeouts for large configurations
- **CRD content compression**: HAProxyCfg content compressed with zstd when exceeding `configPublishing.compressionThreshold` (default 1 MiB), reducing etcd storage
- **HAProxyGeneralFile CRD**: Publish general files (error pages, etc.) as Kubernetes custom resources with compression support
- **HAProxyCRTListFile CRD**: Publish crt-list files as Kubernetes custom resources with compression support
- **`semver_gte` template filter**: Version comparison for gating features on HAProxy version (e.g., `semver_gte(haproxyVersion, "3.3")`)
- **Template-driven status patches**: Templates can register status patches for any Kubernetes resource via `statusPatch()` function, with outcome-keyed variants (`rendered`, `deployed`, `renderFailed`, `deployFailed`) applied automatically based on pipeline phase
- **Backend diff field diagnostics**: Reconciliation log now includes which BackendBase fields caused backend updates, aiding diagnosis of false diffs from parser round-trip asymmetries
- **Status patch helper functions**: `condition()`, `transitionTime()`, and `toJSON()` template functions for building Kubernetes status conditions with stable transition timestamps

### Changed

- **Reconciliation triggering**: Leading-edge triggering with a 5s refractory period; no latency for isolated changes, bursts during that window are batched into a single reconciliation
- **Parallel Dataplane API operations**: Operations execute in parallel within each priority group, reducing sync time for large configurations
- **Balance directive**: `balance roundrobin` moved to `defaults` section to prevent silent behavior change when upgrading to HAProxy 3.3 (which changed the default balance algorithm from `roundrobin` to `random`)
- **Go runtime 1.26.1**: Green Tea GC replaces manual GOGC tuning

### Helm chart

#### Added

- Initial Helm chart deploying the controller and HAProxy pods (2 replicas by default)
- Separate controller Service (ClusterIP for operational endpoints) and HAProxy Service (configurable LoadBalancer/ClusterIP)
- Default NetworkPolicy for HAProxy instances
- Leader election support with configurable replica count
- Default SSL certificate configuration via `controller.defaultSSLCertificate`
- Modular template library system with composable libraries merged at Helm render time (enable/disable via `controller.templateLibraries.<name>.enabled`):
    - `base.yaml`: Core HAProxy template structure with extension points
    - `ingress.yaml`: Kubernetes Ingress support (path types: Exact, Prefix, ImplementationSpecific; TLS termination; default backend)
    - `gateway.yaml`: Gateway API support — HTTPRoute and GRPCRoute are watched and routed; traffic splitting, request/response header modification, URL rewrites, and Gateway/Route status patches are emitted. TLS/TCP/UDP listeners are reflected in each Gateway's `supportedKinds` status but TLSRoute/TCPRoute/UDPRoute resources are not watched or routed
    - `haproxytech.yaml`: `haproxy.org/*` annotation compatibility (backend config snippets, SSL passthrough, CORS, basic auth)
    - `ssl.yaml`: TLS/SSL features
    - `haproxy-ingress.yaml`: 56 `haproxy-ingress.github.io/*` annotation compatibility (enabled by default)
- Gateway API status reporting: Gateway conditions (Accepted, Programmed), listener status, HTTPRoute/GRPCRoute parent status with Accepted and ResolvedRefs conditions
- Ingress status reporting: LoadBalancer addresses propagated to Ingress `.status.loadBalancer`
- HAProxy built-in Prometheus exporter enabled by default on the status frontend (`/metrics` on port 8404)
- Grafana dashboard annotations for leader transitions and controller pod starts
- Auto-generated Dataplane API credentials stored in a Secret (deterministic 32-char SHA256 of release-name + namespace; preserved across upgrades from the existing Secret)
- `haproxy.sysctls` for setting kernel parameters on HAProxy pods via pod-level securityContext
- `haproxy.podAnnotations` for custom pod annotations on HAProxy pods (supports Helm template expressions)
- `haproxy.shareProcessNamespace` to enable process namespace sharing between containers (required for signal-based sidecar reload, e.g., SPIFFE/SPIRE mTLS agents)
- `haproxy.shmStats.enabled` to persist stats counters across HAProxy reloads via shared memory (requires HAProxy 3.3+); automatically provisions `/dev/shm` emptyDir volume with auto-calculated size
- `haproxy.nbthread` to control HAProxy thread count (auto-calculated from CPU requests by default)
- `haproxy.dataplane.validateConfig` to control server-side config validation
- `haproxy.dataplane.debugSocketPath` to enable Unix socket for runtime profiling of the Dataplane API sidecar
- `controller.config.dataplane.maxParallel` to limit concurrent Dataplane API operations
- `controller.statusPatches.enabled` to disable status patch writes during migration from another ingress controller
- `extraDeploy` for deploying arbitrary Kubernetes resources alongside the chart (supports Helm templating)
- `extraEnv`, `haproxy.extraEnv`, `haproxy.dataplane.extraEnv` for custom environment variables on all containers
- `global-settings-*`, `defaults-settings-*`, and `frontend-extra-*` extension points for customizing HAProxy global/defaults sections and early frontend directives via template snippets
- `status-patches-*` and `status-extra-*` extension points for custom status and Prometheus endpoint configuration
- `template` post-processor type for declarative output transformations in `postProcessing`
- `guid` directives on all frontends, backends, and servers for stable object identification

#### Changed

- Dataplane API credentials consolidated into `credentials.dataplane` section; auto-generated if not provided
- Basic auth userlists are named `auth_<secretNs>_<secretName>` and deduplicated per Secret; each Ingress references its userlist via `http_auth()`. Differs from the official HAProxy Ingress Controller's per-Ingress `{namespace}-{ingressName}` naming so multiple Ingresses sharing the same Secret produce a single userlist (significant speedup for bcrypt hashes)
- Production-ready default resource requests and limits: controller (100m CPU / 512Mi memory), HAProxy (250m CPU / 1Gi memory), dataplane sidecar (50m CPU / 256Mi memory)
- `sidecars`, `extraVolumes`, `extraVolumeMounts` and their `haproxy.*` counterparts support Helm template expressions

#### Removed

- `image.appendHaproxyVersion` value (HAProxy version suffix is now always included in controller image tag)
- `haproxy.dataplane.credentials` section (use `credentials.dataplane` instead)
