# Changelog

All notable changes to the HAProxy Template Ingress Controller will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

For Helm chart changes, see [Chart CHANGELOG](./charts/haptic/CHANGELOG.md).

## [Unreleased]

### Added

- The admission webhook now hot-reloads its TLS certificate. The server reads `tls.crt`/`tls.key` from the mounted Secret directory per handshake (via a `GetCertificate` callback that re-parses on content change and keeps serving the last good cert through a torn write), so a cert-manager renewal is served within ~a minute without a controller restart. The controller flag `--webhook-cert-secret-name` (which fetched the cert Secret via the Kubernetes API) is replaced by `--webhook-cert-dir` (env `WEBHOOK_CERT_DIR`); the chart mounts the Secret at `/etc/webhook/certs` and sets the env automatically. The controller no longer reads the webhook cert Secret over the API.
- Runtime-eligible fast-path metrics: `haptic_runtime_fast_path_fires_total`, `haptic_runtime_fast_path_applies_total`, `haptic_runtime_fast_path_failures_total`, `haptic_runtime_fast_path_server_updates_total`. Fires counts every fast-path attempt (one per HAProxy pod per reconcile); Applies counts the subset that applied ≥1 runtime-eligible server update. Applies flat at 0 while Fires climbs means the fast path runs but the render diff carries no runtime-eligible server change (the deploy is keeping the pods current) — the signal that distinguishes "working but idle" from "broken".

### Removed

- Removed the dormant event-driven webhook-certificate-rotation pipeline: the `certloader` component, the `CertResourceChangedEvent` / `CertParsedEvent` events, the webhook-cert `SingleWatcher`, and the `haptic_webhook_cert_expiry_timestamp_seconds` metric. The bridge component was never wired into the controller, so this path never rotated certs at runtime. Real cert hot-rotation now exists — see Added.

### Changed

- Endpoint changes now propagate immediately while structural changes stay lenient. The reconciler-level refractory and the `spec.controller.reconciliationDebounceInterval` knob were **removed**: the Reconciler triggers reconciliation immediately on every watched-resource/HTTP change. Batching is solely per-watcher — `spec.watchedResources.<name>.debounceInterval` default raised from 100ms to **2s** (lenient for operator-initiated Ingress/Gateway/Service edits), with explicit `"0"` (the `DebounceImmediate` sentinel, which `WatcherConfig.SetDefaults` normalises to a true zero) firing on every change. The chart sets `"0"` on EndpointSlice (`libraries/ingress.yaml` + `libraries/gateway/_index.yaml`) so a pod-IP rotation reaches the deployer's runtime-eligible fast path with no debounce delay; reload throttling remains the deployer's `minDeploymentInterval`.
- **`controller validate` now requires `--schema-dir` (or `HAPTIC_SCHEMA_DIR`) for typed access in templates.** Previously the controller binary embedded a hand-trimmed Gateway-API schema as a default fallback (`pkg/k8s/schemafetcher/builtin/`), so `controller validate` worked out of the box for the chart's bundled Gateway path. That parallel offline schema source has been removed; the offline path now consults `--schema-dir` only. `scripts/test-templates.sh` auto-wires `--schema-dir=tests/schemas` (which carries the canonical bundle for the chart's libraries), so chart authors using the supplied script see no change. Operators running `controller validate` directly against a config with typed-access templates: pass `--schema-dir` pointing at a directory of CRD YAMLs (or bare OpenAPI v3 schemas with an `x-kubernetes-group-version-kind` extension); use this repo's `tests/schemas/` as the reference bundle. Configs without typed access continue to work without the flag — chart code reaching for a typed top-level global without a schema available fails at engine compile time with a clear pointer back to `--schema-dir`. Production (live API server) is unaffected. Rationale and alternatives in [ADR-0010](./docs/adr/0010-typed-watched-resources.md).

### Changed

- Dataplane orchestrator no longer opens a transaction for mixed runtime+structural diffs (or pure structural diffs). The previous fine-grained path issued one HTTP call per structural op (5–17 ms each, sequential inside a transaction), then committed with `force_reload=true` — empirically ~636 ms of dataplane time per mixed deploy in CI traces. New path: any runtime-eligible server updates (weight, address, port, maintenance, agent-*, health_check_port) apply first via the Runtime API so the live worker's in-memory state is current before any drain window, then the rendered config is shipped via a single `POST /configuration/raw?force_reload=true` — ~165 ms for the structural side, ~225 ms total per deploy. Atomicity is preserved (raw push is itself all-or-nothing); the rendered config has the same desired values baked in, so the new worker spawned by the reload inherits the runtime-applied state. Transient Runtime-API failures no longer fail the sync: the raw push runs anyway and converges via reload. A `Sync()` whose diff is purely runtime-eligible (no structural op) skips the reload via `applyRuntimeOnly` — a single `skip_reload` push carrying the `X-Runtime-Actions`.
- Runtime-eligible server changes (e.g. a pod-IP rotation during a rolling restart — a server's IP address, port, or admin state) now reach the live HAProxy workers in ~ms instead of waiting on the O(config size) scheduled deploy, via a two-lane serialized deploy model. Each render is classified by diffing it against the last-dispatched config: a diff that is purely runtime-eligible server fields takes the **runtime-raw** lane (a single `skip_reload`+`skip_version` raw push of the desired config body carrying the render diff's `set server` actions — no reload, applied immediately, IGNORING the deployment interval); any structural op takes the **structural** lane (full raw push + reload, rate-limited by the deployment interval, latest-wins, ≤1 enqueued). The runtime-raw lane dispatch and the pre-interval apply of a structural render's runtime subset run with no reload of their own in flight; a runtime apply that overlaps an in-flight structural deploy's reload survives it via retry-across-reload onto the post-reload worker (see Fixed), so it need not be serialized behind the reload. The render diff is computed once per render (render-vs-render, identical for every pod) and shared across pods; per-pod dataplane clients are persistent (keep-alive connection reused) and evicted when a pod disappears. Best-effort, with the scheduled deploy as the correctness floor; the change persists across any later reload because the deploy re-renders current endpoints (config-driven, no server-state-file — ADR-0011).

### Added

- Operator docs on typed resource access: see [Typed Resource Access](./docs/controller/docs/templating.md#typed-resource-access) in the templating reference + the brief note in [Watching Resources](./docs/controller/docs/watching-resources.md#typed-access-in-templates). The chart-side dev context (`charts/CLAUDE.md`) and [ADR-0010](./docs/adr/0010-typed-watched-resources.md) record the design rationale, alternatives considered, and the field-name convention.

- Rolling-restart endpoint changes now also converge in ~ms when a newly-Ready pod's render arrives while the deploy loop is sleeping out `minDeploymentInterval` *after* an unrelated tenant's structural deploy completed — closing the last residual `TestIngressRollingRestartZeroDowntime` 503 (a ~1-in-4-per-run flake, more frequent on slower HAProxy builds such as the 3.0 image, that a 5-round retry-stress across all HAProxy versions surfaced after a single green run looked clean). Once a structural deploy completes, the dispatch baseline has advanced to it, so a newly-Ready pod's render diffs *purely* runtime-eligible and classifies runtime-raw. The two deploy-loop wait points applied a pending's runtime subset asymmetrically: the in-flight (`awaitCompletion`) apply was lane-independent, but the interval-sleep (`waitDeployInterval`) apply was gated to the structural lane — so a runtime-raw render arriving during the post-completion interval sleep was skipped, and the new pod's `set server` only reached HAProxy when the interval elapsed (~1.4 s late), by which time the dying old slot had exhausted `option redispatch` (`SC--` 503, `dur≈405 ms`). Both wait points now share one lane-independent `applyRuntimeSubset` (gated only on a non-empty runtime server subset), so a runtime-raw render is fast-applied immediately at either wait point. Pinned by `TestSchedulerLanes_Case10_RuntimeRawDuringStructuralInterval_AppliesImmediately` (times out without the fix).
- Rolling-restart endpoint changes now reach the live HAProxy workers in ~ms even while an UNRELATED tenant's structural deploy is mid-execution, closing the residual `TestIngressRollingRestartZeroDowntime` 503. The single deploy loop blocks in `awaitCompletion` for the whole duration of an in-flight structural deploy (raw push + `force_reload` + verify + post-sync parse — ~1 s under cross-tenant churn); a pod that became Ready in that window had its reserved-slot address (`set server`) queued behind the entire deploy, long enough for the dying old pod to be the only server in rotation → `SC--` 503. `awaitCompletion` now interleaves: when a newer render arrives mid-deploy it applies that render's runtime-eligible server subset to the live workers immediately via a PARTIAL runtime apply (no CR/status publish — the in-flight structural deploy still owns completion). The concurrent `set server` survives the deploy's reload via the existing retry-across-reload (re-lands on the post-reload worker), and the deploy re-renders the body with the new address (config-driven; no server-state-file — ADR-0011). The earlier interval-gated and `wait <= 0` pre-interval applies (below) covered a render WAITING out the deploy interval; this covers a structural deploy actively EXECUTING. Pinned by `TestSchedulerLanes_Case2_RuntimeSubsetAppliesDuringInFlightStructural` (fails without the interleave) plus a concurrent completion/pending race guard.
- Rolling-restart endpoint changes coalesced with another tenant's structural change now reach the live HAProxy workers in ~ms even when the structural deploy is NOT interval-gated, closing the last residual `TestIngressRollingRestartZeroDowntime` 503. The deploy loop applies a structural render's runtime-eligible server subset up front (a `skip_reload` `set server` push, no reload) so a freshly-Ready pod's slot is current before the immediately-following reload's worker swap. That apply ran only on the interval-gated (`wait > 0`) path — guarded behind the `wait <= 0` early-return — so when the last structural deploy had ended longer ago than `minDeploymentInterval` (the common case: the interval rarely actually fires), the subset was never fast-applied and the pod-IP swap rode the reload's worker-swap window instead, leaving the slot bound to the just-vacated address long enough to burn `option redispatch`'s ~400 ms rescue budget → 503. The subset apply now runs before the `wait <= 0` short-circuit, so it fast-tracks whether or not any interval remains to sleep. Pinned by `TestSchedulerLanes_Case8_StructuralWaitZero_AppliesRuntimeSubset`.
- Discovery component now stops its pending version-probe retry timer on context cancellation. The all-replica Discovery component is rebuilt every controller iteration (e.g. on a config or credential change); a retry timer armed by a transient HAProxy version-probe failure was left running past teardown, firing up to a minute later against the torn-down iteration's EventBus and keeping the dead component (plus its captured stores/credentials) reachable until then. Under repeated config churn against a flaky Dataplane endpoint this accumulated leaked timers/goroutines. `Start` now stops the timer on exit, matching the drift-monitor / scheduler / metrics timer-cleanup pattern.
- HTTP resource store no longer misclassifies a `200 OK` empty-body response with no `ETag` as `304 Not Modified`. `RefreshURL` detected 304 via a `content == "" && newEtag == etag` heuristic; against an ETag-less server (sends neither `ETag` nor a 304-triggering `Last-Modified`), a resource that legitimately went non-empty → empty was silently treated as unchanged, so the stale non-empty content kept being served. `doFetch` now signals 304 explicitly via a sentinel error (`errNotModified`) instead of an empty-content heuristic, so an empty `200` is correctly staged as a pending content change.
- Owned-resource applier (`resourceApplier`) now narrows its event subscription to the three event types it handles (`SubscribeTypes`), matching its sibling `statusApplier`. It previously used a broad `Subscribe`, so high-volume events (`resource.index.updated`, `reconciliation.*`, which fire at kHz during conformance setup / busy clusters) filled its 50-slot buffer and could silently drop the `reconciliation.completed` event that carries the template-declared owned resources to apply (e.g. per-Gateway LoadBalancer Services) — the same overflow `statusApplier` was already fixed for. Owned-resource Server-Side Apply now fires reliably under burst load.
- SSL-certificate Secret publishing now retries on write conflict, matching its three sibling auxiliary-file publish helpers (map file / general file / crt-list). `createOrUpdateSSLSecret` was the lone publish path doing a single-shot get→update with no `RetryOnConflict`; under concurrent writers (e.g. a brief two-leader overlap during a leadership handoff) its update could fail with a `Conflict` and skip the publish until the next reconcile, leaving the observable Secret stale. It now re-gets the fresh resourceVersion and retries in-call like the others. All five publish helpers (the four auxiliary-file CRDs plus the runtime-config CRD) additionally retry a create-time `AlreadyExists` into the update path via `retry.OnError`, so a racing creator no longer surfaces the error to the caller — the previous `RetryOnConflict`-based path matched only `Conflict`, not `AlreadyExists`.
- Auxiliary-file sync now uploads per-file storage operations concurrently (bounded to 16) within each create/update/delete phase, instead of one sequential round-trip per file. This pins the residual `TestIngressRollingRestartZeroDowntime` 503: under the full parallel e2e suite a cross-tenant structural deploy's pre-config aux phase ran tens-to-hundreds of sequential dataplane storage round-trips, which at CI/DinD per-op latency (~25–75 ms) stretched the deploy to multiple seconds — and the deploy loop's runtime fast path is dark for the whole duration of an in-flight structural deploy (a runtime `set server` cannot flap-safely land before that deploy's reload, which would load a config rendered before the new pod). A rolling-restart pod that became Ready inside that window had its slot held back past `option redispatch`'s ~400 ms rescue budget → 503. Parallelizing the phase collapses it to sub-second, keeping endpoint propagation inside the budget; phase ordering (create→update→delete) is preserved and each `skip_reload` storage write targets a distinct path with no inter-file dependency. Root-caused from CI dataplane-log timing (the structural deploys' `force_reload` POSTs were ~5 s apart with the aux round-trips filling the gap); not reproducible on a fast local box, where the same phase runs in ~200 ms.
- Deployment scheduler now bounds reloads to ≤1 per `minDeploymentInterval` under concurrent reconcile churn, eliminating a reload storm. The rate-limit timer was spawned from three sites (scheduler idle path, the completion handler's pending re-schedule, and the recursive pending drain) with no mutual exclusion; under heavy parallel-suite or busy-cluster churn ~10 rate-limit goroutines slept concurrently on the same last-deployment time and woke together, firing ~10 reloads per interval instead of 1. The bursts churned HAProxy worker generations fast enough that an in-flight request transiting the chart's shared h2c loopback (`http-tcp` → unix socket → `http_frontend`) could land on a stale draining worker mid-reload and be rejected as a `<BADREQ>` 400 (or hang, or 503). Replaced the phase state machine with a single long-lived deploy-loop goroutine that owns all rate-limit timing and coalesces to the latest pending render — "≤1 deploy per interval" is now structural rather than emergent. The runtime-eligible fast path (instant endpoint convergence, interval-independent) is preserved. Surfaced + verified via `TestIngressRollingRestartZeroDowntime`, which went from 4/8 to 8/8 clean under the full parallel e2e suite.
- Backend comparator now detects `default-server` parameter changes. client-native's `BackendBase.Equal`/`Diff` skip the `default_server` field, so a backend whose only delta was on its `default-server` line produced an empty diff, took the no-reload runtime path, and never reloaded the new settings onto the worker. Surfaced by gateway-conformance `BackendTLSPolicyConflictResolution`: a conflict backend is created plain before its winning BackendTLSPolicy resolves, so the re-encrypt `ssl ca-file verify` arrives as a *later* `default-server` change — which silently didn't trigger a reload, leaving the backend served in plaintext (`400 Client sent an HTTP request to an HTTPS server`). The comparator now compares `DefaultServer` via reflect.DeepEqual and emits a structural backend update (→ reload) when it differs. Pairs with the chart-side reload-wrapper fix that lets that reload actually apply the ssl.
- Runtime server applies now retry across a concurrent HAProxy reload, fixing intermittent rolling-restart 503s under structural-churn reload pressure. While HAProxy reloads, the dataplaneapi master socket is briefly unavailable, so a `skip_reload` runtime push (the runtime-raw lane, and the scheduled deploy's runtime actions) returns `500 ... cannot execute SetServerState: ... haproxy-master.sock: connect: connection refused`. A pod-rotation server change landing in that ~150-200ms window was previously dropped until the next reconcile, leaving the rotated slot unserved so a request arriving meanwhile saw a 503. New `IsReloadInProgress` retry condition re-applies the runtime change immediately — the dataplaneapi HTTP round-trip paces the loop, no fixed backoff — until a 2s budget, so it re-lands within ~one round-trip of the master CLI listener returning, inside `option redispatch`'s rescue window. Version conflicts (409) and genuine errors are not retried. `CheckResponse` now embeds the (truncated) response body in its error so the reload signature is visible to the retry. Diagnosed from CI failure-snapshot artifacts: the new slot was up/ready/reachable by snapshot time, but the probe's request 503'd ~400ms earlier inside the reload window.
- `pkg/k8s/watcher.SingleWatcher` no longer skips content updates to resources without a status subresource. It skipped every Update whose `.metadata.generation` was unchanged ("status-only update") — the correct heuristic for resources with a status subresource (Deployment, StatefulSet, custom CRDs) but always-true for Secrets and ConfigMaps, which keep generation at 0 forever, so every meaningful content rotation (e.g. a credentials-Secret rotation) got dropped until the next pod restart. `SingleWatcher.handleUpdate` now applies the generation-unchanged skip only when at least one side has non-zero generation, so generation-0 resources fall through to the resourceVersion-changed signal already enforced above. Pinned by `TestSingleWatcher_DoesNotSkipUpdatesWhenGenerationStaysZero`.
- `StoreWrapper` no longer triggers a full `Store.List()` on per-key reads against `store: on-demand` resources, defeating the whole reason `on-demand` exists. The wrapper's `loadSnapshot` previously ran `Store.List()` on first access of ANY method (including `GetSingle` / `Fetch`); for a CachedStore-backed wrapper that fans out into one API fetch per cached reference, surfacing as the repeated `"Listing cached store causes individual API lookups"` WARN on every drift-prevention cycle. On a cluster with 195 Secrets and the chart default `secrets: store: on-demand` (the canonical "many large items, only a few touched by name" case), that was 195 unnecessary GET /api/v1/.../secrets/{name} calls per minute, every minute. The fix splits the snapshot path into eager (the existing behaviour for `store: full`) and lazy modes. Lazy mode primes the snapshot from a new `CachedStore.ListCached()` accessor that surfaces only the LRU's warm entries (no API fetches), and per-key reads fall through to `Store.Get(keys...)` for a single targeted lookup when the snapshot misses — folding the result back into the snapshot so a later `List()` or repeat `GetSingle()` in the same render sees it without re-fetching. `List()` on a lazy wrapper returns whatever the render has assembled (primed entries + touched keys) instead of fanning out to a full-cluster fetch; templates that need cluster-wide iteration should use the default `store: full`. Backward-compat: any wrapper without `LazySnapshot: true` (i.e. anything other than `store: on-demand` resources) keeps the historical eager behaviour exactly. Wired from both `rendercontext.Builder` and `renderer.RenderService` so production, test fixtures, and benchmarks all flow through the same path.
- Deployer's per-pod version cache no longer stores the caller's desired config — it now stores the pod's ACTUAL post-sync state, fetched and parsed by the orchestrator immediately after a commit that applied operations. The previous shape silently masked cross-pod drift: when two HAProxy pods entered a reconcile from different starting baselines (e.g. a rolling Deployment where pod A is synced twice and pod B is synced once during the rollover), the dataplane API's incremental patches landed them at logically-equivalent but byte-different on-disk configs. Both pods' cache entries then pointed at the same desired struct, so on every subsequent reconcile the comparator compared desired-to-desired, found no diff, and `drift_prevention` cheerfully reported `instances=2/2 succeeded, ops=0` while one of the pods continued to serve a stale config. Caching the actual post-sync state lets the comparator see pod-actual-vs-desired on the next reconcile and produce fixup ops until convergence. Costs one extra `GetRawConfiguration()` + parse per sync that applied operations; no-changes paths and fetch/parse failures fall back to the existing behaviour. Surfaced after a chart upgrade: HTTP requests to two ingresses returned 404 ~50% of the time depending on which pod kube-proxy picked, while drift_prevention saw nothing wrong; manual `kubectl rollout restart` cleared the divergent state but didn't fix the underlying cache shape.
- Deployment-scheduler no longer silently skips deployments after a render race. The "skip when config unchanged since last deploy" optimization compared the latest in-memory render's checksum against the cached `lastDeployedConfigHash` — but the cache was updated from `s.lastContentChecksum` at completion time, which a parallel reconcile may have overwritten between deployment-start and deployment-complete. The wrong (newer) hash then matched the next render's hash, hitting the skip branch, and the newer render's content never reached HAProxy. Symptom in e2e: a freshly-added Ingress's `http-request redirect` / auth-deny directive was present in the rendered `HAProxyCfg` CR but absent from the live `haproxy.cfg`, surfacing as redirect/auth tests timing out on 200 from the backend echo server. Fix: thread the deployed checksum through `DeploymentCompletedEvent.ContentChecksum` and read from the event payload, not from the live cache.
- `dig()` now returns nil for absent optional fields when navigating typed top-level globals, matching the long-documented "same behaviour for typed and untyped" contract. Previously, `dig(obj, "field") | fallback(default)` against a typegen-produced struct returned the type's zero value (`""`, `0`, `false`) for fields not populated in the source resource — `fallback()` only fires on nil, so the default never substituted and downstream key composition silently produced malformed strings (e.g. `ResolveCertRefKey` building `/<name>` instead of `<parentNs>/<name>` for cert refs that omit `namespace`, surfaced as 4 HTTPS chart-validation failures). Fix: typegen emits `json:"…,omitempty"` for fields not in the schema's `required` list, and `digStructField` returns nil for omitempty fields whose value is the type's zero value. Required fields keep their explicit zero values intact. Limitation tracked in #52: the heuristic can't distinguish *absent from source* vs *explicitly set to zero* for booleans/integers — no current chart pattern triggers that loss, but the proper tri-state fix (pointer types for optional fields, controller-gen convention) should land before the first chart branch on an optional bool/int.
- Bundled SPOA hub bumped to `v0.6.1` — fixes a use-after-free in `MetricRecorder::install()` that segfaulted the hub on plugin reload (exit 139). Previous `OnceLock`-based `install()` was silently no-op on the second-and-later calls, so the NEW plugin's hub-provided `MetricCtx` pointer never replaced the OLD one; when the hub later dropped the OLD plugin's `Box<MetricCtx>`, the next metric emission anywhere in that plugin's `.so` dereferenced freed memory. Surfaced in this repo as the HTTPRouteRequestMirror conformance flake (intermittent ~1-in-3 per shard); fix confirmed by 2 consecutive clean conformance runs against the patched image. Mandatory bump for `v0.6.0` users: any deployment that reloads plugins (i.e. any haptic deployment, since the controller pushes hub config via the dataplane API and the hub file-watches it) hits this crash. Upstream fix: `haproxy-spoa-hub` !161 → `v0.6.1`.

### Added

- **Typed watched resources (Tier-2)** — chart templates can now access `spec.watchedResources` entries through compile-time typed top-level globals (e.g. `gateways`, `httproutes`) in addition to the existing `resources["<name>"].List()` map shape. Field access (`gw.Metadata.Namespace`, `gw.Spec.GatewayClassName`) is type-checked at engine boot; a misspelling like `gw.Metadata.Naamespace` fails when the controller starts, not at the next reconcile. Driven by typebootstrap, which fetches each resource's OpenAPI v3 schema (via CRD lookup with OpenAPI v3 fallback for permission-restricted environments) and generates a `reflect.Type` per resource. Resources whose schema can't be fetched fall back to a universal envelope (`metadata.{name,namespace,labels,annotations}` typed; spec/status absent so chart code reaching into them surfaces a compile error). `dig()` continues to navigate both map values and typed structs so existing chart code keeps working unchanged. Offline `controller validate` carries the same wiring via embedded builtin schemas in `pkg/k8s/schemafetcher/builtin` — chart authors can develop and test typed access via `./scripts/test-templates.sh`. Chart-side adoption begins with a minimal `global-settings-001-typed-access-smoke` snippet in the gateway library that emits one HAProxy comment per Gateway, doubling as a regression canary and a worked example for chart authors.
- Chart's Ingress library now handles `spec.defaultBackend` in combination with `spec.rules` per the K8s spec: for each rule host, a per-host catch-all entry (`<host>/` → defaultBackend) is emitted in `path-prefix.map` alongside the rule's specific entries. HAProxy's `map_beg` longest-prefix semantics route rule-path matches to their rule backends and anything-else-on-that-host to the defaultBackend. Requests to OTHER hosts are NOT caught (defaultBackend is scoped to the Ingress's declared hosts, matching nginx-ingress / contour behaviour). Multi-Ingress collision per host is resolved by sorting candidates by `metadata.creationTimestamp` desc and picking the newest — matches operator intent on rollout and avoids stale-Ingress 503s during scenario churn. The previous rules-less-only behaviour (single `/` catch-all) is preserved as the `hostKey == ""` case. New chart validation tests cover all three shapes (rules-less, rules+default per-host, multi-Ingress newest-wins).
- **Plugin metrics across the SPOA bundle.** Every plugin in the bundled `haproxy-spoa-hub` image now emits Prometheus counters / gauges / histograms through the hub's `/metrics` endpoint. Names appear under the `plugin_<plugin>_` prefix the hub adds. Operators get first-class observability for the SPOA dispatch path without `kubectl exec` to inspect logs.
  - **Hub** bumped to `v0.6.0` (plugin-API v2). Vtable evolution is append-only — every existing v1 plugin still loads on the v2 hub, and every v2 plugin still loads on a v0.5.x hub (metrics silent there).
  - **mirror** v0.3.0: `dispatches_total`, `dispatch_dropped_total`, `dispatch_outcomes_total`, `dispatch_duration_seconds`, `in_flight`. Saturation rate (drops / dispatches) is the right alert input for tuning `request_concurrency`.
  - **coraza** v0.5.0: `evaluations_total{phase, action, app}`, `evaluation_duration_seconds`, `denials_total{phase, rule_id, app}`. "Which rules are blocking traffic" is now a single PromQL query.
  - **external-auth** v0.5.0: `auth_requests_total{outcome, status_class}`, `auth_duration_seconds`.
  - **fingerprinting** v0.3.0: `fingerprints_computed_total{kind}`, `compute_duration_seconds{kind}` where `kind ∈ {ja3, ja4}`.
  - **maxmind** v0.4.0: `lookups_total{lookup, status}`, `lookup_duration_seconds`.
  - **otel** v0.4.0: `dispatches_total{outcome}`, `dispatch_duration_seconds`.
  - **sso-auth** v0.3.0: `auth_decisions_total{outcome}` (outcome maps 1:1 to AuthAction variants), `auth_decision_duration_seconds`.
- Chart's Ingress library now implements `spec.defaultBackend` for rules-less Ingresses: requests that don't match any rule path are routed to the declared default backend via a catch-all `/` entry in path-prefix.map. Backend pool emitted alongside rule-based backends with the same first_seen dedup so a default backend reusing a rule's service+port doesn't produce a duplicate stanza. Ingresses with both `spec.rules` and `spec.defaultBackend` (per-host fallthrough) remain at 404 — out of scope for the upstream conformance scenarios we wire today; track as a follow-up if needed.
- Chart's Ingress library now correctly preserves trailing slashes on `pathType: Exact` rules: a rule for `/foo/` no longer matches a request for `/foo` (K8s spec: Exact is character-wise exact). The trailing-slash strip that was load-bearing for Prefix-boundary `pfxexact` entries is now scoped to non-Exact path types. Fixes a long-standing routing bug that the new Ingress conformance suite surfaced.
- HAProxy responses now carry a `Server: haptic` header. Most ingress controllers (nginx-ingress, traefik, …) emit one; HAProxy doesn't by default, and the upstream Ingress conformance suite asserts on its presence.
- Upstream Kubernetes Ingress conformance suite (`kubernetes-sigs/ingress-controller-conformance`) is now wired up alongside the Gateway API conformance suite. New `make test-ingress-conformance` target builds two binaries (a thin Go wrapper under build tag `ingress_conformance` that exec's the upstream and parses its Cucumber JSON reports, plus the upstream binary itself from a pinned `git clone`), bakes them into a distroless sibling-container image, and runs the suite against the `haptic-e2e` kind cluster on the same `haptic` IngressClass haptic uses everywhere else. Each upstream scenario surfaces as a named `t.Run` subtest so failures land in the regular `go test -v` output and CI logs without a separate report format to babysit. A new `test-ingress-conformance` GitLab CI job mirrors `test-gateway-conformance`'s trigger rules (skip default branch / tags, run on Go/chart/script changes) and pins the same single HAProxy version since the Ingress API surface is HAProxy-version-agnostic. Upstream is pinned to commit `d920ed3` (last upstream commit 2023-08-28) — the project is dormant but remains SIG-Network's only Ingress conformance vehicle; we do not auto-follow master. - Gateway-API `HTTPRouteFilter` of type `RequestMirror` is now supported, including `SupportHTTPRouteRequestMultipleMirrors` and (provisional) `SupportHTTPRouteRequestPercentageMirror`. Backed by the bundled `haproxy-spoa-hub-plugin-mirror` plugin (per-request dynamic target via SPOE `arg_target`, percent / fraction sampling normalised to a single `rand(100)` draw per request, multiple mirrors per route render as sequential dispatch triples with per-index `mirror-<i>-group` names so HAProxy's once-per-stream group dedup doesn't drop the second NOTIFY). The three corresponding upstream conformance features are now in the `supported` set rather than `excluded`.

### Fixed

- Controller no longer schedules a spurious iteration restart ~1s after every startup. The synthetic `CredentialsUpdatedEvent` published with `version="initial"` (a placeholder that kicks subscribers before the real Secret watcher onAdd) slipped past the bootstrap-match filter in `ConfigChangeHandler.handleSecretRotation` because the literal string `"initial"` never matched the real Secret resourceVersion. The handler treated it as a rotation and debounced a 1s reinit. Mostly harmless in production (the new iteration just re-fetches everything and proceeds), but in tests that perturb dependencies right after startup the restart raced fixture mutations and produced flaky behaviour. Fix mirrors the same `version="initial"` skip that `handleConfigValidated` already had.
- Auxiliary file UPDATEs (`spoe.conf`, maps, SSL certificates that go through the storage API) no longer trigger an auto-reload at the dataplane API. The controller now sends `skip_reload=true` on every `Update*` call and batches every aux-file change into the single reload triggered by the main config sync — or, when only aux content changed and the main config sync had no operations to trigger one, an explicit force-reload at the end of fine-grained sync. Previously the dataplane's default behaviour was to fire an auxiliary reload immediately after each `PUT /storage/*`, against the *current* haproxy.cfg, which raced an in-flight haproxy.cfg push: an HTTPRoute deletion that removed `send-spoe-group mirror-<i>-group` references would land the new spoe.conf first, the auto-reload would abort with "unable to find SPOE group mirror-<i>-group", and the raw-config fallback got stuck on the same error. With the new ordering, the new aux files exist on disk before the reload fires, but HAProxy keeps using the in-memory pre-update copy until the reload, so the new haproxy.cfg and the new aux content are loaded atomically. Same fix path resolves the equivalent race for crt-list shrinkage and any future aux-file content reduction.
- Status patches, admission validation, and template-declared owned-resource apply now resolve a watched resource's plural via the cluster RESTMapper instead of a built-in pluralization guess. The status/resource appliers and the dry-run validator previously derived the API resource name from the Kind with a hardcoded English-pluralization rule (plus a small irregular-plural table), so a watched CRD whose served plural didn't match that guess (an irregular or custom `spec.names.plural`) resolved to the wrong GroupVersionResource — its status conditions, owned resources, and admission overlays silently targeted a nonexistent resource. All three paths now consult the discovery-backed RESTMapper, the same authoritative kind→resource source the controller already uses for its admission webhook and typed-template wiring.

### Changed

- Bundled `haproxy-spoa-hub-plugin-mirror` bumped to `v0.2.1`. `request_concurrency` now auto-derives from `resolved_worker_threads() × 512`, clamped to `[1024, 4096]`, instead of the static 1024 default. Closes the v0.2.0 gap where worker_threads scaled with CPU but the in-flight permit cap stayed pinned — sidecars with 4+ workers had extra threads sitting idle whenever the cap saturated. The floor of 1024 matches v0.2.0's hardcoded default exactly (tiny-CPU sidecars unchanged); the ceiling of 4096 keeps the in-flight body-buffer memory bounded on large hosts. Operators with workloads that genuinely need more than 4k concurrent mirrors per plugin instance can still pin `request_concurrency` under `spoaHub.plugins.mirror.params`; explicit overrides bypass the clamp.
- Bundled `haproxy-spoa-hub-plugin-mirror` bumped to `v0.2.0`. The mirror plugin's tokio runtime is no longer hardcoded to 2 worker threads — it now auto-derives from `std::thread::available_parallelism()` (cgroup-aware on Linux 5.16+ / glibc 2.36+) with a floor of 2, so high-fan-out workloads on multi-core hosts scale with their CPU allotment. Operators tight on CPU can pin a specific count via `worker_threads = N` under `spoaHub.plugins.mirror.params`. The new `pool_max_idle_per_host` knob (default 32) bounds the per-target idle-connection pool so long-running plugin instances mirroring to many distinct backends don't accumulate unbounded idle keep-alive sockets.

- `ResourceApplier` is now stateless on the success path, mirroring the StatusApplier contract: `RenderedResources` travels on `ReconciliationCompletedEvent` and is read directly from the event payload, replacing the previous `cachedResources` field overwritten on every `TemplateRenderedEvent` and read on a later `ReconciliationCompletedEvent`. The previous shape was structurally identical to the racy StatusApplier `cachedPatches` pattern that this release already removes for status; eliminating it from the resource path closes the symmetric architectural inconsistency before render N+1 could clobber render N's resources between trigger and apply (the existing `ReconciliationCompletedEvent` is published synchronously after `TemplateRenderedEvent`, so the race wasn't observable in production, but the pattern was fragile to any future re-trigger that introduces a slow gap). `handleBecameLeader` no longer re-applies a cached set — the Reconciler's already-existing BecameLeader-fresh-reconcile trigger produces a new `ReconciliationCompletedEvent` carrying the current rendered set. No user-visible behaviour change.

### Added

- New `DeploymentSkippedEvent` published by the deployment scheduler when it determines the data plane is already at the just-rendered configuration and no deployment is needed (typically: rendered config hash and pod-set hash both match the last successful deployment). Previously this branch was silent, which silently stopped the StatusApplier from writing the "deployed" status variant for resources whose addition produced no config diff — Gateway with no attached routes, status-only deltas — and those resources stuck at the CRD-default `Programmed=Unknown, observedGeneration: missing` indefinitely. The event carries `Total`, `Reason`, `ConfigHash`, `PodSetHash`, the configuration's status patches, and correlation ID; the StatusApplier treats it equivalently to `DeploymentCompletedEvent` for the deployed-variant write. Distinct event type (not a synthetic `DeploymentCompletedEvent`) so commentator log levels and metrics counters can distinguish converged-no-op steady state from actual deployment activity.
- New `spec.k8sResources` map field on `HAProxyTemplateConfig` declares full Kubernetes resources to be reconciled by the controller via Server-Side Apply. Each entry maps a name to a Scriggo template that has the same context as the main `haproxyConfig` template (resources, filters, snippets, file registry, shared cache); rendered output may emit one or more YAML documents separated by `---`. The renderer parses each document, validates `apiVersion`/`kind`/`metadata.{name,namespace}`, and hands the result to the existing `resourceapplier` so downstream behaviour (SSA, partial-ownership annotation, orphan cleanup) is unchanged. The applier injects an `OwnerReference` (controller=true, blockOwnerDeletion=true) pointing at the HAProxyTemplateConfig CR for full-ownership resources in the controller's own namespace, so cascading delete (e.g. `helm uninstall`) GCs them. Replaces the imperative `renderResource()` template function with a declarative top-level CR concern; resource-emission is now a single source of truth that both runtime and validation paths can reason about.
- `resourceapplier` now supports a partial-ownership mode. When a rendered resource carries the `haproxy-haptic.org/ownership: partial` annotation, the applier (a) skips injecting the `managed-by` label, (b) does not track the resource in its orphan-cleanup set (orphan disappearance never DELETEs a partial-mode resource), and (c) strips the annotation from the SSA payload before applying. Field-manager-aware list-map merging on the apiserver handles per-entry ownership — chart-owned and haptic-owned entries on the same resource (e.g. `Service.spec.ports` keyed by `(port, protocol)`) coexist without conflict.

### Removed

- `renderResource()` template function. Use `spec.k8sResources` (declarative top-level CR field) instead. The runtime `RenderedResourceCollector`-fed-by-templates pathway is gone; the renderer fills the collector synchronously after rendering each `k8sResources` template, so downstream consumers (resourceapplier) see no shape change.

### Fixed

- `default_backend` (the catch-all for requests that match no route) now returns a gRPC-compatible "trailers-only" response for requests with `content-type: application/grpc`: HTTP/2 200 + `grpc-status: 12 (Unimplemented)` + `grpc-message: Unimplemented` + `content-type: application/grpc`. Previously the same backend returned plain HTTP 404 for every unmatched request including gRPC; gRPC clients then reported `malformed header: missing HTTP content-type`, tore down the HTTP/2 connection, and cancelled every sibling multiplexed RPC. This made parallel-subtest gRPC conformance tests `GRPCRouteHeaderMatching` / `GRPCExactMethodMatching` / `GRPCRouteListenerHostnameMatching` / `GRPCRouteWeight` deterministically flaky in CI. HAProxy 3.x's `http-request return ... hdr` strips `content-type` from the response when no body source is supplied, so the chart restores it via `http-after-response set-header` gated on `res.hdr(grpc-status) -m found`. Non-gRPC clients still get a plain HTTP 404 as before.
- GRPCRoute method matching now produces correctly-routed traffic on TLS+ALPN-h2 and plaintext h2c paths. Two independent bugs were silently dropping every gRPC request to default_backend (404):
  - The per-rule method matcher emitted `req.hdr(:path)` against the requested gRPC method. HAProxy's `req.hdr()` targets HTTP/1.1 headers and yields an empty string for the HTTP/2 `:path` pseudo-header — so the comparison was always against `""`, the rule never fired, and gRPC traffic fell through to default_backend (404 with HTTP/1.1 framing). Switched to the `path` sample fetch which parses HTTP/2's `:path` pseudo-header and HTTP/1.1's request-line URL alike.
  - The route-analysis pass synthesized GRPCRoute paths as `{type: "Exact", value: "/"}`, so the entry landed in `path-prefix-exact.map` keyed `<host>|/`. The runtime map_str lookup at request time keys off `<host>|<request-path>`; for any real gRPC request the URL path is `/<service>/<method>` (e.g. `/gateway_api_conformance.echo_basic.grpcecho.GrpcEcho/Echo`) so the lookup missed, gw_routeId stayed empty, the per-rule scope check failed first, and the rule never reached the path-ACL comparison. Switched to `{type: "PathPrefix", value: "/"}` so the synthetic path lands in `path-prefix.map` and the runtime map_beg lookup matches every URL under the host.
  - Together these close the upstream `GRPCExactMethodMatching`, `GRPCRouteHeaderMatching`, `GRPCRouteListenerHostnameMatching`, `GRPCRouteNamedRule`, and `GRPCRouteWeight` conformance tests, plus the e2e `TestGRPCOverTLS` regression.
- TLS listener with `Accepted=False/ProtocolConflict` (mixed Passthrough/Terminate modes on the same port) now reports `supportedKinds: []` instead of the protocol's default-kinds set `[TLSRoute]`. The upstream Gateway-API conformance helper `GatewayStatusMustHaveListeners` (helpers.go:917) compares actual SupportedKinds against the expected slice with empty-vs-non-empty asymmetric semantics, so reporting `[TLSRoute]` on a rejected listener broke the `TLSRouteListenerMixedTerminationNotSupported` conformance test (the `Listener_with_unsupported_mixed_Terminate/Passthrough_must_have_Accepted=False_with_Reason=ProtocolConflict` subtest specifically). Fix mirrors the existing `attachedRoutes = 0` clear in the same protocol-conflict guard.
- Per-Gateway marker Service (for `SupportGatewayInfrastructurePropagation`) and per-IP static-address Service names now stay within the Kubernetes 63-char RFC 1123 label limit. The chart's natural `gw-<ns>-<name>[-<ip>]` join overflows for long namespace + Gateway names — the conformance fixture `gateway-with-infrastructure-metadata` in `gateway-conformance-infra` produced a 65-char marker name, and `gateway-static-addresses` with IP `172.19.255.249` produced a 68-char per-IP name — and the API server rejected both with `metadata.name: must be no more than 63 characters`. The chart now routes both names through a `BoundedK8sName` helper (gateway library, `util-bounded-k8s-name` snippet) that returns the natural form for short inputs and a hashed form (`gw-<truncated-middle>-<8-hex>` for the marker, `gw-<truncated-middle>-<8-hex>-<ip>` for static-address) for long ones. The `gateway.networking.k8s.io/gateway-name` label still carries the original (untruncated) Gateway name so conformance lookup-by-label and the chart's per-Gateway status read-back are unaffected. Closes a real-cluster regression that masked `GatewayInfrastructure` and `GatewayStaticAddresses` conformance closures even after the cross-namespace marker landing fix.
- Per-Gateway marker Service for `SupportGatewayInfrastructurePropagation` now lands in the Gateway's own namespace (where the upstream conformance test searches via the `gateway.networking.k8s.io/gateway-name` label) rather than the controller's namespace. The resourceapplier no longer enforces the same-namespace defense-in-depth at the controller boundary — the chart's RBAC is the sole gate, with cluster-wide `services` write verbs added to the existing ClusterRole whenever the gateway library is enabled. Closes the upstream `GatewayInfrastructure` conformance test. Also fixed a register-allocation bug in the Scriggo template engine ([commit d9ddfaf7](https://gitlab.com/haproxy-haptic/scriggo/-/commit/d9ddfaf7bdc23b2f2a970b504f295b6eb1090138), [MR !89](https://gitlab.com/haproxy-haptic/scriggo/-/merge_requests/89)) that had been silently corrupting `gateway-name` discovery labels on per-Gateway marker / static-address Services: `emitForRange` was hardcoding `reflect.Int` for the key register regardless of the map's actual key type, so a `for k, v := range map[string]any{...}` loop's runtime `setString` would overwrite whatever string-bank slot happened to share that index — typically a previously declared outer variable. Bumped `gitlab.com/haproxy-haptic/scriggo` to `v0.0.0-20260509150618-f2482f37aeee` to pull in the fix.
- gRPC over plaintext HTTP/2 (h2c) on HTTP listener ports is now multiplexed with HTTP/1.1 traffic on the same bind. The chart inspects the first 24 bytes of every incoming connection at a `mode tcp` outer frontend (`frontend http-tcp`); connections matching the HTTP/2 prior-knowledge preface (`PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n`) route to a unix-socket-bound `mode http` frontend with `proto h2` (`frontend http_frontend_h2c`), while HTTP/1.1 connections route to a sibling unix-socket frontend in plain mode http (`frontend http_frontend`). PROXY-protocol v2 across the hop preserves the original client IP. Both inner frontends share the same `frontend-extra-*`, `frontend-routing-logic`, and `frontend-filters-*` extension points, so any chart snippet that emits HTTP-level directives lands in both protocols' paths. The architecture mirrors the chart's existing `ssl-tcp` → `ssl-loopback` → `https` chain on port 443, just for plaintext h2c instead of TLS-passthrough. Closes the upstream Gateway-API `GRPCExactMethodMatching`, `GRPCRouteHeaderMatching`, `GRPCRouteListenerHostnameMatching`, `GRPCRouteNamedRule`, and `GRPCRouteWeight` conformance tests. The TLS+ALPN-h2 path (HTTPS listeners with `alpn h2,http/1.1`) remains the production-typical regime, exercised end-to-end by `tests/e2e/grpc_tls_test.go`.
- Gateway TLS listeners on non-chart-static ports now bind correctly. Previously, TLS-Terminate listeners were folded into `bindHTTPSDefault`/`needHTTPSFrontend` (so the chart's mode-http HTTPS frontend tried to handle L4 TCP, a silent no-op), and TLS-Passthrough listeners on non-default ports were never bound at all. The chart now emits one mode-tcp frontend per Gateway TLS-listener port (`frontends-600-gateway-tls-listener`): Terminate listeners get `bind ... ssl crt-list ...` + `ssl_fc_sni`-based routing; Passthrough listeners get plain bind + `req_ssl_sni`-based routing. Reject-default at the end produces a TCP RST for SNIs that no route claims — closes the upstream `TLSRouteHostnameIntersection`, `TLSRouteInvalidBackendRefNonexistent`, and `TLSRouteInvalidBackendRefUnknownKind` conformance tests (the latter two via Pass 2's ResolvedRefs gate filtering invalid-backend routes out of the SNI allowlist). The chart-static httpsPort keeps its existing `frontends-500-ssl-tcp` (Ingress passthrough + ssl-loopback fall-through). `TLSRouteTerminateSimpleSameNamespace` remains skipped: its fixture uses port 8443 which collides with the chart's default httpsPort (operators set httpsPort to a non-8443 value as a workaround).
- TLSRoute mixed-termination listener-status emission. The chart's status-patches-200-gateway already detected mixed `Terminate`/`Passthrough` TLS listeners on the same port via the `tlsPortModes` pre-scan; pinning this contract via `test-tlsroute-mixed-termination-protocol-conflict` confirms both listeners surface `Accepted=False/ProtocolConflict` with `attachedRoutes=0`. Closes the upstream `TLSRouteListenerMixedTerminationNotSupported` conformance test.
- Gateway backend client-certificate emission. The chart resolves `spec.tls.backend.clientCertificateRef` at backend-emit time (walking the route's parent Gateways) and appends `crt <path>` to the backend's `default-server` line alongside the BackendTLSPolicy `ssl ca-file ... verify required` clause; status side emits `ResolvedRefs=True/ResolvedRefs` on the Gateway. Pinned via `test-gateway-backend-client-cert-shape`. Closes the upstream `GatewayBackendClientCertificateFeature` conformance test.
- Gateway frontend client-certificate validation no longer answers TLS handshakes without verifying the client cert when the listener has no hostname. The default crt-list line now folds in the `ca-file` + `verify <mode>` clause from `spec.tls.frontend.default.validation` (or per-port override) so handshakes whose SNI doesn't match a specific listener still verify against the configured CA. AllowValidOnly produces `verify required`; AllowInsecureFallback produces `verify optional`. Closes the upstream `GatewayFrontendClientCertificateValidation` and `GatewayFrontendClientCertificateValidationInsecureFallback` conformance tests.
- ListenerSet hostname/protocol conflict status emission. Per-LS conflict info is now folded into the same `effectiveListeners` shared cache value as the listener map (sub-key `statuses`), eliminating a race where F3 status patches read stale data and reported every LS-only-conflicting ListenerSet as `Accepted=True`. Per-listener `Conflicted=True/HostnameConflict` and `Conflicted=True/ProtocolConflict` conditions now land correctly, and ListenerSets whose every listener loses a conflict roll up to top-level `Accepted=False/ListenersNotValid`. Closes the upstream `ListenerSetHostnameConflict` and `ListenerSetProtocolConflict` conformance tests.
- ConfigChangeHandler now triggers an iteration restart on credentials-Secret rotation, not only on CRD changes. Previously the credentialsloader published `CredentialsUpdatedEvent` into the void — components held the credentials they parsed at startup, so rotating the Secret silently left the running pod using the stale credentials until it was manually restarted. The handler now records the Secret's resourceVersion at iteration startup and signals reinitialization through the existing `configChangeCh` path the moment a watcher event reports a different version. The next iteration re-fetches the rotated Secret and constructs a fresh dataplane client with the new bytes — no per-component hot-rotation, just one reload path that already covers CRD changes too.
- Renderer now fails fast when the rendered HAProxy config references map files the renderer did not register. Previously, a chart-side inconsistency could ship a config that referenced a missing map; the orchestrator's post-config-delete phase would then delete the file as "unreferenced" and every subsequent reload would fail until the offending Ingress was removed.
- Render-time view of the watched-resource stores is now pinned per-render across `List()`, `Fetch()`, and `GetSingle()`. The template-facing `StoreWrapper` snapshots the underlying store on first access and serves all subsequent reads — including keyed lookups — from an in-memory composite-key index built from the configured `IndexBy`. Previously, a live informer Add landing between two snippet executions could let one snippet (e.g. the auth `global-top-*` userlist emitter) iterate a different ingress set than another (the `backend-directives-*` `http_auth(...)` emitter) within a single render, producing an HAProxy config that referenced a userlist no snippet emitted — admission then denied the offending ingress with `unable to find userlist '...'`. Templates didn't need any change; the cross-snippet coherence guarantee is now structural.

### Added

- `/healthz` now reflects the configured pluggable-validator sockets. When `spec.validators` is non-empty, the probe stat()'s every socket and reports a single `pluggable-validators` component entry — `Healthy: true` when every socket is reachable, otherwise `Healthy: false` with a semicolon-joined `<name>: <reason>` failure list. Empty `validators` keeps `/healthz` output unchanged so operators not using the feature see no behaviour change. The check is sub-millisecond on the happy path so it stays cheap on every Kubernetes liveness/readiness probe interval.
- New `spec.validators` field on `HAProxyTemplateConfig` declares pluggable validator sidecars consulted by the admission webhook. Each entry names a validator (RFC 1123 label), points at a Unix domain socket inside the controller pod, and lists file-glob patterns the controller matches against rendered file paths to decide which files to send to that validator (controller-side routing — the validator program itself is opaque to the controller). Optional `timeoutMs` (per-call deadline) and `maxConnections` (adaptive connection-pool ceiling) round out the per-entry shape. When configured, the controller forwards each glob-matched file over a length-prefixed JSON wire protocol with persistent keep-alive connections; `(validator, file)` round-trips run in parallel. The validator's three-result response (`valid` / `warning` / `error`) maps directly to admission outcomes — warnings populate `AdmissionResponse.Warnings` and let admission proceed; errors deny with line-numbered diagnostics. New `pkg/controller/pluggablevalidator` package implements the wire-protocol primitives, a per-(validator, file-path, content-hash) LRU cache, an adaptive connection pool per validator (starts small, grows on contention, shrinks on idleness), and a `Manager` orchestrating parallel dispatch. The chart-side sidecar wiring lands in a follow-up MR. See `docs/controller/docs/operations/pluggable-validators.md` for end-user documentation and `docs/development/validator-protocol.md` for the wire-protocol spec.
- Make the HAProxyCfg republish throttle (`spec.dataplane.configPublishInterval`), the per-sync reload-verification timeout (`spec.dataplane.reloadVerificationTimeout`), and the overall sync timeout (`spec.dataplane.syncTimeout`) tunable via `HAProxyTemplateConfig`. Together with the existing `minDeploymentInterval`, `driftPreventionInterval`, `deploymentTimeout`, leader-election durations, and per-watcher `debounceInterval`, every throttle on the path between a Kubernetes event and a HAProxy push can now be tuned without rebuilding the controller.
- Per-resource `debounceInterval` override on `spec.watchedResources.*`. Defaults to the global 2s window when empty or unparseable; useful to throttle further for very high-churn resources on large clusters or to react even faster on latency-sensitive resources.
- New multi-arch `spoa-hub` container image at `registry.gitlab.com/haproxy-haptic/haptic/spoa-hub:<version>` bundling [`haproxy-spoa-hub`](https://gitlab.com/haproxy-haptic/haproxy-spoa-hub) plus the six plugin shared libraries (coraza, external-auth, fingerprinting, maxmind, otel, sso-auth). Cosign-signed by digest with a CycloneDX SBOM attestation. See `docs/controller/docs/operations/spoa-hub.md` for the bundled component list.
- New `versions-spoa.env` pinning the upstream hub + plugin versions, with renovate-managed bumps (grouped into one MR per run).
- New `make spoa-hub-image` for local single-arch builds; `make spoa-prep` runs the upstream sha256 + cosign verification of plugin `.so` files into `plugins/`.
- New `spoa-hub` template library wires HAProxy to the bundled SPOA hub sidecar — adds the `backend spoa-hub` block, the `filter spoe engine spoa-hub` directive in frontends, and registers `spoe.conf` as a general file. Auto-enabled when any plugin under `spoaHub.plugins.*` is on, or `spoaHub.enabled: true` is set explicitly. Plugin libraries plug into the rendered SPOE config via the `spoe-agents-*`, `spoe-messages-*`, and `frontend-spoe-filters-*` snippet globs. Configuration flows through the existing `templatingSettings.extraContext` mechanism — the controller stays generic.

The plugin sets `txn.hub.external_auth.allowed` (bool), which the deny rule checks. Per-message dispatch in `spoe-conf-content` lets one MR add a real body for one message without breaking other plugins still in stub form.

### Changed

- `StatusPatches []templating.StatusPatch` is now a payload field on `DeploymentScheduledEvent`, `DeploymentCompletedEvent`, `DeploymentSkippedEvent`, and `ReconciliationFailedEvent` (defensively cloned at construction per the events-package immutability contract). Previously the StatusApplier held a `cachedPatches` field overwritten on every `TemplateRenderedEvent` and read on every deploy/failure event — under sustained render churn the cache could hold render N+1's patches when deploy N's completion fired, so the applier wrote `Programmed=True` for resources whose config the just-completed deploy did NOT carry. The one-shot mTLS conformance test `GatewayFrontendClientCertificateValidation/Validate_default_configuration` triggered this race deterministically in CI (tests dialled after seeing `Programmed=True`, hit a stale `*:443` bind without per-listener `verify required`, wrong client cert accepted). Patches now travel on the deploy event itself — tautologically the patches that describe what the deploy shipped — so no side-channel cache, no LATEST-vs-deployed race. The DeploymentScheduler caches `lastValidatedStatusPatches` symmetrically with the existing `lastRenderedConfig`/`lastAuxiliaryFiles` cache and forwards it through scheduled/skipped events; the Coordinator forwards `lastSuccessfulPatches` onto failure events so the StatusApplier can apply renderFailed/deployFailed variants without state of its own. The StatusApplier is stateless on the success path; `handleBecameLeader` no longer replays anything because the Reconciler triggers a fresh reconciliation on leadership acquisition. Event-bus subscribers that didn't read `StatusPatches` see no behavioural change; subscribers that did (only the StatusApplier in-tree) get a per-event payload instead of a stale cache.

### Removed

- Drop `namespaceSelector` from `watchedResources` entries. The field was never wired up; setting it had no effect. Configs that included it must remove it (the API server may now reject unknown fields). For namespace scoping, filter at the template level against a watched `namespaces` resource, use `labelSelector:` on the resource, or run separate controller instances per scope.

- **HAProxy Ingress annotation compatibility**: 56 `haproxy-ingress.github.io/*` annotations via the haproxy-ingress template library
- **Dataplane API concurrency limiting**: `maxParallel` config option to limit concurrent API operations, preventing timeouts for large configurations
- **CRD content compression**: HAProxyCfg content compressed with zstd when exceeding `configPublishing.compressionThreshold` (default 1 MiB), reducing etcd storage
- **HAProxyGeneralFile CRD**: Publish general files (error pages, etc.) as Kubernetes custom resources with compression support
- **HAProxyCRTListFile CRD**: Publish crt-list files as Kubernetes custom resources with compression support
- **`semver_gte` template filter**: Version comparison for gating features on HAProxy version (e.g., `semver_gte(haproxyVersion, "3.3")`)
- **Template-driven status patches**: Templates can register status patches for any Kubernetes resource via `statusPatch()` function, with outcome-keyed variants (`rendered`, `deployed`, `renderFailed`, `deployFailed`) applied automatically based on pipeline phase
- **Backend diff field diagnostics**: Reconciliation log now includes which BackendBase fields caused backend updates, aiding diagnosis of false diffs from parser round-trip asymmetries
- **Status patch helper functions**: `condition()`, `transitionTime()`, and `toJSON()` template functions for building Kubernetes status conditions with stable transition timestamps

### Changed

- **Reconciliation triggering**: Leading-edge triggering with a 5s refractory period; no latency for isolated changes, bursts during that window are batched into a single reconciliation
- **Parallel Dataplane API operations**: Operations execute in parallel within each priority group, reducing sync time for large configurations
- **Balance directive**: `balance roundrobin` moved to `defaults` section to prevent silent behavior change when upgrading to HAProxy 3.3 (which changed the default balance algorithm from `roundrobin` to `random`)
- **Go runtime 1.26.1**: Green Tea GC replaces manual GOGC tuning
