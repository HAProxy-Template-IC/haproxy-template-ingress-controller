## [Unreleased]

### Added

- **Plugin metrics across the SPOA bundle.** Every plugin in the bundled `haproxy-spoa-hub` image now emits Prometheus counters / gauges / histograms through the hub's `/metrics` endpoint. Names appear under the `plugin_<plugin>_` prefix the hub adds. Operators get first-class observability for the SPOA dispatch path without `kubectl exec` to inspect logs.
  - **Hub** bumped to `v0.6.0` (plugin-API v2). Vtable evolution is append-only — every existing v1 plugin still loads on the v2 hub, and every v2 plugin still loads on a v0.5.x hub (metrics silent there).
  - **mirror** v0.3.0: `dispatches_total`, `dispatch_dropped_total`, `dispatch_outcomes_total`, `dispatch_duration_seconds`, `in_flight`. Saturation rate (drops / dispatches) is the right alert input for tuning `request_concurrency`.
  - **coraza** v0.5.0: `evaluations_total{phase, action, app}`, `evaluation_duration_seconds`, `denials_total{phase, rule_id, app}`. "Which rules are blocking traffic" is now a single PromQL query.
  - **external-auth** v0.5.0: `auth_requests_total{outcome, status_class}`, `auth_duration_seconds`.
  - **fingerprinting** v0.3.0: `fingerprints_computed_total{kind}`, `compute_duration_seconds{kind}` where `kind ∈ {ja3, ja4}`.
  - **maxmind** v0.4.0: `lookups_total{lookup, status}`, `lookup_duration_seconds`.
  - **otel** v0.4.0: `dispatches_total{outcome}`, `dispatch_duration_seconds`.
  - **sso-auth** v0.3.0: `auth_decisions_total{outcome}` (outcome maps 1:1 to AuthAction variants), `auth_decision_duration_seconds`.
- Chart's Ingress library now implements `spec.defaultBackend` for rules-less Ingresses: requests that don't match any rule path are routed to the declared default backend via a catch-all `/` entry in path-prefix.map. Backend pool emitted alongside rule-based backends with the same first_seen dedup so a default backend reusing a rule's service+port doesn't produce a duplicate stanza. Ingresses with both `spec.rules` and `spec.defaultBackend` (per-host fallthrough) remain at 404 — out of scope for the upstream conformance scenarios we wire today; track as a follow-up if needed.
- Chart's Ingress library now correctly preserves trailing slashes on `pathType: Exact` rules: a rule for `/foo/` no longer matches a request for `/foo` (K8s spec: Exact is character-wise exact). The trailing-slash strip that was load-bearing for Prefix-boundary `pfxexact` entries is now scoped to non-Exact path types. Fixes a long-standing routing bug that the new Ingress conformance suite surfaced.
- HAProxy responses now carry a `Server: haptic` header. Most ingress controllers (nginx-ingress, traefik, …) emit one; HAProxy doesn't by default, and the upstream Ingress conformance suite asserts on its presence.
- Upstream Kubernetes Ingress conformance suite (`kubernetes-sigs/ingress-controller-conformance`) is now wired up alongside the Gateway API conformance suite. New `make test-ingress-conformance` target builds two binaries (a thin Go wrapper under build tag `ingress_conformance` that exec's the upstream and parses its Cucumber JSON reports, plus the upstream binary itself from a pinned `git clone`), bakes them into a distroless sibling-container image, and runs the suite against the `haptic-e2e` kind cluster on the same `haptic` IngressClass haptic uses everywhere else. Each upstream scenario surfaces as a named `t.Run` subtest so failures land in the regular `go test -v` output and CI logs without a separate report format to babysit. A new `test-ingress-conformance` GitLab CI job mirrors `test-gateway-conformance`'s trigger rules (skip default branch / tags, run on Go/chart/script changes) and pins the same single HAProxy version since the Ingress API surface is HAProxy-version-agnostic. Upstream is pinned to commit `d920ed3` (last upstream commit 2023-08-28) — the project is dormant but remains SIG-Network's only Ingress conformance vehicle; we do not auto-follow master. The build also git-applies the vendored upstream PR #101 (convergence-retry mechanism, opened by Cilium's Tam Mach in 2022, never merged) from `tests/conformance/patches/`. Without that patch the upstream's no-retry single-shot HTTP step loses to the inherent K8s-Endpoints-to-runtime-config gap that every Ingress controller has a non-zero gap on; Cilium carries the same patch in their fork (`cilium/ingress-controller-conformance`) for the same reason.
- Gateway-API `HTTPRouteFilter` of type `RequestMirror` is now supported, including `SupportHTTPRouteRequestMultipleMirrors` and (provisional) `SupportHTTPRouteRequestPercentageMirror`. Backed by the bundled `haproxy-spoa-hub-plugin-mirror` plugin (per-request dynamic target via SPOE `arg_target`, percent / fraction sampling normalised to a single `rand(100)` draw per request, multiple mirrors per route render as sequential dispatch triples with per-index `mirror-<i>-group` names so HAProxy's once-per-stream group dedup doesn't drop the second NOTIFY). The three corresponding upstream conformance features are now in the `supported` set rather than `excluded`.

### Fixed

- Auxiliary file UPDATEs (`spoe.conf`, maps, SSL certificates that go through the storage API) no longer trigger an auto-reload at the dataplane API. The controller now sends `skip_reload=true` on every `Update*` call and batches every aux-file change into the single reload triggered by the main config sync — or, when only aux content changed and the main config sync had no operations to trigger one, an explicit force-reload at the end of fine-grained sync. Previously the dataplane's default behaviour was to fire an auxiliary reload immediately after each `PUT /storage/*`, against the *current* haproxy.cfg, which raced an in-flight haproxy.cfg push: an HTTPRoute deletion that removed `send-spoe-group mirror-<i>-group` references would land the new spoe.conf first, the auto-reload would abort with "unable to find SPOE group mirror-<i>-group", and the raw-config fallback got stuck on the same error. With the new ordering, the new aux files exist on disk before the reload fires, but HAProxy keeps using the in-memory pre-update copy until the reload, so the new haproxy.cfg and the new aux content are loaded atomically. Same fix path resolves the equivalent race for crt-list shrinkage and any future aux-file content reduction.

### Changed

- Bundled `haproxy-spoa-hub-plugin-mirror` bumped to `v0.2.1`. `request_concurrency` now auto-derives from `resolved_worker_threads() × 512`, clamped to `[1024, 4096]`, instead of the static 1024 default. Closes the v0.2.0 gap where worker_threads scaled with CPU but the in-flight permit cap stayed pinned — sidecars with 4+ workers had extra threads sitting idle whenever the cap saturated. The floor of 1024 matches v0.2.0's hardcoded default exactly (tiny-CPU sidecars unchanged); the ceiling of 4096 keeps the in-flight body-buffer memory bounded on large hosts. Operators with workloads that genuinely need more than 4k concurrent mirrors per plugin instance can still pin `request_concurrency` under `spoaHub.plugins.mirror.params`; explicit overrides bypass the clamp.
- Bundled `haproxy-spoa-hub-plugin-mirror` bumped to `v0.2.0`. The mirror plugin's tokio runtime is no longer hardcoded to 2 worker threads — it now auto-derives from `std::thread::available_parallelism()` (cgroup-aware on Linux 5.16+ / glibc 2.36+) with a floor of 2, so high-fan-out workloads on multi-core hosts scale with their CPU allotment. Operators tight on CPU can pin a specific count via `worker_threads = N` under `spoaHub.plugins.mirror.params`. The new `pool_max_idle_per_host` knob (default 32) bounds the per-target idle-connection pool so long-running plugin instances mirroring to many distinct backends don't accumulate unbounded idle keep-alive sockets.

- `ResourceApplier` is now stateless on the success path, mirroring the StatusApplier contract: `RenderedResources` travels on `ReconciliationCompletedEvent` and is read directly from the event payload, replacing the previous `cachedResources` field overwritten on every `TemplateRenderedEvent` and read on a later `ReconciliationCompletedEvent`. The previous shape was structurally identical to the racy StatusApplier `cachedPatches` pattern that this release already removes for status; eliminating it from the resource path closes the symmetric architectural inconsistency before render N+1 could clobber render N's resources between trigger and apply (the existing `ReconciliationCompletedEvent` is published synchronously after `TemplateRenderedEvent`, so the race wasn't observable in production, but the pattern was fragile to any future re-trigger that introduces a slow gap). `handleBecameLeader` no longer re-applies a cached set — the Reconciler's already-existing BecameLeader-fresh-reconcile trigger produces a new `ReconciliationCompletedEvent` carrying the current rendered set. No user-visible behaviour change.

### Added

- New `DeploymentSkippedEvent` published by the deployment scheduler when it determines the data plane is already at the just-rendered configuration and no deployment is needed (typically: rendered config hash and pod-set hash both match the last successful deployment). Previously this branch was silent, which silently stopped the StatusApplier from writing the "deployed" status variant for resources whose addition produced no config diff — Gateway with no attached routes, status-only deltas — and those resources stuck at the CRD-default `Programmed=Unknown, observedGeneration: missing` indefinitely. The event carries `Total`, `Reason`, `ConfigHash`, `PodSetHash`, the configuration's status patches, and correlation ID; the StatusApplier treats it equivalently to `DeploymentCompletedEvent` for the deployed-variant write. Distinct event type (not a synthetic `DeploymentCompletedEvent`) so commentator log levels and metrics counters can distinguish converged-no-op steady state from actual deployment activity.
- New `spec.k8sResources` map field on `HAProxyTemplateConfig` declares full Kubernetes resources to be reconciled by the controller via Server-Side Apply. Each entry maps a name to a Scriggo template that has the same context as the main `haproxyConfig` template (resources, filters, snippets, file registry, shared cache); rendered output may emit one or more YAML documents separated by `---`. The renderer parses each document, validates `apiVersion`/`kind`/`metadata.{name,namespace}`, and hands the result to the existing `resourceapplier` so downstream behaviour (SSA, partial-ownership annotation, orphan cleanup) is unchanged. The applier injects an `OwnerReference` (controller=true, blockOwnerDeletion=true) pointing at the HAProxyTemplateConfig CR for full-ownership resources in the controller's own namespace, so cascading delete (e.g. `helm uninstall`) GCs them. Replaces the imperative `renderResource()` template function with a declarative top-level CR concern; resource-emission is now a single source of truth that both runtime and validation paths can reason about.
- `resourceapplier` now supports a partial-ownership mode. When a rendered resource carries the `haproxy-haptic.org/ownership: partial` annotation, the applier (a) skips injecting the `managed-by` label, (b) does not track the resource in its orphan-cleanup set (orphan disappearance never DELETEs a partial-mode resource), and (c) strips the annotation from the SSA payload before applying. Field-manager-aware list-map merging on the apiserver handles per-entry ownership — chart-owned and haptic-owned entries on the same resource (e.g. `Service.spec.ports` keyed by `(port, protocol)`) coexist without conflict.

### Removed

- `renderResource()` template function. Use `spec.k8sResources` (declarative top-level CR field) instead. The runtime `RenderedResourceCollector`-fed-by-templates pathway is gone; the renderer fills the collector synchronously after rendering each `k8sResources` template, so downstream consumers (resourceapplier) see no shape change.

### Fixed

- `default_backend` (the catch-all for requests that match no route) now returns a gRPC-compatible "trailers-only" response for requests with `content-type: application/grpc`: HTTP/2 200 + `grpc-status: 12 (Unimplemented)` + `grpc-message: Unimplemented` + `content-type: application/grpc`. Previously the same backend returned plain HTTP 404 for every unmatched request including gRPC; gRPC clients then reported `malformed header: missing HTTP content-type`, tore down the HTTP/2 connection, and cancelled every sibling multiplexed RPC. This made parallel-subtest gRPC conformance tests `GRPCRouteHeaderMatching` / `GRPCExactMethodMatching` / `GRPCRouteListenerHostnameMatching` / `GRPCRouteWeight` deterministically flaky in CI. HAProxy 3.x's `http-request return ... hdr` strips `content-type` from the response when no body source is supplied, so the chart restores it via `http-after-response set-header` gated on `res.hdr(grpc-status) -m found`. Non-gRPC clients still get a plain HTTP 404 as before.
- GRPCRoute method matching now produces correctly-routed traffic on TLS+ALPN-h2 and plaintext h2c paths. Two independent bugs were silently dropping every gRPC request to default_backend (404):
  - The per-rule method matcher emitted `req.hdr(:path)` against the requested gRPC method. HAProxy's `req.hdr()` targets HTTP/1.1 headers and yields an empty string for the HTTP/2 `:path` pseudo-header — so the comparison was always against `""`, the rule never fired, and gRPC traffic fell through to default_backend (404 with HTTP/1.1 framing). Switched to the `path` sample fetch which parses HTTP/2's `:path` pseudo-header and HTTP/1.1's request-line URL alike.
  - The route-analysis pass synthesized GRPCRoute paths as `{type: "Exact", value: "/"}`, so the entry landed in `path-prefix-exact.map` keyed `<host>|/`. The runtime map_str lookup at request time keys off `<host>|<request-path>`; for any real gRPC request the URL path is `/<service>/<method>` (e.g. `/gateway_api_conformance.echo_basic.grpcecho.GrpcEcho/Echo`) so the lookup missed, gw_routeId stayed empty, the per-rule scope check failed first, and the rule never reached the path-ACL comparison. Switched to `{type: "PathPrefix", value: "/"}` so the synthetic path lands in `path-prefix.map` and the runtime map_beg lookup matches every URL under the host.
  - Together these close the upstream `GRPCExactMethodMatching`, `GRPCRouteHeaderMatching`, `GRPCRouteListenerHostnameMatching`, `GRPCRouteNamedRule`, and `GRPCRouteWeight` conformance tests, plus the e2e `TestGRPCOverTLS` regression.
- TLS listener with `Accepted=False/ProtocolConflict` (mixed Passthrough/Terminate modes on the same port) now reports `supportedKinds: []` instead of the protocol's default-kinds set `[TLSRoute]`. The upstream Gateway-API conformance helper `GatewayStatusMustHaveListeners` (helpers.go:917) compares actual SupportedKinds against the expected slice with empty-vs-non-empty asymmetric semantics, so reporting `[TLSRoute]` on a rejected listener broke the `TLSRouteListenerMixedTerminationNotSupported` conformance test (the `Listener_with_unsupported_mixed_Terminate/Passthrough_must_have_Accepted=False_with_Reason=ProtocolConflict` subtest specifically). Fix mirrors the existing `attachedRoutes = 0` clear in the same protocol-conflict guard.
- Per-Gateway marker Service (for `SupportGatewayInfrastructurePropagation`) and per-IP static-address Service names now stay within the Kubernetes 63-char RFC 1123 label limit. The chart's natural `gw-<ns>-<name>[-<ip>]` join overflows for long namespace + Gateway names — the conformance fixture `gateway-with-infrastructure-metadata` in `gateway-conformance-infra` produced a 65-char marker name, and `gateway-static-addresses` with IP `172.19.255.249` produced a 68-char per-IP name — and the API server rejected both with `metadata.name: must be no more than 63 characters`. The chart now routes both names through a `BoundedK8sName` helper (gateway library, `util-bounded-k8s-name` snippet) that returns the natural form for short inputs and a hashed form (`gw-<truncated-middle>-<8-hex>` for the marker, `gw-<truncated-middle>-<8-hex>-<ip>` for static-address) for long ones. The `gateway.networking.k8s.io/gateway-name` label still carries the original (untruncated) Gateway name so conformance lookup-by-label and the chart's per-Gateway status read-back are unaffected. Closes a real-cluster regression that masked `GatewayInfrastructure` and `GatewayStaticAddresses` conformance closures even after the cross-namespace marker landing fix.
- Per-Gateway marker Service for `SupportGatewayInfrastructurePropagation` now lands in the Gateway's own namespace (where the upstream conformance test searches via the `gateway.networking.k8s.io/gateway-name` label) rather than the controller's namespace. The resourceapplier no longer enforces the same-namespace defense-in-depth at the controller boundary — the chart's RBAC is the sole gate, with cluster-wide `services` write verbs added to the existing ClusterRole whenever the gateway library is enabled. Closes the upstream `GatewayInfrastructure` conformance test. Also fixed a register-allocation bug in the Scriggo template engine ([commit d9ddfaf7](https://gitlab.com/haproxy-haptic/scriggo/-/commit/d9ddfaf7bdc23b2f2a970b504f295b6eb1090138), [MR !89](https://gitlab.com/haproxy-haptic/scriggo/-/merge_requests/89)) that had been silently corrupting `gateway-name` discovery labels on per-Gateway marker / static-address Services: `emitForRange` was hardcoding `reflect.Int` for the key register regardless of the map's actual key type, so a `for k, v := range map[string]any{...}` loop's runtime `setString` would overwrite whatever string-bank slot happened to share that index — typically a previously declared outer variable. Bumped `gitlab.com/haproxy-haptic/scriggo` to `v0.0.0-20260509150618-f2482f37aeee` to pull in the fix.
- gRPC over plaintext HTTP/2 (h2c) on HTTP listener ports is now multiplexed with HTTP/1.1 traffic on the same bind. The chart inspects the first 24 bytes of every incoming connection at a `mode tcp` outer frontend (`frontend http-tcp`); connections matching the HTTP/2 prior-knowledge preface (`PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n`) route to a unix-socket-bound `mode http` frontend with `proto h2` (`frontend http_frontend_h2c`), while HTTP/1.1 connections route to a sibling unix-socket frontend in plain mode http (`frontend http_frontend`). PROXY-protocol v2 across the hop preserves the original client IP. Both inner frontends share the same `frontend-extra-*`, `frontend-routing-logic`, and `frontend-filters-*` extension points, so any chart snippet that emits HTTP-level directives lands in both protocols' paths. The architecture mirrors the chart's existing `ssl-tcp` → `ssl-loopback` → `https` chain on port 443, just for plaintext h2c instead of TLS-passthrough. Closes the upstream Gateway-API `GRPCExactMethodMatching`, `GRPCRouteHeaderMatching`, `GRPCRouteListenerHostnameMatching`, `GRPCRouteNamedRule`, and `GRPCRouteWeight` conformance tests. The TLS+ALPN-h2 path (HTTPS listeners with `alpn h2,http/1.1`) remains the production-typical regime, exercised end-to-end by `tests/e2e/grpc_tls_test.go`.
- Gateway TLS listeners on non-chart-static ports now bind correctly. Previously, TLS-Terminate listeners were folded into `bindHTTPSDefault`/`needHTTPSFrontend` (so the chart's mode-http HTTPS frontend tried to handle L4 TCP, a silent no-op), and TLS-Passthrough listeners on non-default ports were never bound at all. The chart now emits one mode-tcp frontend per Gateway TLS-listener port (`frontends-600-gateway-tls-listener`): Terminate listeners get `bind ... ssl crt-list ...` + `ssl_fc_sni`-based routing; Passthrough listeners get plain bind + `req_ssl_sni`-based routing. Reject-default at the end produces a TCP RST for SNIs that no route claims — closes the upstream `TLSRouteHostnameIntersection`, `TLSRouteInvalidBackendRefNonexistent`, and `TLSRouteInvalidBackendRefUnknownKind` conformance tests (the latter two via Pass 2's ResolvedRefs gate filtering invalid-backend routes out of the SNI allowlist). The chart-static httpsPort keeps its existing `frontends-500-ssl-tcp` (Ingress passthrough + ssl-loopback fall-through). `TLSRouteTerminateSimpleSameNamespace` remains skipped: its fixture uses port 8443 which collides with the chart's default httpsPort (operators set httpsPort to a non-8443 value as a workaround).
- TLSRoute mixed-termination listener-status emission. The chart's status-patches-200-gateway already detected mixed `Terminate`/`Passthrough` TLS listeners on the same port via the `tlsPortModes` pre-scan; pinning this contract via `test-tlsroute-mixed-termination-protocol-conflict` confirms both listeners surface `Accepted=False/ProtocolConflict` with `attachedRoutes=0`. Closes the upstream `TLSRouteListenerMixedTerminationNotSupported` conformance test.
- Gateway backend client-certificate emission. The chart resolves `spec.tls.backend.clientCertificateRef` at backend-emit time (walking the route's parent Gateways) and appends `crt <path>` to the backend's `default-server` line alongside the BackendTLSPolicy `ssl ca-file ... verify required` clause; status side emits `ResolvedRefs=True/ResolvedRefs` on the Gateway. Pinned via `test-gateway-backend-client-cert-shape`. Closes the upstream `GatewayBackendClientCertificateFeature` conformance test.
- Gateway frontend client-certificate validation no longer answers TLS handshakes without verifying the client cert when the listener has no hostname. The default crt-list line now folds in the `ca-file` + `verify <mode>` clause from `spec.tls.frontend.default.validation` (or per-port override) so handshakes whose SNI doesn't match a specific listener still verify against the configured CA. AllowValidOnly produces `verify required`; AllowInsecureFallback produces `verify optional`. Closes the upstream `GatewayFrontendClientCertificateValidation` and `GatewayFrontendClientCertificateValidationInsecureFallback` conformance tests.
- ListenerSet hostname/protocol conflict status emission. Per-LS conflict info is now folded into the same `effectiveListeners` shared cache value as the listener map (sub-key `statuses`), eliminating a race where F3 status patches read stale data and reported every LS-only-conflicting ListenerSet as `Accepted=True`. Per-listener `Conflicted=True/HostnameConflict` and `Conflicted=True/ProtocolConflict` conditions now land correctly, and ListenerSets whose every listener loses a conflict roll up to top-level `Accepted=False/ListenersNotValid`. Closes the upstream `ListenerSetHostnameConflict` and `ListenerSetProtocolConflict` conformance tests.
- ConfigChangeHandler now triggers iteration restart on credentials-Secret and webhook-cert Secret rotation, not only on CRD changes. Previously the certloader / credentialsloader would publish `CertParsedEvent` / `CredentialsUpdatedEvent` into the void — components held references to whichever PEM bytes they parsed at startup, so rotating the underlying Secret silently left the running pod serving the stale cert (or stale credentials) until it was manually restarted. The handler now records each Secret's resourceVersion at iteration startup and signals reinitialization through the existing `configChangeCh` path the moment a watcher event reports a different version. The next iteration re-fetches the rotated Secret as part of `fetchAndValidateInitialConfig` and constructs a fresh webhook server / dataplane client with the new bytes — no per-component hot-rotation, just one reload path that already covers CRD changes too.
- Renderer now fails fast when the rendered HAProxy config references map files the renderer did not register. Previously, a chart-side inconsistency could ship a config that referenced a missing map; the orchestrator's post-config-delete phase would then delete the file as "unreferenced" and every subsequent reload would fail until the offending Ingress was removed.
- Render-time view of the watched-resource stores is now pinned per-render across `List()`, `Fetch()`, and `GetSingle()`. The template-facing `StoreWrapper` snapshots the underlying store on first access and serves all subsequent reads — including keyed lookups — from an in-memory composite-key index built from the configured `IndexBy`. Previously, a live informer Add landing between two snippet executions could let one snippet (e.g. the auth `global-top-*` userlist emitter) iterate a different ingress set than another (the `backend-directives-*` `http_auth(...)` emitter) within a single render, producing an HAProxy config that referenced a userlist no snippet emitted — admission then denied the offending ingress with `unable to find userlist '...'`. Templates didn't need any change; the cross-snippet coherence guarantee is now structural.

### Added

- `/healthz` now reflects the configured pluggable-validator sockets. When `spec.validators` is non-empty, the probe stat()'s every socket and reports a single `pluggable-validators` component entry — `Healthy: true` when every socket is reachable, otherwise `Healthy: false` with a semicolon-joined `<name>: <reason>` failure list. Empty `validators` keeps `/healthz` output unchanged so operators not using the feature see no behaviour change. The check is sub-millisecond on the happy path so it stays cheap on every Kubernetes liveness/readiness probe interval.
- New `spec.validators` field on `HAProxyTemplateConfig` declares pluggable validator sidecars consulted by the admission webhook. Each entry names a validator (RFC 1123 label), points at a Unix domain socket inside the controller pod, and lists file-glob patterns the controller matches against rendered file paths to decide which files to send to that validator (controller-side routing — the validator program itself is opaque to the controller). Optional `timeoutMs` (per-call deadline) and `maxConnections` (adaptive connection-pool ceiling) round out the per-entry shape. When configured, the controller forwards each glob-matched file over a length-prefixed JSON wire protocol with persistent keep-alive connections; `(validator, file)` round-trips run in parallel. The validator's three-result response (`valid` / `warning` / `error`) maps directly to admission outcomes — warnings populate `AdmissionResponse.Warnings` and let admission proceed; errors deny with line-numbered diagnostics. New `pkg/controller/pluggablevalidator` package implements the wire-protocol primitives, a per-(validator, file-path, content-hash) LRU cache, an adaptive connection pool per validator (starts small, grows on contention, shrinks on idleness), and a `Manager` orchestrating parallel dispatch. The chart-side sidecar wiring lands in a follow-up MR. See `docs/controller/docs/operations/pluggable-validators.md` for end-user documentation and `docs/development/validator-protocol.md` for the wire-protocol spec.
- Make the reconciliation refractory window (`spec.controller.reconciliationDebounceInterval`), the HAProxyCfg republish throttle (`spec.dataplane.configPublishInterval`), the per-sync reload-verification timeout (`spec.dataplane.reloadVerificationTimeout`), the overall sync timeout (`spec.dataplane.syncTimeout`), and the HTTP 409 retry budget (`spec.dataplane.syncMaxRetries`) tunable via `HAProxyTemplateConfig`. Together with the existing `minDeploymentInterval`, `driftPreventionInterval`, `deploymentTimeout`, leader-election durations, and per-watcher `debounceInterval`, every throttle on the path between a Kubernetes event and a HAProxy push can now be tuned without rebuilding the controller.
- Per-resource `debounceInterval` override on `spec.watchedResources.*`. Defaults to the global 1s window when empty or unparseable; useful to throttle further for very high-churn resources on large clusters or to react even faster on latency-sensitive resources.
- New multi-arch `spoa-hub` container image at `registry.gitlab.com/haproxy-haptic/haptic/spoa-hub:<version>` bundling [`haproxy-spoa-hub`](https://gitlab.com/haproxy-haptic/haproxy-spoa-hub) plus the six plugin shared libraries (coraza, external-auth, fingerprinting, maxmind, otel, sso-auth). Cosign-signed by digest with a CycloneDX SBOM attestation. See `docs/controller/docs/operations/spoa-hub.md` for the bundled component list.
- New `versions-spoa.env` pinning the upstream hub + plugin versions, with renovate-managed bumps (grouped into one MR per run).
- New `make spoa-hub-image` for local single-arch builds; `make spoa-prep` runs the upstream sha256 + cosign verification of plugin `.so` files into `plugins/`.
- New `spoa-hub` template library wires HAProxy to the bundled SPOA hub sidecar — adds the `backend spoa-hub` block, the `filter spoe engine spoa-hub` directive in frontends, and registers `spoe.conf` as a general file. Auto-enabled when any plugin under `spoaHub.plugins.*` is on, or `spoaHub.enabled: true` is set explicitly. Plugin libraries plug into the rendered SPOE config via the `spoe-agents-*`, `spoe-messages-*`, and `frontend-spoe-filters-*` snippet globs. Configuration flows through the existing `templatingSettings.extraContext` mechanism — the controller stays generic.
- External-auth flow wired up end to end: nginx-ingress library reads `nginx.ingress.kubernetes.io/auth-url` annotations into a new `auth-url.map`, the spoa-hub library emits a per-frontend lookup + `send-spoe-group` trigger + `deny_status 401` rule, and the spoe.conf agent uses `groups` with explicit triggering (canonical pattern from the haproxy-spoa-hub external-auth plugin). The plugin sets `txn.hub.external_auth.allowed` (bool), which the deny rule checks. Per-message dispatch in `spoe-conf-content` lets one MR add a real body for one message without breaking other plugins still in stub form.

### Changed

- `StatusPatches []templating.StatusPatch` is now a payload field on `DeploymentScheduledEvent`, `DeploymentCompletedEvent`, `DeploymentSkippedEvent`, and `ReconciliationFailedEvent` (defensively cloned at construction per the events-package immutability contract). Previously the StatusApplier held a `cachedPatches` field overwritten on every `TemplateRenderedEvent` and read on every deploy/failure event — under sustained render churn the cache could hold render N+1's patches when deploy N's completion fired, so the applier wrote `Programmed=True` for resources whose config the just-completed deploy did NOT carry. The one-shot mTLS conformance test `GatewayFrontendClientCertificateValidation/Validate_default_configuration` triggered this race deterministically in CI (tests dialled after seeing `Programmed=True`, hit a stale `*:443` bind without per-listener `verify required`, wrong client cert accepted). Patches now travel on the deploy event itself — tautologically the patches that describe what the deploy shipped — so no side-channel cache, no LATEST-vs-deployed race. The DeploymentScheduler caches `lastValidatedStatusPatches` symmetrically with the existing `lastRenderedConfig`/`lastAuxiliaryFiles` cache and forwards it through scheduled/skipped events; the Coordinator forwards `lastSuccessfulPatches` onto failure events so the StatusApplier can apply renderFailed/deployFailed variants without state of its own. The StatusApplier is stateless on the success path; `handleBecameLeader` no longer replays anything because the Reconciler triggers a fresh reconciliation on leadership acquisition. Event-bus subscribers that didn't read `StatusPatches` see no behavioural change; subscribers that did (only the StatusApplier in-tree) get a per-event payload instead of a stale cache.
- Default debounce interval lowered from 5s to 1s. Both the per-watcher debounce window (`spec.watchedResources.*.debounceInterval`) and the reconciler refractory window (`spec.controller.reconciliationDebounceInterval`) now default to 1s. The 5s default was a leftover from early EndpointSlice-churn experiments; in practice every change still fires immediately on the leading edge — the refractory window only batches *follow-up* events within it. 1s keeps the chart's reaction time well inside conformance polling cadences and admission-controller status-feedback expectations without flooding (kube-apiserver watch coalescing and per-render dedup keep the actual render rate proportional to real spec churn). Operators on high-churn EndpointSlice workloads can opt back into longer windows by setting per-watcher overrides explicitly.

### Removed

- Drop `namespaceSelector` from `watchedResources` entries. The field was never wired up; setting it had no effect. Configs that included it must remove it (the API server may now reject unknown fields). For namespace scoping, filter at the template level against a watched `namespaces` resource, use `labelSelector:` on the resource, or run separate controller instances per scope.

## [0.1.0] - 2026-03-09

### Added

- **Template-driven HAProxy configuration**: Generate HAProxy configs using Scriggo templates (Go-based, Jinja2-like syntax) with full access to Kubernetes resources, built-in utility functions, and modular template snippets
- **Embedded validation tests**: Declarative test fixtures and assertions for testing HAProxy configurations within template libraries; run via `haptic-controller validate --test <name>`
- **Dry-run validation webhook**: Admission webhook for opted-in watched resources (Ingress, HTTPRoute, GRPCRoute by default) that re-renders the template set with the proposed change and rejects requests that would produce an invalid HAProxy configuration
- **Multi-architecture container images**: `linux/amd64`, `linux/arm64`, `linux/arm/v7`
- **HAProxy version support**: 3.0, 3.1, 3.2, 3.3 — version-specific images tagged accordingly
- **Supply chain security**: Container images, binaries, and Helm charts signed with Cosign (keyless OIDC); SBOM attestations in SPDX format
- **Prometheus metrics**: Reconciliation timing, template rendering duration, validation results, and Kubernetes API latencies
- **Leader election for high availability**: Multiple controller replicas with automatic leader election; hot-standby replicas continue watching and validating; configurable failover timing
- **Stall detection**: Components detect when blocked and report unhealthy via `/healthz`, enabling automatic pod restart via Kubernetes liveness probes
- **Configurable deployment timeout**: `deploymentTimeout` in dataplane config (default: 30s) to recover from stuck deployments
- **Server slot preservation**: Preserve HAProxy server slots during rolling deployments to enable zero-reload runtime API updates via `currentConfig` template context
- **HAProxy Ingress annotation compatibility**: 56 `haproxy-ingress.github.io/*` annotations via the haproxy-ingress template library
- **Dataplane API concurrency limiting**: `maxParallel` config option to limit concurrent API operations, preventing timeouts for large configurations
- **CRD content compression**: HAProxyCfg content compressed with zstd when exceeding `configPublishing.compressionThreshold` (default 1 MiB), reducing etcd storage
- **HAProxyGeneralFile CRD**: Publish general files (error pages, etc.) as Kubernetes custom resources with compression support
- **HAProxyCRTListFile CRD**: Publish crt-list files as Kubernetes custom resources with compression support
- **`semver_gte` template filter**: Version comparison for gating features on HAProxy version (e.g., `semver_gte(haproxyVersion, "3.3")`)
- **Template-driven status patches**: Templates can register status patches for any Kubernetes resource via `statusPatch()` function, with outcome-keyed variants (`rendered`, `deployed`, `renderFailed`, `deployFailed`) applied automatically based on pipeline phase
- **Backend diff field diagnostics**: Reconciliation log now includes which BackendBase fields caused backend updates, aiding diagnosis of false diffs from parser round-trip asymmetries
- **Status patch helper functions**: `condition()`, `transitionTime()`, and `toJSON()` template functions for building Kubernetes status conditions with stable transition timestamps

### Changed

- **Reconciliation triggering**: Leading-edge triggering with a 5s refractory period; no latency for isolated changes, bursts during that window are batched into a single reconciliation
- **Parallel Dataplane API operations**: Operations execute in parallel within each priority group, reducing sync time for large configurations
- **Balance directive**: `balance roundrobin` moved to `defaults` section to prevent silent behavior change when upgrading to HAProxy 3.3 (which changed the default balance algorithm from `roundrobin` to `random`)
- **Go runtime 1.26.1**: Green Tea GC replaces manual GOGC tuning
