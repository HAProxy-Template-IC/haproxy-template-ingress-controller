# Changelog

All notable changes to the HAProxy Template Ingress Controller will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

For Helm chart changes, see [Chart CHANGELOG](./charts/haptic/CHANGELOG.md).

## [Unreleased]

### Added

- Field-level validation-test stripping: `validationTests` accept `requiresFields` (`<watchedResource>.<field.path>` entries); tests whose fields are absent from the resolved schema generation are stripped at config load. Fixes the controller crash-loop on clusters serving older Gateway API releases (v1.1/v1.4) whose schemas lack fields the chart's tests exercise (#59).
- Runtime API-version detection for watched resources: `watchedResources` entries accept an ordered `apiVersions` candidate list and an `optional` flag, resolved against live apiserver discovery at startup. `templateSnippets`/`validationTests` accept `requires` — features whose optional resources aren't served are stripped at config load instead of failing startup.
- A CRD watch reinitializes the controller when a watched resource's CRD is installed, upgraded in place, or removed — Gateway API support activates or re-resolves at runtime with no Helm operation and no pod restart. Reloads fire only when the resolution outcome actually changes.
- A required watched resource with no served candidate version now fails startup fast with an error naming the resource and candidates (previously: silent infinite informer-sync hang with `/healthz` stuck at 503).
- Templates can read the resolved version of any watched resource via `resources.<name>.APIVersion()`; the resolution is exposed at `/debug/vars/effectiveConfigResolution`.
- `controller validate` resolves `apiVersions` candidate lists against `--schema-dir` CRD manifests and strips unavailable optional features, making degraded cluster profiles testable offline.
- Bulk resource watchers register a watch-error handler, so a watch that starts failing mid-run (e.g. its API version stopped being served) is logged instead of being visible only inside client-go.
- The controller now emits Kubernetes Events on the `HAProxyTemplateConfig`: a `Warning`/`ValidationFailed` (carrying the first error) when a config change fails validation — template, JSONPath, or `haproxy -c` — and a `Normal`/`Validated` on recovery. Failures now surface in `kubectl describe haproxytemplateconfig` and `kubectl get events`, not only in CRD status and controller logs.
- HAProxy 3.4 support: the controller is now built, validated, and released for HAProxy 3.4 (which ships DataPlane API v3.3, served by the existing v3.3 client).
- The controller now runs the config's embedded `validationTests` before accepting a `HAProxyTemplateConfig` — at startup and on every change — so it never loads a config whose tests fail (previously only the `controller validate` CLI ran them). A failing change is rejected and the last-good config keeps serving; at startup the controller stays unready until a passing config is present. Failing test names and reasons are surfaced on the CR's `status.validationErrors`. Runs only on config load, never on the reconciliation hot path.
- The admission webhook now also runs the config's embedded `validationTests` (the same suite as the load gate), so a `HAProxyTemplateConfig` whose tests fail is denied at `kubectl apply` and never reaches etcd — closing the gap where a broken config could be stored and then crash-loop the next fresh controller pod. The run is time-bounded; if it can't finish within the admission budget, or the webhook is unreachable (`failurePolicy: Ignore`), the apply is admitted-with-warning and the load gate still enforces.
- **Typed watched resources** — chart templates can access watched resources through compile-time typed top-level globals (e.g. `gateways`, `httproutes`); field access is type-checked at controller startup. Schemas come from the live apiserver, or `--schema-dir` offline. See [ADR-0010](./docs/adr/0010-typed-watched-resources.md).
- `spec.k8sResources` declares full Kubernetes resources reconciled via Server-Side Apply, with an `OwnerReference` to the `HAProxyTemplateConfig` CR so `helm uninstall` GCs them. Replaces the imperative `renderResource()` template function.
- `resourceapplier` partial-ownership mode (`haproxy-haptic.org/ownership: partial`): chart-owned and haptic-owned entries coexist on one resource via field-manager-aware list-map merging; orphan cleanup never deletes a partial-mode resource.
- `spec.validators` declares pluggable validator sidecars consulted by the admission webhook (per-entry socket, file-glob routing, timeout, connection pool); `/healthz` reports each socket's reachability.
- The admission webhook hot-reloads its TLS certificate via a `GetCertificate` callback that re-parses the mounted Secret on change, so a cert-manager renewal is served within ~a minute without a controller restart. The `--webhook-cert-secret-name` flag is replaced by `--webhook-cert-dir` (env `WEBHOOK_CERT_DIR`), and the controller no longer reads the cert Secret over the API.
- Gateway API `HTTPRouteFilter` of type `RequestMirror`, including multiple and percentage/fraction mirrors, backed by the bundled mirror SPOA plugin.
- Ingress `spec.defaultBackend` support, both rules-less (catch-all `/`) and combined with `spec.rules` (per-host fallthrough, newest-Ingress-wins on collision).
- Ingress `pathType: Exact` now preserves trailing slashes (`/foo/` no longer matches `/foo`).
- HAProxy responses now carry a `Server: haptic` header.
- Prometheus metrics for every bundled SPOA plugin (mirror, coraza, external-auth, fingerprinting, maxmind, otel, sso-auth) via the hub's `/metrics` endpoint.
- Runtime fast-path metrics: `haptic_runtime_fast_path_fires_total`, `_applies_total`, `_failures_total`, `_server_updates_total`.
- Deployment operation metrics: `haptic_haproxy_reloads_total` (HAProxy reloads triggered by deployments — the canonical capacity/SLO signal, since a reload forks the process) and `haptic_dataplane_api_operations_total` (DataPlane API operations applied to HAProxy).
- `spec.dataplane.configPublishInterval`, `reloadVerificationTimeout`, and `syncTimeout` are now tunable via `HAProxyTemplateConfig`; `spec.watchedResources.*.debounceInterval` adds a per-resource override.
- New `spoa-hub` container image bundling the hub plus seven plugin libraries, Cosign-signed by digest with a CycloneDX SBOM. A `spoa-hub` template library wires HAProxy to the sidecar, auto-enabled when any plugin is on.
- External-auth flow wired end to end (nginx-ingress `auth-url` annotation → `auth-url.map` → per-frontend SPOE check + `deny_status 401`).

### Changed

- Leader-election timing defaults raised from 15s/10s/2s to 30s/20s/5s (leaseDuration/renewDeadline/retryPeriod), giving the leader a 20s budget to ride out apiserver or CPU starvation stalls without losing the lease. Trade-off: crash-failover (leader dies without releasing the lease) now takes up to ~35s instead of ~17s; voluntary handoffs (rolling update, graceful shutdown) still release the lease immediately. Tune via `spec.controller.leaderElection` (#57).
- The controller now runs the `HAProxyTemplateConfig`'s embedded `validationTests` at **startup/load**, not only on live changes, and **crash-loops** (stays un-`/healthz`, so the liveness probe restarts the pod) if they fail. Previously a fresh or restarted controller — every `helm upgrade` restarts the controllers — loaded the config after only structural validation and served it even if its `validationTests` failed; only a live edit to an already-running controller was gated. A rolling upgrade now stalls on the old, good pods instead of rolling out a config that fails its own tests. Both gates share one code path so they can't drift.
- Rapid successive `HAProxyTemplateConfig` edits now coalesce: when several config changes are queued, the controller validates only the latest, skipping superseded ones rather than running the (now multi-second) `validationTests` suite against each in turn. The operator's most recent config is what gets validated and applied.
- `store: on-demand` watched resources now keep far less memory resident: the underlying informer strips each object's body to just the `indexBy`, field-selector, and identity fields, dropping large payloads (e.g. Secret `data`, plus the configured ignore-fields such as `metadata.managedFields` and the `last-applied-configuration` annotation that otherwise duplicates the whole body) from the in-memory cache. Templates still read the full object — it is fetched live on access — so rendering behavior is unchanged. See [ADR-0012](./docs/adr/0012-on-demand-projection-and-access-gated-reconcile.md).
- All controller log output now shares one logfmt format. client-go's leader-election/informer logs (klog) and automemlimit's `GOMEMLIMIT is updated` line are routed through the structured slog handler instead of their own formats; every message starts with a capital letter; resource counts are emitted as individual `resource_counts.<type>=N` keys instead of a non-parseable Go `map[...]` literal; and startup labels all eight stages at INFO (previously only 5–8).
- Reduced steady-state INFO log noise: routine per-request/per-reconcile success and housekeeping lines now log at DEBUG instead of INFO — successful admission-webhook validations (denials and warning-bearing admissions stay INFO), runtime-eligible fast-path server applies, HTTP-content refresh/validation/promotion/eviction, validation-test no-ops and completions, unreferenced aux-file cleanup, and pod-reference/stale-status cleanup on pod termination. Failures, denials, config/credential changes, leadership transitions, and HAProxy-pod topology changes remain at INFO. Set `LOG_LEVEL=DEBUG` to restore the previous verbosity.
- Endpoint changes now propagate immediately while reload-inducing structural changes stay lenient. The reconciler-level refractory and `spec.controller.reconciliationDebounceInterval` were **removed** (the reconciler fires on every change); batching is per-watcher, with `spec.watchedResources.<name>.debounceInterval` default raised from 100ms to 2s and `"0"` firing on every change. Reload throttling remains the deployer's `minDeploymentInterval`.
- Runtime-eligible server changes (pod-IP rotation, port, admin state) now reach the live HAProxy workers in ~ms via a runtime fast path that bypasses the deployment interval, instead of waiting on the O(config-size) scheduled deploy; structural changes still take the rate-limited reload path. The change persists across reloads because the deploy re-renders current endpoints (ADR-0011).
- Map file content changes (routing host/path/weight maps) now apply to the live HAProxy workers via the runtime API without a reload, instead of forcing one. Only content updates to existing maps qualify; adding or removing a map file, or any other auxiliary-file change (crt-lists, general/error files), still reloads. A runtime apply failure falls back to a reload, so the result always converges.
- TLS certificate content changes (e.g. a cert-manager renewal of an existing certificate) now apply to the live HAProxy workers via the runtime API without a reload, on HAProxy 3.2+ (`set ssl cert` + `commit ssl cert`). Adding or removing a certificate, crt-list changes, and HAProxy <3.2 still reload. A runtime apply failure falls back to a reload.
- Frontend `maxconn` changes now apply to the live HAProxy workers via the runtime API (`set maxconn frontend`, carried as the `SetFrontendMaxConn` runtime action) without a reload. Previously a maxconn-only change forced a reload even though it was listed as runtime-eligible. Any other frontend attribute change in the same update, or unsetting maxconn, still reloads. Works on all supported HAProxy versions.
- SSL CA-file content changes — mTLS trust bundles for `BackendTLSPolicy` backend verification and Gateway frontend client-cert verification — now apply to the live HAProxy workers via the runtime API without a reload, on HAProxy 3.2+ (`add ssl ca-file` + `commit ssl ca-file`, which replaces the bundle content). This makes frequent trust-bundle rotation (e.g. SPIFFE/SPIRE SVID roots with hourly TTLs) reload-free. Adding or removing a CA file, and HAProxy <3.2, still reload. A runtime apply failure falls back to a reload.
- `controller validate` now requires `--schema-dir` (or `HAPTIC_SCHEMA_DIR`) for typed-access templates; the embedded built-in Gateway schema fallback was removed. `scripts/test-templates.sh` auto-wires `tests/schemas`. Production (live apiserver) is unaffected. See [ADR-0010](./docs/adr/0010-typed-watched-resources.md).

### Fixed

- Deleting an unreferenced TLS certificate (or crt-list) from HAProxy storage no longer lets the DataPlane API schedule a second, uncoordinated reload after the deploy's own reload. That stray reload blacked out the master CLI socket ~0.5–1s after every certificate-removing deploy, so runtime fast-path `set server` updates landing in that window failed and retried while the outgoing worker drained with a stale server list — observed as a single 503 during a single-replica rolling restart when a backend rollout coincided with the window (#67). Storage deletes now send `skip_reload=true`, matching the existing create/update behavior; the deploy pipeline's config push remains the only reload trigger.
- Config validation no longer blocks the config-change event loop: the validation scatter-gather (dominated by the embedded `validationTests` suite, 13-15s+ under load) now runs asynchronously with single-flight/latest-wins ordering. Previously a leadership acquisition during an in-flight validation (e.g. right after a CRD-triggered reinitialization) left the leader-only config publisher without a template config for the whole validation — no `HAProxyCfg` spec update could be written in that window (#55).
- The pure-runtime deploy lane now verifies runtime map updates by read-back after apply and falls back to a reload when the live map did not converge. Previously a runtime map write acknowledged by the DataPlane API but lost on the master socket (observed on the haproxytech 3.1 image under reload churn) latched stale routing — the on-disk file already matched the desired state, so no later deploy re-synced the map and requests kept hitting `default_backend` until an unrelated reload (#48).
- A replica that genuinely loses the leader-election lease (renewal missed under apiserver/CPU starvation) now reinitializes and re-enters the election loop instead of running as a permanent follower with a dead elector — client-go's election loop exits for good on a lost lease, so previously the replica could never lead again until a config change or pod restart; on single-replica deployments that meant a permanent deployment stall (#57).
- A structural deploy no longer trusts an empty config diff against a headerless on-disk config (one whose last write was a `skip_version` runtime push): it now forces one reload to activate the pushed body. Previously the runtime fast path could park a render carrying structural changes on the pod's disk without a reload — the dataplane writes the body even when the accompanying runtime actions fail — and the next deploy would fetch that disk state, see "no changes", report success, and mark Gateways `Programmed` while the running worker still served the old config; convergence then waited for an unrelated structural change (observed as 90s of refused connections on new TCP listeners in gateway-conformance shard 4, issue #56). A successful authoritative runtime-raw apply now also re-stamps the config's `# _version` header (one versioned skip_reload push) so the pure runtime lane stays reload-free across later syncs.
- The `transitionTime()` template helper now preserves condition `lastTransitionTime` for typed (schema-loaded) watched resources — previously it only handled map-shaped conditions, so in production every render re-stamped the timestamp, and each unchanged GatewayClass/Gateway/route/policy status was SSA-rewritten ~1/s under load, feeding watch events back into reconciliation; BackendTLSPolicy additionally now matches its existing `status.ancestors` entry by controllerName + ancestorRef instead of navigating the nonexistent `.status.parents` path (#63).
- The load-path `validationTests` gate now runs with its own 120s suite budget instead of inheriting the live change gate's 25s scatter-gather budget. On slow or contended nodes the engine compile plus the `haproxy -c` sweep legitimately exceed 25s at startup, which crash-looped fresh pods with "validationTests did not complete within the suite timeout" despite a valid config.
- The CRD watch re-checks an inconclusive re-resolution on a bounded 5s cadence (until stable-equal for 3 consecutive checks) instead of accepting a single "no change" answer — a re-resolution racing the apiserver's discovery-propagation lag after a CRD apply no longer stalls the reload permanently (#59).
- Resource status conditions no longer race the infrastructure they describe: the "rendered" status variant (e.g. a Gateway's `Accepted=True`) is now applied only after the same render's `spec.k8sResources` (e.g. per-Gateway Services carrying the `gateway.networking.k8s.io/gateway-name` label) have been applied. Previously the status applier and resource applier consumed sibling events in parallel, so a consumer reacting to `Accepted=True` could list the Gateway's generated infrastructure before it existed.
- Components with latest-wins event semantics (status applier, resource applier, deployer) now drain their event subscription through an unbounded coalescing mailbox: an intake goroutine empties the bus-side buffer immediately and collapses uninterrupted runs of coalescible events to their latest element, so a slow handler (e.g. status applies taking seconds under churn) can no longer cause the event bus to overflow the subscription buffer and drop events. Each component declares which event types are latest-wins for it (the status applier coalesces rendered/deployment events; the deployer deliberately not deployment-completed, which carries its per-deploy bookkeeping), and status applies fan out wider so the apply keeps pace with the deploy cadence. Previously a sustained burst could drop the final events of the burst — including deployment-completed events — leaving resource status stale until the next config change or drift check.
- A pod's `deployedToPods` status entry is no longer silently lost when its deployment completes before the initial `HAProxyCfg` publish lands (a startup race): the per-pod status write previously swallowed the NotFound as success and — with subsequent no-op deploys deduped on the unchanged checksum — never retried, leaving the pod unreported until the next config change or drift check. The update is now requeued and retried until the resource exists.
- Event coalescing no longer starves the coalesced event type under sustained load: the drain previously held the latest coalescible event back until the subscription channel emptied, so during long bursts (e.g. continuous resource churn) rendered status patches could stall for the whole burst while deployment-completed events kept being handled — and later events of other types were dispatched ahead of the older held event. Coalescing now flushes the held event at every run boundary, preserving arrival order across event types.
- Reload-free map-only and certificate-only updates no longer fail on HAProxy 3.4: a skip-reload config push with no runtime server actions previously sent an empty `X-Runtime-Actions` header, which HAProxy 3.4's DataPlane API rejects (`empty value is not allowed`); the header is now omitted when there are no actions to apply.
- A failed deployment to a pod no longer records the new config checksum on `HAProxyCfg.status.deployedToPods[].checksum`, which previously made a partial/failed rollout read as fully converged (the checksum matched `spec.checksum` even though the pod was serving stale config). The pod now keeps its last successfully-deployed checksum plus a `lastError`, so checksum-equality consumers correctly see it as not-yet-converged.
- A partial or failed deployment is no longer cached as the "last deployed" config hash, so the controller re-attempts it on the next reconcile instead of suppressing the retry until the config changes or the drift-prevention timer fires (previously up to `driftPreventionInterval` of delayed self-heal).
- DataPlane API minor versions newer than the newest bundled client (v3.3) now clamp down to it instead of selecting the oldest, most-restrictive v3.0 client; the client-selection and schema-validator version-resolution paths now agree.
- The `_global` shared-fixtures entry in `validationTests` is no longer executed as a standalone test — it inflated the reported test count and ran its assertions against an empty-fixture render. Its fixtures still merge into every real test.
- Watched-resource admission (e.g. Ingress) now uses the same ~9 s internal validation deadline as `HAProxyTemplateConfig` admission (was 5 s), so a large-config dry-run is not prematurely cut off and admitted-without-validation under the webhook's 10 s budget.
- Config-publisher Kubernetes API calls (CRD publish, pod status updates, pod-reference cleanup) now derive from the controller's lifecycle context, so they cancel promptly on shutdown or config-triggered iteration restart instead of running against a background context; the final pre-shutdown flush still completes via a detached context.
- Hardened controller component lifecycle: leader-only components (DeploymentScheduler, DriftPreventionMonitor, ConfigPublisher) now unsubscribe from the event bus on shutdown, so a pod that re-acquires leadership no longer stacks orphaned subscriptions that fill up and log "critical drops" indefinitely; the StatusUpdater's `Stop` is now idempotent (no panic on a double stop); and the commentator, debug event buffer, metrics, and HTTP-store event loops now recover from a handler panic instead of silently killing the goroutine.
- `controller validate` and production now build identical template render contexts. The `capabilities` map is exposed in validation/benchmark renders too (it was production-only, so capability-gated templates could validate differently than they ran), and production now always populates `extraContext` (an empty map when unset, avoiding nil panics in `extraContext | dig(...)`) and promotes its top-level keys (e.g. `{{ debug.enabled }}`) the same way validation already did. Previously a template could pass `controller validate` yet render differently in production.
- Fixed a potential permanent config drift after runtime fast-path applies: a skip_version push leaves the pod's config without a `# _version` header (it reads as version 1 for any body), and the version cache could falsely treat a later "version 1" reading as unchanged and skip a needed sync. Version 1 is now treated as unknown state — never a cache hit, never cached.
- HAProxy 3.3 configurations are now schema-validated against the bundled v3.3 DataPlane API schema; previously they were validated against the v3.2 schema even though the v3.3 validators shipped with 3.3 support.
- HAProxy target paths (map/cert/general-file references in rendered configs and DataPlane API identifiers) are now handled with slash-only path semantics, so they no longer pick up the host OS path separator when the controller binary runs on Windows (no-op on Linux).
- Eliminated intermittent 503s during rolling restarts of single-replica backends: a newly-Ready pod's endpoint change now reaches the live workers within `option redispatch`'s rescue window even when it coalesces with another tenant's in-flight or interval-gated structural deploy, and runtime applies retry across a concurrent reload (master socket briefly down).
- Deployment scheduler now bounds reloads to ≤1 per `minDeploymentInterval` under concurrent churn, eliminating a reload storm that could surface as `<BADREQ>` 400s or dropped connections on the h2c loopback.
- Auxiliary-file UPDATEs no longer trigger a separate dataplane auto-reload; all aux changes batch into the main config sync's single reload, fixing SPOE-group and crt-list shrink races.
- Credentials-Secret rotation now triggers a controller iteration restart, and `SingleWatcher` no longer drops content updates on resources (Secrets/ConfigMaps) that keep `generation` at 0 (the generation-unchanged skip now applies only when a status subresource exists).
- `default_backend` now returns a gRPC trailers-only response (`grpc-status: 12`) for `application/grpc` requests instead of a plain 404 that tore down the HTTP/2 connection.
- GRPCRoute method matching now routes correctly on TLS+ALPN-h2 and plaintext h2c, and gRPC over h2c is multiplexed with HTTP/1.1 on the same bind.
- Gateway TLS listeners on non-default ports now bind (Terminate via crt-list + SNI routing, Passthrough via `req_ssl_sni`); TLS listeners in `ProtocolConflict` report `supportedKinds: []`; TLSRoute mixed-termination listeners report `Accepted=False/ProtocolConflict`.
- Gateway frontend/backend client-certificate validation: hostname-less listeners verify against the configured CA, backend `clientCertificateRef` emits `crt`, and per-listener mTLS / ListenerSet hostname-protocol conflict statuses now land correctly.
- Per-Gateway marker / static-address Service names stay within the 63-char limit and land in the Gateway's own namespace; fixed a Scriggo register-allocation bug that corrupted their discovery labels.
- Renderer now fails fast when the config references a map file it didn't register, instead of deleting it as unreferenced and breaking every subsequent reload.
- Render-time view of the watched-resource stores is pinned per render across `List()`/`Fetch()`/`GetSingle()`, so one snippet can no longer iterate a different resource set than another within a single render.
- `StoreWrapper` no longer triggers a full `Store.List()` on per-key reads against `store: on-demand` resources (was one API fetch per cached reference on every drift cycle).
- Debug introspection endpoints (`/debug/vars/resources`, `/debug/vars/state`, `/debug/vars/all`) no longer trigger one kube-apiserver lookup per resource for `store: on-demand` types; resource counts are read from the in-memory reference index instead.
- Deployer's per-pod version cache now stores each pod's actual post-sync state, so cross-pod drift is detected and fixed up instead of silently serving a stale config.
- Deployment scheduler no longer skips a deployment after a render race left a stale `lastDeployedConfigHash`, which could keep a newer render from ever reaching HAProxy.
- HTTP resource store no longer misclassifies an empty `200 OK` (no ETag) as `304 Not Modified`, which kept serving stale content.
- SSL-certificate Secret publishing now retries on write conflict and `AlreadyExists`, matching the other auxiliary-file publish paths.
- Backend comparator now detects `default-server` parameter changes, so a backend whose only delta is on its `default-server` line reloads instead of silently staying on stale settings.
- `dig()` now returns nil for absent optional fields on typed globals, so `dig(obj, "field") | fallback(default)` behaves identically for typed and untyped resources (#52).
- Gateway/Ingress resources whose addition produces no config diff (e.g. a Gateway with no attached routes) now get their `Programmed` status written instead of sticking at `Programmed=Unknown`; status patches travel on the deploy event, fixing a stale-status race under render churn.
- Status patches, admission overlays, and owned-resource apply now resolve a watched resource's plural via the cluster RESTMapper instead of a built-in pluralization guess, so a CRD with an irregular served plural no longer targets a nonexistent GroupVersionResource.
- Controller no longer schedules a spurious iteration restart ~1s after every startup.
- Bundled SPOA hub updated to v0.7.3: reloads now quiesce in-flight SPOE dispatches before retiring the old plugin set (fixing mirror losses around config reloads, #47), unhandled SPOE messages are surfaced via WARN log and `spoa_messages_unhandled_total`, reload drains in-flight mirror/OTLP work before swapping, and earlier hub fixes are included (use-after-free segfaults on plugin reload, config-reload conformance flake).

### Removed

- `renderResource()` template function — use `spec.k8sResources` instead.
- The dormant event-driven webhook-cert-rotation pipeline (the `certloader` component, its cert events, the webhook-cert watcher, and the `haptic_webhook_cert_expiry_timestamp_seconds` / `haptic_webhook_cert_rotations_total` metrics) — it was never wired in and never rotated certs; webhook-cert hot-reload (see Added) replaces it.
- `namespaceSelector` on `watchedResources` entries (was never wired up). Scope at the template level, via `labelSelector:`, or with separate controller instances.
- Management of HAProxy `program` sections — `client-native` v6.4.0 dropped the `program` model (HAProxy removed the section in 3.3). Rendered configs may still contain `program` sections on older HAProxy versions, but the controller no longer parses, diffs, or normalizes them.

## [0.1.0] - 2026-03-09

### Added

- **Template-driven HAProxy configuration**: Generate HAProxy configs using Scriggo templates (Go-based, Jinja2-like syntax) with full access to Kubernetes resources, built-in utility functions, and modular template snippets
- **Embedded validation tests**: Declarative test fixtures and assertions for testing HAProxy configurations within template libraries; run via `haptic-controller validate --test <name>`
- **Dry-run validation webhook**: Admission webhook that intercepts CREATE/UPDATE on opted-in watched resources (Ingress, HTTPRoute, GRPCRoute by default), renders templates with the proposed object overlaid on the live store, and rejects the write if rendering or HAProxy validation fails
- **Multi-architecture container images**: `linux/amd64`, `linux/arm64`, `linux/arm/v7`
- **HAProxy version support**: 3.0, 3.1, 3.2, 3.3 — version-specific images tagged accordingly
- **Supply chain security**: Container images, binaries, and Helm charts signed with Cosign (keyless OIDC); SBOM attestations in SPDX format
- **Prometheus metrics**: Reconciliation timing, template rendering duration, validation results, and Kubernetes API latencies
- **Leader election for high availability**: Multiple controller replicas with automatic leader election; hot-standby replicas continue watching and validating; configurable failover timing
- **Stall detection**: Components detect when blocked and report unhealthy via `/healthz`, enabling automatic pod restart via Kubernetes liveness probes
- **Configurable deployment timeout**: `deploymentTimeout` in dataplane config (default: 30s) to recover from stuck deployments
- **Server slot preservation**: Preserve HAProxy server slots during rolling deployments to enable zero-reload runtime API updates via `currentConfig` template context
- **HAProxy Ingress annotation compatibility**: 56 `haproxy-ingress.github.io/*` annotations via the haproxy-ingress template library
- **Dataplane API concurrency limiting**: `maxParallel` config option to limit concurrent API operations, preventing timeouts for large configurations
- **CRD content compression**: HAProxyCfg content compressed with zstd when exceeding `configPublishing.compressionThreshold` (default 1 MiB), reducing etcd storage
- **HAProxyGeneralFile CRD**: Publish general files (error pages, etc.) as Kubernetes custom resources with compression support
- **HAProxyCRTListFile CRD**: Publish crt-list files as Kubernetes custom resources with compression support
- **`semver_gte` template filter**: Version comparison for gating features on HAProxy version (e.g., `semver_gte(haproxyVersion, "3.3")`)
- **Template-driven status patches**: Templates can register status patches for any Kubernetes resource via `statusPatch()` function, with outcome-keyed variants (`rendered`, `deployed`, `renderFailed`, `deployFailed`) applied automatically based on pipeline phase
- **Backend diff field diagnostics**: Reconciliation log now includes which BackendBase fields caused backend updates, aiding diagnosis of false diffs from parser round-trip asymmetries
- **Status patch helper functions**: `condition()`, `transitionTime()`, and `toJSON()` template functions for building Kubernetes status conditions with stable transition timestamps

### Changed

- **Reconciliation triggering**: Leading-edge triggering with a 5s refractory period; no latency for isolated changes, bursts during that window are batched into a single reconciliation
- **Parallel Dataplane API operations**: Operations execute in parallel within each priority group, reducing sync time for large configurations
- **Balance directive**: `balance roundrobin` moved to `defaults` section to prevent silent behavior change when upgrading to HAProxy 3.3 (which changed the default balance algorithm from `roundrobin` to `random`)
- **Go runtime 1.26.1**: Green Tea GC replaces manual GOGC tuning
